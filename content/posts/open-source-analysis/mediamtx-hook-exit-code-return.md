외부 명령이 오류로 끝났는데 서버 로그에는 종료 코드 0이 남았습니다. 자동 재시작을 끄면 오류 종료 로그 자체가 사라졌습니다. 둘은 서로 다른 증상처럼 보이지만, 같은 반환값 누락에서 시작됐습니다.

MediaMTX 훅의 결과 전달 경로를 조사하면서 저는 실제 프로세스의 종료 상태와 서버가 받은 값을 대조했습니다. [PR #6155](https://github.com/bluenviron/mediamtx/pull/6155)의 수정은 한 줄이지만, 중요한 판단은 훅의 실행 정책을 바꾸지 않고 **잃어버린 실패 결과를 기존 콜백에 돌려주는 범위로 한정**한 것입니다. 조사·구현·실측·검토는 AI 협업으로 진행했고, 공개할 원인과 검증 범위를 확인했습니다. 이 PR은 2026년 8월 30일 병합돼 [v1.21.0 릴리스](https://github.com/bluenviron/mediamtx/releases/tag/v1.21.0)에 포함됐습니다.

## 실패는 자식 프로세스에서 이미 발생하고 있었다

MediaMTX는 방송 시작이나 접속 같은 사건에서 외부 명령을 실행할 수 있습니다. 이런 훅이 파일 등록 등 후속 작업을 담당할 때, 서버가 실패를 제대로 보고하지 않으면 작업 자체가 성공했다고 잘못 해석할 수 있습니다. 다만 이 버그는 프로세스를 성공으로 바꾸거나 실패를 복구하는 기능의 문제가 아닙니다. 이미 발생한 종료 결과를 상위 계층이 잘못 받는 문제였습니다.

non-Windows 구현은 실행 오류에서 `*exec.ExitError`를 찾고 `ExitCode()`를 호출했습니다. 그러나 반환하지 않아 아래의 기본값 0까지 제어 흐름이 내려갔습니다. 값을 읽는 코드가 있다는 것만 보고 정상이라고 판단하기 쉬운 형태입니다. 필요한 것은 계산식의 존재가 아니라 그 값이 호출자에게 도달하는지였습니다.

[회귀를 도입한 커밋](https://github.com/bluenviron/mediamtx/commit/7437ee7a)은 타입 단언을 `errors.As`로 바꾸는 과정에서 `return`을 빠뜨렸습니다. 이 형태는 v1.4.2부터 이어졌고, 이후 파일 이름이나 오류 변환 방식이 바뀌어도 누락이 남았습니다. Windows 구현은 이미 올바르게 반환하고 있었으므로 영향 범위를 모든 플랫폼으로 넓혀 쓰지 않았습니다.

## 같은 0이 재시작 설정에 따라 다르게 보였다

외부 명령의 결과는 기존 `OnExit` 보고 규칙을 거칩니다. 재시작 설정을 켠 경우에는 실패한 명령의 결과가 “code 0”으로 기록됐고, 끈 경우에는 잘못 전달된 0 때문에 실패 보고가 나타나지 않았습니다.

| 명령의 실제 종료 | 재시작 설정 | 수정 전 관측 | 수정 후 관측 |
|---|---|---|---|
| 오류 종료 | OFF | 실패 종료 로그 없음 | 실제 비영 종료 코드 보고 |
| 오류 종료 | ON | 종료 코드 0으로 기록 | 실제 비영 종료 코드 보고 |
| 정상 종료 | 기존 설정 | 기존 정책 적용 | 기존 정책 유지 |

PR의 최소 재현은 `runOnInit`에서 오류 종료하는 명령을 사용하는 방식입니다. 재시작을 켠 상태에서 같은 실패가 반복될 때 코드 0이 나오는지, 수정 후 실제 코드가 나오는지 비교했습니다. 재시작 간격을 바꾸는 방식으로 증상을 가리지 않았습니다.

이 차이를 구분하지 않고 “오류가 항상 0으로 로그에 찍혔다”고만 쓰면 OFF 조건을 놓칩니다. 반대로 “로그를 추가했다”고만 쓰면 기존 실패 보고 경로에 올바른 값이 전달되도록 고쳤다는 원인을 설명하지 못합니다.

## 수정은 반환 경계에, 검증은 상위 동작까지

수정은 `ExitError`를 확인한 분기에서 `ExitCode()`를 즉시 반환하도록 하는 것입니다. 기존 훅의 시작·종료 정책, 재시작 여부와 간격은 유지했습니다. 회귀 테스트에서는 종료 코드 5를 만드는 명령으로 재시작 ON/OFF 두 조건을 모두 확인했습니다.

| 검증 질문 | 사용한 조건 |
|---|---|
| 실패 코드가 0으로 덮이는가 | 실제 종료 코드 5 |
| 재시작 ON에서 값이 전달되는가 | 재시작 활성화 |
| OFF에서도 실패를 받을 수 있는가 | 재시작 비활성화 |
| 다른 플랫폼까지 같은 버그인가 | Windows 반환 경로와 대조 |

테스트가 중요한 이유는 수정 줄 수와 영향 범위가 비례하지 않기 때문입니다. 한 줄을 바꾸더라도 호출자가 그 값을 어떻게 해석하는지에 따라 관측 결과가 달라집니다. 최소 수정에 맞춰 검증도 반환값 하나로 끝내지 않고 설정별 보고 동작까지 연결했습니다.

## 모든 훅의 실패가 이 수정 하나로 보이는 것은 아니다

이 PR은 이미 `OnExit`를 연결한 훅에 실제 실패 결과를 복구합니다. 콜백 자체가 없는 다른 호출부까지 해결한 것은 아닙니다. 이후 [PR #6259](https://github.com/bluenviron/mediamtx/pull/6259)에서는 외부 명령을 생성하는 13곳 중 콜백이 없는 7곳을 별도 문제로 다뤘습니다. 반환값과 호출부의 배선을 분리해 봐야 관측 공백의 전체 범위를 설명할 수 있습니다.

또 시그널로 종료된 프로세스는 Go의 종료 코드 의미에 따라 -1로 보고될 수 있습니다. MediaMTX가 직접 중지시키는 경로는 기존처럼 `OnExit`에 도달하기 전에 처리됩니다. 단순히 “0이 아니면 어떤 경우든 같은 실패 로그를 낸다”는 새로운 정책을 도입한 것이 아닙니다.

이 변경으로 정상 스트림의 처리속도가 빨라졌다는 주장은 하지 않습니다. 성과는 실패한 명령을 실패한 결과로 관측하게 된 것입니다. 로그가 잘못됐을 때 메시지를 먼저 고치기보다, 실제 사건에서 반환값과 콜백을 거쳐 기록까지 이어지는 경로를 따라가야 했습니다. 그 경로에서 빠진 return 하나가 오류 관측의 의미를 바꾸고 있었습니다.
