방송이 잠시 끊겼을 때 시청 화면을 유지하는 대체 영상은 유용합니다. 하지만 그 화면까지 원본 녹화에 계속 쌓이면, 편집용 기록에는 실제 방송이 아닌 구간이 포함됩니다. “시청 가능한 경로가 있다”와 “실제 방송 소스가 온라인이다”는 같은 상태가 아니었습니다.

MediaMTX의 이 문제에는 이미 AbdElrahmaN31의 [PR #5767](https://github.com/bluenviron/mediamtx/pull/5767)이 있었습니다. 저는 원 작성자의 커밋을 보존하고 그 작업을 [PR #6182](https://github.com/bluenviron/mediamtx/pull/6182)로 이어갔습니다. 제 기여는 새 설정의 아이디어를 처음 만든 것이 아니라 **누락된 static source·설정 재적용 경계를 확인하고, 같은 상태 규칙과 회귀 테스트로 보완한 것**입니다. 구현·검증에는 AI 협업을 활용했습니다.

이 PR은 2026년 9월 5일 병합돼 **[v1.21.0 정식 릴리스](https://github.com/bluenviron/mediamtx/releases/tag/v1.21.0)에 반영됐습니다.**

## 원 기여가 해결한 경로와 남은 경로를 나눴다

`alwaysAvailable`은 실제 소스가 오프라인이어도 대체 화면을 제공할 수 있게 합니다. `record`가 켜져 있으면 그 대체 화면도 녹화되는 기존 동작이 있었습니다. 원 기여는 `alwaysAvailableRecorded` 설정으로 이를 끌 수 있게 하는 출발점이었습니다.

그러나 publisher가 연결되는 경로에서 녹화 시작을 처리하는 것만으로는 충분하지 않았습니다. MediaMTX는 외부 publisher뿐 아니라 설정된 static source가 온라인이 되는 경로도 갖습니다. 이 경로에서는 publisher 추가 함수만 거치지 않으므로 녹화 시작이 누락됐습니다.

설정 reload에는 다른 빈틈이 있었습니다. `pa.source != nil`을 온라인 판정으로 사용하면 실제로 연결되지 않은 static source 객체나 대체 소스의 존재를 실제 방송으로 해석할 수 있습니다. 오프라인 상태에서 설정을 다시 읽었을 뿐인데 대체 화면의 녹화가 시작되는 이유였습니다.

| 같은 회귀 시나리오 | 원 기여 커밋만 적용 | 보완 뒤 |
|---|---|---|
| publisher가 온라인이 됨 | 정상 | 통과 |
| static source가 온라인이 됨 | 녹화 시작 누락 | 통과 |
| 오프라인 상태에서 reload | 대체 화면 녹화 시작 | 통과 |

기존 작업을 출발점으로 삼되, 새 분기의 존재만 확인하지 않고 서로 다른 진입 경로에서 같은 계약이 지켜지는지 대조했습니다. 원 기여를 지우고 모든 변경을 제 단독 성과로 쓰면 이 작업의 실제 경계를 잃게 됩니다.

## 녹화의 기준을 진입 함수에서 상태 전환으로 옮겼다

수정은 녹화 시작·종료를 `setOnline()`과 `setOffline()`에 연결하는 방향입니다. publisher와 static source가 모두 통과하는 상태 전환에서 처리하면 입력 방식이 달라도 같은 녹화 규칙을 따를 수 있습니다. reload 역시 source 포인터가 있는지보다 `isOnline()`을 확인하도록 바꿨습니다.

이를 통해 시청용 대체 화면을 제공하는 책임과 실제 원본을 녹화하는 책임을 분리했습니다. 소스가 끊겨도 대체 화면은 계속 제공할 수 있지만, 사용자가 해당 옵션을 끄면 오프라인 구간은 녹화하지 않습니다. 두 기능을 동시에 켜거나 끄는 것으로 문제를 단순화하지 않았습니다.

이 경계를 고를 때 중요했던 것은 “어느 함수에 코드를 추가할까”보다 “언제 녹화가 시작되어야 하는가”였습니다. 하나의 요청 경로에만 조건을 더하면 다음 입력 방식이나 reload에서 같은 누락이 반복될 수 있습니다. 실제 소스의 온라인 여부라는 상태에 녹화 수명을 맞춘 이유입니다.

## 기본값과 설정 인터페이스도 변경 범위였다

`alwaysAvailableRecorded`의 기본값은 `true`로 유지했습니다. 기존 사용자는 설정을 바꾸지 않으면 대체 화면을 녹화하던 동작을 그대로 얻습니다. `false`를 선택한 경우에만 실제 소스가 온라인인 동안 녹화합니다.

| 설정 | 동작 |
|---|---|
| 기본값 `true` | 기존 녹화 동작 유지 |
| 명시적 `false` | 실제 소스가 온라인일 때만 녹화 |
| 시청 경로 | 대체 화면 제공과 별도로 동작 |

새 옵션은 런타임 코드 안에만 있으면 충분하지 않습니다. `mediamtx.yml`의 설명과 생성된 OpenAPI 정의도 맞췄습니다. 파일 설정으로 보이는 이름과 API가 받는 계약이 달라지지 않게 한 것입니다. 이 작업의 공개 변경 범위는 PR의 파일 목록에서 확인할 수 있습니다.

## 재로드 중의 상태도 회귀 검증에 넣었다

재현 조건은 `alwaysAvailable` 활성화, `alwaysAvailableRecorded: false`, `record` 활성화, H264 트랙 1개였습니다. 같은 세 테스트를 원 기여 상태와 보완 상태에 적용했습니다. 원 기여에서는 publisher 시나리오만 통과했고, static source와 오프라인 reload가 실패했습니다. 보완 뒤 세 시나리오가 모두 통과했습니다.

테스트 실행 시간이 줄거나 늘어난 것을 녹화 성능 개선으로 쓰지 않았습니다. 검증한 것은 어떤 입력 경로로 온라인이 됐는지와 reload 당시 상태에 관계없이 정한 녹화 규칙이 지켜지는지입니다. 세 테스트의 성공이 모든 소스·코덱·장애 상황의 완전한 보장을 뜻하는 것도 아닙니다.

대체 화면을 녹화에서 빼는 요구는 설정 하나로 표현되지만, 실제 구현은 소스 수명과 재설정의 경계를 통과해야 했습니다. 기존 기여를 보존하면서 빠진 진입 경로를 보완한 경험은, 오픈소스 작업이 새 아이디어를 단독으로 내는 일뿐 아니라 다른 사람의 변경을 이어 실제 동작의 범위를 완성하는 일임을 보여줍니다.
