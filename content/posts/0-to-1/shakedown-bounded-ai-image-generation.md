Shakedown에서 저장소를 받아 이미지를 만들고 배포하는 경로를 연결하면서, AI에게 어디까지 생성하게 할지 먼저 정해야 했습니다. Dockerfile과 인프라 코드를 자유롭게 만들게 하면 지원 범위는 넓어 보이지만, 실행할 자원과 권한·실패 상태를 검토할 범위도 커집니다.

SoftBank Hackathon의 Emerald 팀에서 만든 Shakedown은 저장소 분석, 이미지 생성, 배포, HTTP 시운전을 연결하는 서비스입니다. 저는 PostgreSQL 샘플과 로컬 Target API에서 시작해 엔진 통합, 이미지 생성 순서, 선택한 AWS 계획의 적용과 복구 검증을 맡았습니다. 여기서는 **예측 가능한 부분은 규칙으로 처리하고, AI의 판단을 허용된 선택지 안으로 제한한 과정**을 설명합니다.

## Dockerfile이 있는데도 모델부터 호출할 필요는 없었습니다

생성 순서는 기존 Dockerfile, 지원 스택 규칙, 규칙 실패 때 Claude 1회, 생성 결과 검증, 별도 소스 복사본에서 빌드로 정했습니다. 기존 입력이나 규칙으로 처리할 수 있는 저장소까지 처음부터 모델에 맡기지 않았습니다.

| 단계 | 맡기는 일 | 다음 단계로 넘어가는 조건 |
|---|---|---|
| 기존 Dockerfile | 저장소가 제공한 빌드 방법 사용 | 기존 파일이 없는 경우 규칙 검토 |
| 지원 스택 규칙 | 알려진 구성에서 생성 | 규칙으로 처리하지 못한 이유 확보 |
| Claude fallback | 실패 진단과 제한된 분석 정보로 보완 | 허용 형식과 검증 조건 충족 |
| 결과 검증·빌드 | 실제 빌드 가능성 확인 | 원본을 덮어쓰지 않는 별도 복사본 사용 |

모델에 보낸 것은 제한된 분석 정보와 규칙 실패 진단입니다. 원본 코드, README, 환경변수 전체를 보낸다는 설계가 아닙니다. 근거가 부족하면 null을 허용했고, 생성 결과가 나왔다는 사실만으로 배포를 시작하지 않았습니다. 이 선택은 [이미지 생성 PR #11](https://github.com/SoftBankHackathon/shakedown/pull/11)에 포함됐습니다.

## 소스 코드만으로 운영 요구를 알아낼 수는 없었습니다

코드가 같아도 피크 트래픽과 허용 중단 시간은 다를 수 있습니다. 저장소 분석만으로 이를 추정해 정답처럼 실행하지 않도록 사용자 운영 입력을 받았습니다. 먼저 규칙으로 최소 등급을 정하고, 모델은 소·중·대 템플릿과 근거 ID 안에서 판단하게 했습니다.

이 방식은 임의의 IaC를 생성하는 것보다 지원 범위가 좁습니다. 대신 모델이 제안할 수 있는 자원·권한·비용의 범위와, 서버가 실행 전에 다시 검사할 항목을 정할 수 있습니다. 카탈로그는 실행 가능한 선택지이지, 적힌 등급이 특정 처리량을 보장하는 시험 성적표는 아닙니다.

## 실제 호출은 확인했지만, 개선율은 측정하지 않았습니다

2026년 10월 9일 [실제 AI 호출 보고서](https://github.com/SoftBankHackathon/shakedown/blob/0147f4774443568becab4421ee1b7c8d86b25513/docs/experiments/2026-10-09-live-ai.md)에서 규칙이 지원하지 않는 Flask 입력을 fallback으로 처리했습니다. 각 시간은 단일 호출의 관측값입니다.

| 시험 | 관측 |
|---|---|
| Flask fallback 1회 | 응답 3.679초, Docker 빌드와 HTTP 200 확인 |
| small 판단 1회 | 3.876초 |
| medium 판단 1회 | 4.551초 |
| large 판단 1회 | 4.434초 |
| large 요구에서 small 선택 | 400으로 거부 |
| 같은 요구에서 large 선택 | 200으로 수용 |

여기서 핵심은 몇 초 만에 답했는지보다, 요구보다 작은 선택을 실행 경계에서 거부했는지입니다. 호출 한 번씩의 시간을 모델 품질이나 속도 개선율로 일반화하지 않았습니다. Dockerfile 검사도 실행 샌드박스는 아닙니다.

## 팀 기반 위에서 맡은 경계

HTTP 시운전과 규칙·Claude 원인 보고서는 김태현, 초기 ECS·ALB·RDS 어댑터와 공유 세션 기반은 김재환, 초기 보안 게이트와 다국어 기본 보완은 김도경의 기여입니다. 제 역할은 그 기반을 연결하면서 요구와 허용 범위를 정하고, 결과에 따라 변경을 확정하는 것이었습니다. 조사·구현·실험 실행에는 AI를 활용했습니다. [고정 커밋의 작업 회고](https://github.com/SoftBankHackathon/shakedown/blob/078cb687d516aa50a95f3994ba099f0ec776914a/docs/retrospectives/2026-10-10-taeyun-engineering.md)에서 범위를 확인할 수 있습니다.

개인 PR #2·#5·#10·#11·#12·#29·#31은 2026년 10월 15일 기준 팀 저장소에 병합됐습니다. 이는 외부 오픈소스의 정식 릴리스 성과와 다른 종류의 결과이며, UI부터 검사·LLM·AWS까지 하나로 이어진 전체 E2E 성공을 의미하지도 않습니다.

이번 작업에서 AI 활용의 완료 조건은 그럴듯한 구성을 받는 것이 아니었습니다. 규칙으로 처리할 부분, 모델에 물을 부분, 실행 전에 거부할 부분을 나누고 실제 경계가 작동하는지를 확인하는 것이었습니다.
