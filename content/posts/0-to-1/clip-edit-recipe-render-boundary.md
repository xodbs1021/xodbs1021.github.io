가로 영상으로 만든 하이라이트를 세로 쇼츠로 바꾸고, 배경음악을 끄고, 자막의 위치를 다시 옮기려면 무엇을 저장해야 할까요. 완성된 영상 파일 하나만으로는 편집자가 어떤 구간과 트랙을 선택했는지 되살리기 어렵습니다. 결과물에 이미 합쳐진 음악이나 자막을 나중에 분리하는 문제까지 떠안게 됩니다.

PokeClip에서는 원본 미디어와 편집 결정을 나눠 보관하기로 했습니다. 저는 미디어·인프라 구조를 맡아 **클립을 편집 레시피와 렌더 결과물의 조합으로 정의하고**, 웹 미리보기와 서버 렌더의 책임을 정했습니다. 설계 초안·조사에는 AI 협업이 있었고, 웹과 Spring 코어·렌더 워커의 주 구현은 팀원 담당입니다. 이 글은 완성된 에디터의 성능 보고가 아니라 그 구현을 연결하기 위해 정한 계약을 설명합니다.

## 되돌릴 수 있어야 하는 것은 파일보다 선택이었다

편집 결과만 저장하는 방식은 재생과 배포가 단순합니다. 그러나 다시 편집하려면 사용자의 선택을 복원할 별도 정보가 필요합니다. 특히 PokeClip은 편집용 원본에 6개 오디오 트랙을 보존하고, 되감기용 출력은 영상 1개·오디오 1개로 구분합니다. 최종 혼합본만 보관하면 원하는 소리만 다시 고를 수 있다는 제품의 전제가 사라집니다.

그래서 원본은 유지하고, 사용자가 바꾼 선택은 레시피 JSON에 남기도록 설계했습니다. 레시피가 답해야 할 질문을 다음처럼 나눴습니다.

| 레시피의 정보 | 재렌더링할 때 필요한 이유 |
|---|---|
| 선택 시간 구간 | 원본의 어느 부분을 가져올지 결정 |
| 크롭·출력 비율 | 가로 영상과 세로 쇼츠의 화면 구성 재현 |
| 트랙·트랙별 음량 | 원본의 소리 중 무엇을 얼마나 사용할지 결정 |
| 제목·자막 스타일 | 영상 위 표현을 다시 구성 |

예를 들어 음악의 음량을 0으로 바꾸면 원본 파일을 덮어쓰는 대신 레시피의 선택을 바꿉니다. 서버는 같은 원본을 새 레시피로 읽어 다른 결과물을 만듭니다. 원본과 결과물 사이에 편집 의도가 남으므로, 파일을 다시 만들 필요가 생겨도 사용자가 처음부터 선택을 반복할 이유가 줄어듭니다.

## 미리보기와 최종 파일이 같은 일을 할 필요는 없었다

에디터에서 음량이나 화면 위치를 조금 바꿀 때마다 서버가 완성 파일을 만들면, 인터랙션이 렌더 작업의 완료에 묶입니다. 화면에서는 클라이언트의 video와 화면 합성으로 선택을 확인하고, 저장 시점의 최종 렌더를 서버의 비동기 작업으로 보내도록 책임을 나눴습니다.

렌더·업로드에는 작업 상태와 진행률, 재시도가 필요합니다. 긴 작업을 화면 요청의 수명과 분리하고, 재시도에서도 어떤 원본과 편집 선택을 사용했는지 다시 확인할 수 있어야 합니다. 다만 레시피가 존재한다는 사실만으로 모든 재시도가 동일한 바이트를 만든다고 보장할 수는 없습니다. 여기서 확정한 것은 편집 입력의 명시화이며, 인코더 환경까지 포함한 결과의 완전한 재현성 검증은 별도의 문제입니다.

자동 업로드 템플릿도 같은 레시피 모델을 사용하도록 했습니다. 구간이 정해지기 전에는 구간을 비워 두고, 실제 클립이 선택되면 나머지 편집 설정과 함께 사용합니다. 수동 편집과 자동 생성이 전혀 다른 입력 형식을 요구하지 않게 하는 선택입니다. 자막도 영상에 직접 입히는 번인과 별도 자막인 CC 출력 모드를 구분해, 편집자의 선택을 렌더 계층이 받을 계약에 포함했습니다.

## 빠른 재포장 경로를 렌더까지 확장하지 않았다

되감기용 재포장은 압축된 미디어를 다시 담는 작업입니다. 반면 크롭, 상하 분할, 자막 번인은 영상의 픽셀을 바꿉니다. [FFmpeg의 streamcopy 설명](https://ffmpeg.org/ffmpeg.html#Streamcopy)도 디코딩·필터링·인코딩 없이 압축 패킷을 전달하는 경로를 구분합니다. 픽셀을 바꾸는 필터 처리는 [별도의 필터링 경로](https://ffmpeg.org/ffmpeg.html#Filtering)가 필요합니다.

필터가 없는 키프레임 컷에 smart cut 예외를 두는 방법도 검토했습니다. 하지만 기본 렌더와 예외 경로를 함께 유지하면 입력 조건에 따라 결과 생성 방식이 달라지고, 두 경로를 모두 검증해야 합니다. 당시에는 최종 출력의 기본 흐름을 재인코딩으로 통일했습니다. 모든 미디어 처리를 한 방법으로 해결하기보다, 되감기와 편집 결과의 목적이 다르다는 데서 경계를 정한 것입니다.

| 확인한 내용 | 현재 이 사례가 입증하는 범위 |
|---|---|
| 원본·레시피·결과물의 분리 | 편집 의도와 실행 결과를 나누는 계약 |
| 미리보기·최종 렌더의 분리 | 화면 조작과 긴 서버 작업의 책임 구분 |
| 트랙·볼륨·자막 출력 모드 | 편집자의 선택을 렌더 계층에 넘길 입력 정의 |
| 렌더 처리 시간·비용 절감률 | 이 설계 기록에서 측정하지 않음 |

## 원본을 남기는 대가도 남는다

레시피로 저장해도 렌더 자원과 원본 보관 비용은 사라지지 않습니다. 다시 만들 수 있다는 장점은 원본을 계속 읽을 수 있다는 조건에 의존합니다. 편집 계약을 정했다는 사실과 에디터·렌더·업로드 전체가 운영 배포됐다는 사실도 구분해야 합니다.

이 선택의 기준은 파일 개수를 줄이는 데 있지 않았습니다. 사용자가 이미 한 결정을 잃지 않고 다음 편집으로 이어갈 수 있느냐였습니다. 원본을 보존하고 편집 의도를 명시한 덕분에, 미디어 계층과 팀원의 렌더 계층이 무엇을 주고받아야 하는지부터 합의할 수 있었습니다.
