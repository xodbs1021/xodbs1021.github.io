AI 코딩 세션을 Git 워크트리마다 나눠 띄워도, 그 세션들을 검사하는 개발 하네스의 상태는 한 폴더를 같이 썼습니다. 2026년 10월 1일 한 세션이 다른 세션이 남긴 산출물 9개 때문에 종료를 세 번 막혔고, 같은 날 읽기만 한 Bash 호출 하나가 체크아웃 파일 197개를 리뷰 대상으로 적었습니다. 워크트리에서 고친 코드에는 거꾸로 검사 표시가 생기지 않았습니다. 검사 상태를 세션별 폴더로 옮기고, 작업 루트를 세션의 첫 훅에서 정해 끝까지 유지하게 바꿨습니다. 10월 2일 로컬에 적용했고 10월 12일 하네스 템플릿의 main에 병합했습니다.

하네스는 AI 코딩 에이전트(Claude Code)가 도구를 쓰기 전후와 작업을 끝낼 때 도는 훅, 그리고 아직 남은 리뷰나 변경 설명 같은 의무를 표식 파일로 관리하는 장치입니다. 10월 1일 저는 이 결함을 그 세션에서 바로 고치기로 했고, 격리 단위를 세션으로 정했으며, 예전 공유 폴더의 표식은 읽지도 지우지도 않기로 했습니다. 10월 2일에는 루트를 첫 훅에서 고정하기로 정했고, 메인 체크아웃과 워크트리 4곳에 로컬로 적용하는 것과 병합을 승인했습니다. 구현과 시험은 AI(Claude Code)가 했고 리뷰는 Claude Code와 Codex가 했습니다. 하네스 템플릿 저장소는 비공개라 PR은 링크하지 않습니다.

## 워크트리를 나눠도 검사 상태는 한 폴더를 같이 썼습니다 {#코드-디렉터리와-검사-상태의-경계가-달랐다}

Git 워크트리는 한 저장소의 여러 브랜치를 서로 다른 작업 폴더에 펼칩니다([git-worktree 문서](https://git-scm.com/docs/git-worktree)). 저장소 정보의 일부는 공유하고, Git 밖에서 도구가 만든 상태 파일은 나눠 주지 않습니다.

Claude Code 데스크톱 앱은 워크트리에서 연 세션에도 환경 변수 `CLAUDE_PROJECT_DIR`로 메인 체크아웃의 경로를 넘겼습니다. 공개 문서도 워크트리 세션에서 `CLAUDE_PROJECT_DIR`은 세션을 시작한 프로젝트 루트에 머물고, 훅 입력의 `cwd`가 워크트리 루트를 가리킨다고 설명합니다([Claude Code 워크트리 문서](https://code.claude.com/docs/en/worktrees#what-worktrees-share-with-the-main-checkout), 11월 12일 확인). 하네스는 이 값 하나로 상태 폴더도 정하고 「이 파일이 코드인가」도 판정했습니다. 그래서 서로 다른 세 증상이 같은 가정에서 나왔습니다.

| 증상 | 원인 | 실제 영향(10월 1일) |
|---|---|---|
| 다른 세션의 의무를 읽음 | 모든 세션이 같은 상태 폴더를 씀 | 다른 세션의 산출물 9개 때문에 종료가 3번 막힘 |
| 읽기 작업이 변경으로 잡힘 | Bash 변경 감지 시간 창을 세션끼리 공유 | 체크아웃 파일 197개가 리뷰 대상으로 기록됨 |
| 워크트리 수정이 빠짐 | 메인 체크아웃 기준 상대 경로로만 파일을 분류 | 워크트리의 실제 코드가 하네스 밖 경로처럼 보여 검사 누락 |

검사 규칙을 늘려서는 풀리지 않았습니다. 먼저 「어느 세션의 상태인가」와 「어느 체크아웃의 파일인가」를 나눠야 했습니다.

## 검사 상태를 세션별 폴더로 옮기고 옛 공유 상태는 건드리지 않았습니다 {#상태는-세션별로-기존-상태는-그대로}

훅 입력에는 세션을 가리키는 `session_id`가 들어 있습니다([Claude Code 훅 문서](https://code.claude.com/docs/en/hooks)의 공통 입력 필드). 이 값이 있으면 세션 ID의 SHA-256 앞 32자리(128비트)를 이름으로 한 세션 폴더에 상태를 씁니다. 처음에는 `cksum`(32비트)으로 이름을 만들었는데, 리뷰에서 Codex가 서로 다른 세션 ID 두 개가 같은 이름이 되는 실제 충돌 예를 찾아내 SHA-256으로 바꿨습니다. 그 충돌 쌍은 시험 케이스로 남겼습니다.

세션 폴더에는 리뷰 필요 표식뿐 아니라 Bash 변경 감지 창과 종료 차단 횟수도 넣었습니다. 서브에이전트의 도구 호출도 부모와 같은 `session_id`를 싣는 것을 10월 1일 확인했습니다. 그래서 이 변경은 에이전트마다 상태를 나누는 것이 아니라, 한 작업 세션의 의무를 한곳에서 관리하는 것입니다.

영상은 두 워크트리 세션이 표식을 한 공유 폴더에 쓰다가 세션별 폴더로 갈라지는 전후입니다. 앞부분에서 세션 A가 세션 B의 표식 때문에 막히는 것을 보십시오.

`session_id`가 없는 입력은 예전 공유 폴더로 돌아가게 남겼습니다. 반대로 `session_id`가 있는 세션은 예전 공유 폴더의 표식을 읽지도 지우지도 않습니다. 새 세션이 남의 오래된 의무를 떠안거나, 다른 실행에 필요한 표식을 지우지 않게 하려는 결정이었습니다.

## 작업 루트는 첫 훅에서 정해 세션 내내 유지합니다 {#루트는-첫-훅에서-정하고-세션-동안-유지}

상태 폴더를 나눠도 파일 분류 기준이 메인 체크아웃이면 워크트리 편집은 계속 빠집니다. 그래서 세션의 첫 훅이 받은 `cwd`를 작업 루트로 정해 세션 폴더의 `.root`에 한 번만 기록하고, 이후 `cd`로 옮겨 다녀도 바꾸지 않게 했습니다. 기록은 하드 링크로 「없을 때만 만들기」를 원자적으로 하고, 하드 링크를 쓸 수 없으면 셸의 noclobber(`set -C`)로 대신합니다.

처음 설계는 의무마다 루트를 따로 적는 것이었습니다. 그러면 앞서 생긴 리뷰 의무와 나중에 도는 검사가 서로 다른 체크아웃을 가리킬 수 있습니다. 교차 검토 뒤 10월 2일 「한 세션에는 루트 하나」로 단순화했습니다.

## 커밋 가드를 넓히자 다른 저장소의 커밋까지 막혔습니다

하네스에는 기본 브랜치(main)에 바로 커밋하는 것을 막는 가드가 있습니다. 워크트리를 다루면서 이 가드가 `git -C`, `cd`, 훅 입력의 `cwd`로 가리킨 저장소까지 보게 넓혔습니다. 그러자 main에 직접 커밋하는 것이 규약인 별도 저장소의 정상적인 저장 커밋까지 막혔습니다. 같은 날 실제로 일어난 회귀였습니다.

고친 기준은 Git의 공통 디렉터리입니다. 같은 저장소의 워크트리들은 `git rev-parse --git-common-dir`가 같은 곳을 가리킵니다([git-rev-parse 문서](https://git-scm.com/docs/git-rev-parse)). 워크트리의 `.git`은 디렉터리가 아니라 실제 Git 디렉터리를 가리키는 파일일 수 있어서([gitrepository-layout 문서](https://git-scm.com/docs/gitrepository-layout)), 폴더 모양이 아니라 이 값을 비교했습니다. 대상의 공통 디렉터리가 세션 루트와 같을 때만 막게 바꿨습니다. 이어서 Codex가 「Git 조회가 실패하면 다른 저장소로 보고 통과시킨다」는 빈틈을 지적해, 조회 실패는 막는 쪽으로 다시 고쳤습니다. 두 경우 모두 회귀 시험을 더했습니다.

## 일부러 망가뜨린 구현 32개 중 31개를 시험이 잡았습니다 {#정상-통과뿐-아니라-잘못된-구현을-잡는지도-확인}

시험이 통과한다는 것만으로는 시험이 결함을 놓치는지 알 수 없습니다. 그래서 상태 공유나 판정 오류를 일부러 되살린 구현(변이)을 만들고, 시험이 그 구현에서 실패하는지 확인했습니다.

| 검증 대상 | 당시 기록 |
|---|---|
| 세션 상태 격리 | 시험 14개, 변이 8개 모두 검출. 기존 시험 12종 통과 |
| 작업 루트 판정 | 시험 54개, 변이 24개 중 23개 검출. 기존 시험 13종 통과 |
| 커밋 가드 회귀 | 다른 저장소 통과, 조회 실패 차단 시험 2개 추가 |
| 적용 범위 | 10월 2일 메인 체크아웃과 워크트리 4곳에 로컬 적용, 10월 12일 템플릿 main에 병합 |

세션 격리 쪽 변이는 세션 폴더를 묶는 줄을 지우거나, 감지 창을 쓸어 담을 때 `session_id`를 넘기지 않거나, 이름을 다시 `cksum`으로 되돌리는 식이었습니다. 루트 판정에서 살아남은 변이 하나는 같은 방어가 두 겹이라 한 겹을 지워도 시험이 통과한 경우였고, 겹친 다른 방어는 별도의 변이로 잡혔습니다. 그래서 모든 잘못된 구현을 잡았다고 쓰지 않습니다. 이 수치는 개발 속도가 빨라졌다는 측정이 아니라, 특정한 누락과 상태 간섭을 막는다는 회귀 근거입니다.

## 세션 격리는 의무 승계와 다른 체크아웃 검사를 하지 않습니다 {#세션-격리가-해결하지-않는-것}

남은 한계는 다음과 같습니다.

- 세션이 바뀌면 이전 세션에 남은 의무를 이어받지 않습니다.
- 리뷰 산출물 일부와 변경 감지의 시간 창 일부는 여전히 공유합니다.
- 첫 훅이 엉뚱한 폴더에서 시작하면 그 루트가 세션 내내 유지됩니다. `.root`는 같은 저장소인지 따로 검사하지 않습니다.
- 다른 체크아웃의 편집은 의무로 적지만, 그 체크아웃의 타입 검사·스타일 검사·push 확인까지 돌리지는 않습니다.
- 하드 링크를 쓸 수 없는 파일 시스템의 noclobber 대체 경로는 원자적이지 않고, SHA-256 계산이 실패하면 `cksum`으로 대신합니다. 그래서 악의적인 우회를 막는 보안 격리 장치로 설명할 수 없습니다.

템플릿은 그 뒤 10월 17일까지 바뀌었습니다. 세션 루트 밖에 따로 선언한 폴더 안의 저장소에도 표식 4종을 거는 설정(`HARNESS_EXTRA_GATE_DIRS`)이 생겼습니다. 다만 타입 검사, 스타일 검사, push 확인, 커밋 가드는 이 설정의 폴더에 적용하지 않기로 제가 정했으므로, 위의 넷째 한계는 그 폴더에도 그대로입니다.

10월 5일에는 셋째 변경으로 리뷰와 변경 설명 검사를 매 턴 끝이 아니라 커밋·push·PR 생성 직전으로 옮기려 했지만, 하네스 개발은 단계마다 리뷰하는 편이 낫다고 판단해 철회했습니다.

워크트리를 늘려 병렬로 개발한다면 코드 충돌만 보지 말고, 그 작업을 검사하는 도구가 어떤 상태를 공유하는지부터 확인하십시오. 상태의 주인과 검사 대상이 어긋나면 검사 규칙을 아무리 늘려도 엉뚱한 세션을 막거나 진짜 변경을 놓칩니다.
