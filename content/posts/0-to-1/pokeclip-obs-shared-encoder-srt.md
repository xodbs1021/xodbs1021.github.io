방송자는 이미 OBS로 본방을 인코딩하고 있다. PokeClip에 같은 화면을 보내기 위해 영상 인코더를 하나 더 만들면 추가 부담을 떠안게 된다. 그래서 본방이 만든 압축 프레임을 SRT 출력에도 전달하는 구조를 선택했다. 그런데 같은 인코더를 공유한다는 결정은 시작 전에 바꿔야 할 설정과 종료 때 함께 정리해야 할 자원까지 묶는 일이었다.

나는 전체 송출 구조와 미디어 입력 계약을 정하고 OBS 담당 팀원과 통합 경계를 검토했다. [PR #179](https://github.com/3K-PokeClip/PokeClip-mono/pull/179)의 C++ 플러그인 구현과 실측은 jaehwan-space의 작업이다. 아래 수치는 그 팀 검증 기록이며 내가 단독으로 구현·측정했다는 의미가 아니다.

## 출력만 추가하고 영상 인코딩은 공유한다

선택한 구조는 본방 출력의 비디오·오디오 인코더를 참조하고 SRT/MPEG-TS 출력을 추가하는 방식이다. 범용 다중 송출 플러그인의 설정 화면 전체를 가져오는 대신, 출력 생성·인코더 참조·해제 순서를 중심으로 필요한 부분을 이식했다. 방송자가 여러 타깃과 키를 직접 편집하는 UI는 페어링으로 연결하려는 제품 흐름과 맞지 않았다.

| 대안 | 장점 | 남는 문제 |
|---|---|---|
| 영상 인코더를 별도로 실행 | 출력 설정 독립 | 같은 화면을 다시 인코딩해야 함 |
| 범용 다중 송출 플러그인 전체 사용 | 기존 기능을 폭넓게 활용 | 방송자에게 필요 없는 URL·키 편집까지 노출 |
| 본방 인코더 공유 + 필요한 출력 수명만 이식 | 추가 영상 인코더 없이 동시 송출 | 본방 시작·실패·종료와 수명을 맞춰야 함 |

같은 압축 프레임을 재사용한다고 수신 파일이 자동으로 원하는 길이로 잘리는 것은 아니다. 키프레임 간격도 서버의 녹화·재생 계약에 맞아야 했다.

## GOP는 실행 중에 조용히 바꾸지 않는다

계약은 GOP 2초였다. 팀 구현은 OBS가 프로필 인코더 설정을 적용한 뒤, 실제 인코더 생성 전에 발생하는 `STREAMING_STARTING`에서 이를 맞췄다. 이 순서는 OBS 소스 대조를 통해 검토됐다. 이벤트 이름만 보고 안전한 시점이라 가정하지 않은 것이다.

이미 녹화가 본방 인코더를 공유해 인코더가 실행 중이면 상황이 달라진다. 해당 x264 경로는 실행 중 GOP 변경을 받아들이지 않는다. 이때 조용히 다른 규격을 보내기보다 비호환 활성 인코더를 거절하도록 했다. 서버에서 파일 길이의 드리프트를 뒤늦게 발견하는 것보다 입력 경계에서 이유를 알리는 선택이었다.

출력 종료도 같은 문제다. 본방이 실패하거나 정지했을 때, 또는 OBS 자체가 종료될 때 부가 SRT 출력이 남지 않아야 한다. 인코더 참조와 서비스 해제 순서는 [OBS 플러그인 API](https://docs.obsproject.com/plugins)와 실제 버전의 코드에 맞춰 검토할 대상이었다.

## UI와 비밀 전달은 송출 코어 밖으로 나눴다

passphrase는 SRT URL에 섞지 않고 별도 서비스 필드로 전달하도록 했다. URL이 로그에 남더라도 비밀이 같이 남는 경로를 피하려는 판단이다. 독 화면과 플러그인은 루프백 브리지로 연결하고 Host·Origin·토큰·본문 크기를 검사한다. 브라우저 독이 없으면 최소 Qt 패널을 쓸 수 있도록 송출 코어와 UI 책임도 분리했다.

이 구성만으로 모든 비밀 전달이 안전해졌다고 말할 수는 없다. PR의 당시 개발 Auth 주소는 HTTP였고, 로컬 MediaMTX에는 passphrase가 구성되지 않아 실측은 `send_passphrase=false` 조건이었다. 계정별 암호가 켜진 수신 경로와 HTTPS는 별도로 연결하고 검증해야 할 일이었다. 페어링 성공과 암호화된 전체 송출 검증을 같은 완료로 묶지 않는다.

## 로컬에서 확인한 것은 어디까지인가

팀은 macOS OBS 32.2.2, x264 1080p30, 로컬 Compose MediaMTX와 로컬 Auth를 사용했다. 본방 목적지는 실제 치지직 대신 로컬 RTMP 대역이었다.

| 확인 대상 | PR의 관측 |
|---|---|
| 두 출력 | RTMP·SRT 녹화가 함께 생성 |
| 영상 인코더 | x264 인스턴스 1개 |
| 수신 키프레임 간격 | 약 2초 |
| 수신 조각 길이 | 약 4.06~4.07초, 오디오 포함 |
| 종료·재연결 | 미디어 재시작 후 재연결, 본방 실패·정지와 동반 종료, 송출 중 OBS 종료 확인 |

이 결과는 추가 영상 인코더 없이 두 경로가 만들어졌다는 근거다. CPU·GPU 사용량이 몇 퍼센트 줄었다는 측정은 아니며 Windows 실기와 실제 치지직 동시 송출을 통과했다는 뜻도 아니다. 빌드 성공은 그 플랫폼에서 방송을 끝까지 했다는 증거가 되지 않는다.

인코더를 공유하는 결정은 단순히 객체 하나를 재사용하는 일이 아니었다. 시작 전 설정, 진행 중 변경 거부, 본방 실패와 종료의 수명까지 함께 정해야 의미가 있었다. 입력 계약을 고를 때 정상 송출뿐 아니라 “언제 시작하지 말아야 하는가”를 포함하게 된 사례다.
