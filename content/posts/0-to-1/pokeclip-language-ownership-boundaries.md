채팅 수집은 처음에 Node·TypeScript로 가기로 했다. 기존 자산을 재사용할 수 있었고 프론트엔드를 맡은 팀원의 익숙한 언어와도 맞았다. 그런데 담당자가 Spring을 주로 쓰는 인원으로 바뀌었다. 처음의 근거가 사라졌는데도 이미 정했다는 이유로 언어를 유지할 필요가 있을까.

2026년 7월 31일, 채팅 수집을 Spring으로 전환하는 결정을 반영했다. 나는 3인 팀의 전체 역할과 인터페이스를 조율하면서, 누가 변경을 읽고 실패를 검토할 수 있는지를 선택 기준으로 삼았다. Spring 서비스 구현을 내가 모두 작성한 것은 아니다. 팀원은 코어를 구현했고, 나는 미디어·인프라 담당으로 서비스 간 계약과 구조를 함께 검토했다.

## 모든 기능을 한 언어로 맞추면 사라지는 비용과 남는 비용

PokeClip에는 계정·권한·클립 상태를 다루는 요청 처리, 오래 연결된 방송과 파일을 다루는 미디어 작업, OBS 안에서 동작하는 플러그인, 모델 실행과 연결되는 AI 작업이 있다. 언어를 통일하면 빌드와 학습 도구가 줄지만 각 경계의 특성까지 같아지지는 않는다.

| 역할 | 선택한 언어·환경 | 선택 이유 |
|---|---|---|
| 계정·권한·클립 등 코어 API | Spring | 팀의 구현·검토 역량과 생태계 활용 |
| 미디어 파일과 장기 실행 작업 | Go | 동시 작업과 바이너리 처리 경계에 맞춘 자체 계층 |
| OBS 연동 | C++ | libobs와 직접 연결되는 플러그인 경계 |
| 음성·모델 처리 | Python | 모델 실행 도구와의 접점; 설계상의 역할 배정과 구현 완료는 구분 |
| 채팅 수집 | Node·TypeScript 원안 → Spring | 담당 변화 뒤 유지·검토 책임을 다시 맞춤 |

이 표는 언어별 성능 순위가 아니다. 같은 기능을 모든 언어로 구현해 벤치마크한 적도 없다. 코어 API 규모에서 근거 없는 미세 성능 차이를 앞세우기보다 팀이 수정 내용을 이해하고 검증할 수 있는지를 봤다. OBS의 경우에는 [공식 플러그인 개발 문서](https://docs.obsproject.com/plugins)가 설명하는 libobs 연결 자체가 중요한 제약이었다.

## 언어가 달라도 실패의 의미는 같아야 한다

서비스를 나누면 내부 객체를 공유하는 대신 호출 계약이 필요하다. 미디어가 파일을 만들었다고 코어가 곧바로 편집 가능한 상태로 표시해도 되는가. 업로드 재시도 때 같은 대상을 어떻게 알아보는가. 방송이 다시 연결됐을 때 같은 회차인지 새 회차인지 누가 결정하는가.

각 서비스가 제각각 답하면 언어의 장점을 얻기 전에 통합에서 막힌다. 그래서 API·이벤트의 데이터 형태, 식별자, 상태가 바뀌는 시점, 실패 응답과 소유자를 맞췄다. 내부 구현은 서비스가 선택하되 바깥에서 관측하는 의미를 계약으로 고정하는 방향이었다. 전체 연결은 [프로젝트 아키텍처 기록](https://github.com/3K-PokeClip/PokeClip-architecture/blob/d0c104481a50f25ff0f4f11a23a275cb4d12961f/4_Pokeclip_SysA.html)과 함께 읽을 수 있다.

채팅 담당 변화도 같은 원칙으로 판단했다. “처음의 개발자가 TypeScript를 잘한다”는 근거가 유지될 때는 기존 자산 재사용이 유효하다. 맡는 사람이 바뀌었다면 재사용 비용과 이후 변경 검토 비용을 다시 비교해야 한다. 옛 결정을 지키는 것이 항상 일관성 있는 선택은 아니었다.

## 다언어 구조의 비용은 없애지 못했다

서비스별로 언어를 골랐다고 해서 모노레포의 빌드·테스트·배포 규칙이 자동으로 통일되지는 않는다. 변경 경로에 따라 검증할 대상을 나눠야 하고, 서비스 사이에서 관측할 상태와 오류도 맞춰야 한다. 이를 경로 필터와 계약으로 관리하는 방향을 택했지만, 다언어 자체가 개발 속도를 높였다는 정량 성과로 쓰지는 않는다.

반대로 모든 코어를 한 사람이 익숙한 기술에 맞추면 그 사람에게 검토 책임이 몰릴 수 있다. 3인 팀에서 나는 자신이 주로 다루는 미디어 기술을 다른 서비스에도 밀어 넣기보다, 팀원이 책임질 수 있는 선택을 함께 만드는 쪽이 맞다고 판단했다. 구조 설계에 참여했다는 것과 해당 서비스의 구현을 소유한다는 것은 다른 기여다.

## 스택 결정에는 유효한 전제가 필요하다

이 사례에서 확인한 결과는 실행 속도 개선이 아니라 담당 변경에 맞춘 결정의 갱신이다. 2026년 10월 기준으로도 서비스별 설계 배치, 실제 병합된 기능, 통합 진행 상태를 따로 설명한다. 도표에 Python이나 렌더 워커가 있다고 해서 모든 경로의 운영이 완료된 것은 아니다.

다음 스택 결정을 할 때도 먼저 적을 질문은 같다. 누가 구현하고, 누가 검토하고, 문제가 났을 때 어느 계약을 따라 조사할 수 있는가. 그 답이 달라졌다면 언어 선택도 다시 열어야 한다. 채팅을 Spring으로 옮긴 이유는 Spring이 무조건 우수해서가 아니라, 당시 그 책임을 맡을 사람과 검토 경계를 다시 맞추기 위해서였다.
