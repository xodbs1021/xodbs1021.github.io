재생목록 요청은 성공했고 플레이어 오류도 없었습니다. 그런데 141.97초 분량의 목록에서 브라우저가 인식한 구간은 80.03초뿐이었습니다. 60초로 탐색하면 약 87초로 이동했습니다. 오류가 없다는 지표가 사용자가 필요한 장면을 고를 수 있다는 뜻은 아니었습니다.

PokeClip은 방송 중 지난 장면을 되감아 클립의 시작점을 고르는 기능을 만들고 있습니다. 저는 이 문제를 보며 HTTP 상태와 오류 수 외에, 선언 길이·브라우저 버퍼·실제 탐색 위치를 각각 확인하기로 했습니다. 원인 분석과 실험은 AI와 협업했고, 무엇을 재생 성공의 기준으로 둘지와 원본 보존 방향을 제가 선택했습니다.

## 세 개의 시계가 같은 말을 하지 않았습니다

재생목록은 파일을 어떤 순서와 길이로 읽을지 알려 줍니다. 그러나 각 파일 안에도 샘플을 놓을 시각이 있습니다. fMP4의 `tfdt`는 디코딩 시작 시각을 담습니다. 당시 녹화 파일은 독립적으로 재생할 수 있도록 파일마다 상대 시간이 다시 시작했으므로, 목록의 순서대로 늘어놓는 것만으로 하나의 미디어 시간축이 되지 않았습니다.

| 확인한 대상 | 초기 관측 |
|---|---:|
| 재생목록에 선언한 길이 | 141.97초 |
| 브라우저가 인식한 구간 | 80.03초 |
| 두 값의 차이 | 61.94초 |
| 60초 탐색의 실제 이동 | 약 87초 |
| 플레이어 오류 | 0건 |

초기 사례 제목에는 “42%”라는 요약이 남아 있었지만, 현재 글에서는 직접 대조할 수 있는 **141.97−80.03=61.94초**를 사용합니다. 이 두 값을 기준으로 한 누락 비율은 약 43.63%이므로 과거의 비율 표현을 반복하지 않습니다. [현재 정리본](/portfolio/2026-10-15-v2/full.pdf#page=11)도 절대 차이를 기준으로 고쳤습니다.

## 태그를 바꾸는 시도만으로는 충분하지 않았습니다

처음에는 재생목록의 안내를 보완하는 접근을 비교했습니다. 절대 시각을 알려 주는 PROGRAM-DATE-TIME, 초기화 정보를 지정하는 EXT-X-MAP, 연속되지 않는 구간을 알리는 DISCONTINUITY입니다. 각각의 태그가 다루는 문제는 다릅니다. [HLS 규격 RFC 8216](https://datatracker.ietf.org/doc/html/rfc8216)도 이 역할을 별도로 정의합니다.

| 시도 | 보완하려던 것 | 남은 문제 |
|---|---|---|
| PROGRAM-DATE-TIME | 절대 시각과 미디어의 연결 | 파일 내부 상대 시간의 중첩 |
| EXT-X-MAP | 코덱·트랙 초기화 정보 | 조각 간 시간 위치 |
| DISCONTINUITY | 연속성 변화 표시 | 일부 경계의 빈 구간·멈춤 |

절대 시각을 써 넣었다고 파일의 내부 시간값이 자동으로 바뀌지는 않습니다. init을 제공해도 플레이어가 해석할 샘플의 시간 배치가 여전히 겹칠 수 있습니다. DISCONTINUITY는 일부 구간을 살렸지만, 이후에는 경계의 간극과 멈춤을 따로 추적해야 했습니다. “태그를 추가했으니 정상”이라는 결론을 내리기 어려웠습니다.

## 원본과 재생 산출물의 책임을 나눴습니다

이때 선택한 방향은 녹화 원본을 보존하고, S3·CDN에 전달할 재생용 파일에서 트랙과 시간축을 명시적으로 만드는 것이었습니다. 편집용 원본에는 여러 오디오 트랙이 필요하므로 재생 문제를 해결한다고 원본을 덮어쓰면 다른 기능의 재료를 잃습니다.

또 하나의 정정도 필요합니다. 파일마다 상대 시간이 시작하는 MediaMTX의 저장 방식은 의도된 설계입니다. 공식 playback 서버가 있는 경로와 S3에서 파일을 그대로 전달하는 경로는 다릅니다. [MediaMTX playback 문서](https://mediamtx.org/docs/features/playback)가 제공하는 재생 경로를 사용하지 않기로 했다면, 그 경로에서 맡던 시간 재배치 책임을 우리 쪽에서 다뤄야 합니다. 이 관측을 상류 저장 방식의 버그 수정 성과라고 표현하지 않습니다.

## 후속 성공을 초기 입력의 전후 결과로 붙이지 않았습니다

다음 실험은 동일 녹화 파일 10개에서 공통 init과 시간값 변경을 분리한 [단일 변수 대조](/posts/0-to-1/pokeclip-cdn-timeline-normalization/)였습니다. 이후에는 10분·150조각과 재접속 2회로 이어지는 다른 검증도 수행했습니다. 그러나 141.97초 입력, 39.87초 입력, 10분 입력은 서로 다른 데이터입니다. 후속 실험의 오류 0이나 탐색 성공을 초기 입력의 동일 조건 전후 개선처럼 합치지 않습니다.

제가 바꾼 통과 기준은 구체적입니다. 목록 길이가 어떤지, `buffered`가 하나로 이어지는지, 요청한 지점에서 재생이 시작하는지를 각각 봅니다. 오류 로그는 이 중 한 부분만 알려 줍니다. 재생기를 만들 때는 전송이 끝났다는 신호를 넘어서, 사용자가 원하는 시간대를 실제로 다룰 수 있는지까지 검증해야 했습니다.
