화면에서 large 구성을 선택하고 저장했다고 실제 AWS에도 그 구성이 적용됐다고 말할 수 있을까요? Shakedown의 초기 기능에서는 추천·저장과 고정 설정을 쓰는 AWS 실험이 분리돼 있었습니다. 선택 결과가 실행 경계까지 전달되고, 배포 뒤 실제 상태가 일치하는지 확인해야 했습니다.

저는 SoftBank Hackathon에서 이 연결 범위와 통과 조건을 정하고 검증 결과에 따라 변경을 확정했습니다. 초기 AWS 어댑터는 팀원이 만든 기반이며, 제 기여는 ECR·계획 적용 연결과 경계 수정·검증입니다. 구현과 실험 실행에는 AI를 활용했습니다. 변경은 [PR #12](https://github.com/SoftBankHackathon/shakedown/pull/12)에 포함됐습니다.

## 저장된 계획을 다시 검증한 뒤 실행했습니다

클라이언트가 보낸 CPU나 태스크 수를 그대로 실행하면 추천과 실행의 계약을 우회할 수 있습니다. `architecture_plan_id`로 최신 선택인지, 같은 프로젝트와 분석 근거를 가리키는지 다시 확인한 뒤 서버 카탈로그를 적용하도록 연결했습니다. 선택을 저장하는 요청만으로 자원이 생성되는 구조도 아니었습니다. 이 검증은 사전에 준비한 기반 스택을 사용하며, 빈 AWS 계정에서 모든 기반 자원을 자동 구성한 결과는 아닙니다.

실제 배포에서는 계획의 값보다 상태와 시간 예산이 문제였습니다.

| 만난 문제 | 바꾼 부분 | 지킨 조건 |
|---|---|---|
| 준비 전 ALB 403 차단이 ECS 생성 실패로 연결 | 기본 forward 연결 유지, 우선순위 1 규칙에서 403·공개 제어 | 준비 중 차단과 target group 연결을 함께 유지 |
| Spring 기동 약 41초, health 유예 30초 | 유예를 120초로 조정 | 건강 검사를 끄지 않음 |
| 중지 차단은 됐지만 120초 뒤 502 | 어댑터 600초, 외부 엔진 630초로 조정 | 상태 수렴을 기다린 뒤 응답 |

배포 중에는 차단을 유지하고, 실제 healthy 태스크와 AZ를 확인한 뒤 공개했습니다. 수정 뒤 large 중지는 189.70초에 204, INACTIVE, running/pending 0으로 끝났습니다. 앞선 medium의 502는 성공 기록으로 덮지 않았습니다. [실제 배포 보고서](https://github.com/SoftBankHackathon/shakedown/blob/8d9b37b4d388100c093467b1e0fb9a6c9946e39a/docs/experiments/2026-10-09-plan-deployment-connection.md)에 당시 결과가 있습니다.

## 설정값과 실제 상태를 대조했습니다

2026년 10월 9일 검증은 FastAPI TestClient에서 이미지·ECR·AWS로 이어지는 경로였고, `use_ai=false`로 실행했습니다. 브라우저부터 LLM까지 모두 포함한 시험은 아닙니다.

| 항목 | medium | large |
|---|---:|---:|
| 태스크당 CPU | 1 vCPU | 2 vCPU |
| 태스크당 메모리 | 2GiB | 4GiB |
| 정상 태스크 / AZ | 2개 / 2개 | 3개 / 3개 |
| RDS | Single→Multi-AZ | Single→Multi-AZ |
| CPU 60% 확장 범위 | 2–4개 | 3–12개 |
| 세션·쓰기·조회 | 교차 인스턴스 통과 | 세 인스턴스 통과 |

이 표는 카탈로그대로 실제 자원이 설정되고 샘플의 세션·데이터 경로가 동작했는지의 확인입니다. large의 DB도 db.t3.micro였으며, 최대 12태스크나 대표 운영 부하를 시험한 결과는 아닙니다.

## 복구 시간에는 무엇이 포함됐는가

설정이 적용됐다는 확인에서 멈추지 않고, [별도 장애·확장 시험](https://github.com/SoftBankHackathon/shakedown/blob/0147f4774443568becab4421ee1b7c8d86b25513/docs/experiments/2026-10-09-aws-full-stack.md)을 진행했습니다.

| 시험 | 관측 결과 | 읽을 때의 제한 |
|---|---|---|
| large 태스크 강제 종료 | 58.69초 뒤 healthy 3개·3 AZ, 세션·데이터 유지 | 요청부터 관측까지 폴링·API 지연 포함 |
| CPU 자동 확장 | desired/running 2→4, 96.53초에 healthy ≥3, 이후 4개 | 확장 확인이며 축소 검증은 별개 |
| RDS 강제 AZ 전환 | 71.57초 뒤 기존 데이터 조회·같은 세션 추가 쓰기 | 실패 폴링과 healthy 0 구간 존재 |

58.69초와 71.57초는 각 실험에서 복구를 확인한 시간입니다. 정밀 RTO, 무중단, 운영 SLA로 쓰지 않았습니다. 자동 축소도 성공했다고 할 수 없었습니다. 처음 16분 동안 축소는 확인되지 않았고, 추가 관측에서는 정리가 시작돼 유효한 재시험이 아니었습니다.

## 앱 중지는 기반 자원 삭제와 달랐습니다

앱이 중지됐다고 RDS·ALB 등의 기반 스택이 삭제되는 것은 아닙니다. DB 변경의 자동 롤백도 제공하는 결과가 아닙니다. 시간 예산 역시 해당 샘플의 실제 기동·중지 관측을 토대로 정한 값입니다. 최소 IAM이나 전체 브라우저 E2E는 이번 확인 범위 밖에 남겼습니다.

선택 화면에서 실행 결과까지 이어지는 기능에서는 계획 ID, 서버 카탈로그, 실제 자원 상태가 같은 결정을 가리켜야 합니다. 이후의 장애 시험은 그 구성의 일부 복구 경로를 확인해 줬지만, 성공 응답 하나로 이 모든 단계를 대신할 수는 없었습니다.
