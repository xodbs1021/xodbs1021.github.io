PokeClip 미디어 서버는 방송 시작·종료를 다른 서비스에 이벤트로 알립니다. 이 이벤트의 `streamId`는 계약에 뜻이 정해져 있지 않았고, 실제로 들어갈 값은 같은 스트리머의 여러 방송이 함께 쓰는 송출 경로였습니다. 2026년 9월 3일 `streamId`를 방송마다 새로 생기는 세션 id로 정의하기로 했는데, 소비자 쪽 조각 조회가 같은 필드를 녹화 경로로 쓰고 있었습니다. 의미만 바꾸면 정상 요청의 조회가 0행이 됩니다. 그래서 경로는 `ingestStreamId`라는 새 필드에 남기고, 새 필드를 읽는 소비자를 먼저 배포한 뒤 생산자가 새 의미의 `streamId`를 내기로 했습니다. 확인을 요청한 지 1시간 9분 만인 16시 19분에 계약을 확정했습니다.

저는 `streamId`를 방송 단위 좌표로 바꾸자고 정했고, 소비자 영향을 팀원에게 묻고, 팀원의 답을 받아 필드 추가와 배포 순서를 확정했습니다. 계약 문안 초안은 AI(Claude Code)가 썼고, 소비자 조회가 이 필드를 그대로 쓴다는 점은 계약 문서를 리뷰한 AI가 짚었습니다. 계약 문서 리뷰는 AI(Claude Code와 Codex)가 했습니다. 소비자 서비스(Spring)의 구현은 팀원이 맡았습니다. 당시에는 세션을 「방송 회차」라고 불렀습니다. 지금은 시청자가 「방송 한 번」으로 보는 단위를 회차라고 부르고, 세션은 그 안에서 사이드카가 목록 하나를 여닫는 단위로, 송출이 끊겼다 이어지거나 조각이 목록의 목표 길이를 넘거나(TD 분할) init이 바뀌면 새로 열립니다.

## 같은 streamId를 생산자는 세션으로, 소비자는 경로로 읽었습니다 {#송출-경로와-방송-회차는-수명이-다르다}

송출 키와 그 키로 정해지는 인제스트 경로는 계정에 묶여 여러 날 다시 쓰입니다. 반면 월요일 방송과 화요일 방송은 저마다 시작·종료, 녹화 원본, 클립을 갖습니다. 재사용되는 경로를 방송 id로 쓰면 같은 계정의 방송을 서로 구별하지 못합니다.

미디어 서버에는 이미 세션 id(`session_id`)가 있었습니다. 사이드카가 녹화기 훅과 DB 장부로 송출을 여닫을 때 붙이는 id이고, 되감기 목록 주소와 초기화 조각도 이 단위로 나뉩니다. 그래서 이벤트의 `streamId`를 세션 id로 정의하려 했습니다. 생산자에게 `streamId`는 「이 방송」이었고, 소비자에게 `streamId`는 「녹화 조각이 있는 경로」였습니다. 이름과 타입이 같은 필드를 두 쪽이 다른 뜻으로 읽고 있었습니다.

## 의미를 바로 바꾸면 정상 요청의 조회가 0행이 됩니다

소비자는 클립을 만들 때 녹화 조각을 `stream_segments` 표에서 찾습니다. 조건은 이벤트의 `streamId`를 그대로 넣은 경로 값과 시간 범위였습니다. `streamId`에 세션 id를 넣으면 경로 칸에 세션 id가 들어가 일치하는 행이 하나도 없습니다. 장부에 세션 id 칸을 두는 것은 9월 1일 정했지만 아직 배포 전이었고, 배포 뒤에도 그 전에 쌓인 행과 방송 앞부분 조각은 세션 id가 비어(NULL) 있을 수 있었습니다. 소비자가 세션 id로 조회를 바꾼다고 풀리는 문제도 아니었습니다.

이 영향은 바뀐 계약 문서를 리뷰하던 AI가 가장 심각한 지적(CRITICAL)으로 올렸습니다. 생산자 코드는 아직 이 값을 내기 전이었으므로 실제로 0행이 난 적은 없습니다. 바뀐 계약 문구만 먼저 발행돼 있던 상태였습니다.

## 물리 경로는 ingestStreamId로 남기고 소비자를 먼저 배포하기로 했습니다 {#소비자의-답변을-받고-필드와-배포-순서를-함께-바꿨다}

9월 3일 오후의 협의는 영향을 먼저 알리는 데서 시작했습니다.

| 시각 | 한 일 |
|---|---|
| 15:10 | 세션 id로 바꾸면 기존 조각 조회가 깨질 수 있다고 공유하고, 소비자 쪽 대응 방식을 정해 달라고 요청 |
| 16:06 | 팀원 답: 조각 조회는 경로와 시간 범위를 그대로 쓴다. 앞부분 조각과 기존 NULL 행, 배포 순서 때문에 세션 id로 바꾸지 않는다. 이벤트에 경로 필드를 더해 달라 |
| 16:19 | `ingestStreamId` 추가, 소비자 배포를 마친 뒤 새 의미의 `streamId` 발행으로 계약 확정 |

팀원의 답으로 바뀐 것은 이름 하나가 아니었습니다. `streamId`는 방송을 가르고 이벤트를 묶는 데만 쓰고, 조각을 찾는 좌표는 `ingestStreamId`가 맡습니다. `ingestStreamId`는 장부의 경로 칸과 같은 값이라 미디어 쪽 DB에 새 칸을 만들 필요가 없었고, 발행 코드가 필드 하나를 더 채우면 됐습니다. 이 결정은 팀 위키의 계약 문서에 반영했습니다.

배포 순서도 계약의 일부로 적었습니다. 영상의 위 줄은 소비자를 먼저 배포한 경우, 아래 줄은 생산자가 먼저 새 값을 낸 경우입니다. 마지막 칸의 조회 결과를 보면 됩니다.

계약 문서만 맞아도 전환하는 순간 함께 떠 있는 판의 조합이 맞지 않으면 조회는 깨집니다. 그래서 필드 정의와 배포 순서를 한 변경으로 묶었습니다.

## 종료 판정은 생산자 한 곳에서 내리게 했습니다 {#종료-판정도-소비자마다-반복하지-않게-했다}

필드 의미를 나눠도 방송이 언제 끝났는지 서비스마다 따로 판단하면 상태가 어긋납니다. 미디어 경로에서 SRT 연결이 끊기는 것과 녹화기 `runOnOffline` 훅은 종료 사유를 알려 주지 않습니다. 스트리머가 종료를 누른 것과 잠깐 끊긴 것이 미디어 쪽에서는 같아 보입니다. 9월 3일 저녁 종료를 이렇게 정했습니다.

- 방송 송출 플러그인이 보낸 의도적 종료 신호를 받으면 바로 끝냅니다.
- 신호 없이 끊기면 300초를 기다린 뒤 끝냅니다. 300초 안에 돌아오면 같은 방송으로 잇습니다.
- 종료 이벤트는 마지막 녹화 조각의 정산을 마친 뒤 냅니다.

소비자는 미디어 서버가 낸 시작·종료를 상태로 반영하기만 합니다. 이벤트 한 건은 `eventId`로 중복을 거르고, 같은 방송 안의 순서는 `sequence`로 봅니다. 중복 전달이나 역순 도착이 없다는 보장은 아니고, 중복과 순서를 소비자가 판단할 재료를 계약에 넣은 것입니다. 종료가 시작보다 먼저 도착하는 경우의 자리표시 행도 검토 대상에 두었습니다. 이벤트는 SNS FIFO 주제로 내고 서비스마다 SQS FIFO 큐와 DLQ로 받는 구조로 설계했습니다.

의도적 종료 신호 수신부는 10월 29일 [PR #450](https://github.com/3K-PokeClip/PokeClip-mono/pull/450)으로, 시작·종료 이벤트 발행 배선은 10월 30일 [PR #461](https://github.com/3K-PokeClip/PokeClip-mono/pull/461)로 develop에 머지됐습니다. 발행은 주제 주소, 허용 목록, 내부 스트림 키 조회(resolve) 설정을 모두 넣어야 켜지는 기본 꺼짐 상태로 들어갔습니다.

## 그 뒤 세션 위에 사슬과 회차가 생겼습니다

9월 3일에는 세션 하나가 방송 하나라고 봤습니다. 구현이 진행되면서 한 방송이 세션 여럿으로 갈리는 경우가 생겼습니다. 끊긴 송출이 300초 안에 돌아오면 새 세션이 앞 세션을 잇고(계승), 조각 하나가 목록의 목표 길이를 넘거나 코덱 설정이 바뀐 채 돌아와도 새 세션이 열립니다. `streamId`가 세션 id 그대로였다면 한 방송에 `streamId`가 여럿 생길 수 있었습니다.

그래서 미디어 쪽은 세션 위에 두 단위를 더 뒀습니다. 계승으로 이어진 세션 묶음이 사슬이고, 시청자가 「방송 한 번」으로 보는 단위가 회차입니다. 재접속 창 300초를 넘기거나 의도적 종료 신호 뒤 다시 켜면 새 회차입니다. 지금 이벤트의 `streamId`는 회차 id이고, 그 값은 회차 첫 세션의 id입니다([media/README.md 「회차 단위 VOD 용어」](https://github.com/3K-PokeClip/PokeClip-mono/blob/1818c54948395fb0ba80cb37e85770b4d526d853/media/README.md?plain=1#L797-L806)). 시작 이벤트도 새 회차를 열 때만 내고, 계승이나 분할로 같은 회차를 잇는 세션은 내지 않습니다(PR #461). 값의 모양은 여전히 세션 id이지만 뜻은 「방송 한 번」입니다. 9월 3일에 「방송 회차」라고 부르며 노린 뜻이 이렇게 자리 잡았습니다.

| 필드·칸 | 2026년 9월 3일 계약 | 2026년 11월 지금 |
|---|---|---|
| `streamId`(이벤트) | 세션 id(당시 「방송 회차」) | 회차 id = 회차 첫 세션의 id |
| `ingestStreamId`(이벤트) | 인제스트 경로 = 장부 경로 칸 | 그대로 |
| `session_id`(장부) | 세션 = 당시의 방송 회차 | 세션 = 목록 하나의 단위(끊김·TD 분할·init 변경마다 새로) |
| `round_id`(장부) | 없음 | 회차 |
| `eventId` · `sequence`(이벤트) | 중복 식별 · 순서 | `eventId`는 「회차 id.started」·「회차 id.ended」로 정해지는 값, `sequence`는 회차 안 순서 |

그림 2는 지금 이벤트 필드가 장부의 어느 칸을 가리키는지입니다. 청록 경로가 소비자의 조각 조회입니다.

조각 조회 쪽은 9월 3일과 같습니다. 미디어 쪽이 방송 단위를 두 번 고치는 동안 소비자의 조회 좌표는 `ingestStreamId` 하나로 버텼습니다. 포트폴리오 요약(2026-10-15판) 19쪽은 `streamId`를 「방송 회차(session_id)」로 적습니다. 그 판의 「회차」는 지금의 세션이고, 이 표의 왼쪽 열에 해당합니다.

## 필드 의미를 바꿀 때는 소비자의 실제 쿼리부터 보십시오 {#호환성은-생산자의-새-의미만으로-정해지지-않는다}

- 이름과 타입이 같아도 소비자가 그 값을 어느 칸에 넣어 조회하는지는 다를 수 있습니다. 계약 문서보다 소비자 코드의 WHERE 절을 먼저 읽으십시오.
- 의미를 바꾸는 대신 새 필드를 더하면 옛 조회 좌표를 지킬 수 있습니다. 필드가 하나 느는 비용이 이름 하나에 두 뜻을 싣는 비용보다 작았습니다.
- 새 필드를 읽는 쪽을 먼저 배포하고, 새 값을 내는 쪽을 나중에 켜십시오. 이 순서를 계약 문서에 함께 적어 두면 전환하는 순간의 판 조합을 맞출 수 있습니다.
- 기존 데이터에서 새 칸이 비어 있는 행을 세어 보십시오. 이번에는 배포 전 행과 세션 앞부분 조각의 NULL 때문에 소비자가 새 칸으로 옮겨 갈 수 없었습니다.

소비자 배포가 실제로 생산자 발행보다 먼저 끝났는지, 운영에서 이벤트 발행을 켰는지는 확인하지 못했습니다. 확인한 것은 필드 의미·종료 판정·전환 순서의 합의와 생산자 쪽 구현까지입니다.
