방송자는 웹에서 이미 로그인했는데 OBS에서도 다시 로그인해야 할까. 플러그인에 OAuth를 넣으려면 C++ 쪽에서 브라우저를 열고 콜백을 받고 토큰을 갱신하는 흐름을 추가해야 했다. 반대로 SRT URL과 비밀을 통째로 복사하게 하면 입력은 간단해도 화면 공유나 로그에 비밀이 남을 수 있었다.

나는 웹의 기존 로그인 상태를 이용해 짧은 일회용 코드로 OBS를 연결하는 흐름을 선택했다. 목표는 매 방송마다 설정을 반복하지 않는 것이었다. 온보딩 때 코드 한 번을 입력하는 것과 매 방송 반복 설정 0회는 서로 다른 요구이므로, 연결 과정을 한 번에 한정하는 선택이 가능했다.

## 코드가 로그인과 장기 비밀 사이를 잇는다

로그인한 방송자가 웹에서 코드를 발급받아 OBS에 입력한다. 플러그인은 그 코드를 Auth에 교환해 자기 계정의 송출 설정을 받는다. 짧은 코드는 곧 만료되거나 사용 처리되고, 실제 송출에 쓰는 자격증명과 별개의 수명으로 관리한다.

| 대안 | 선택할 때 늘어나는 책임 | 판단 |
|---|---|---|
| OBS에서 OAuth 전체 구현 | 브라우저·콜백·토큰 갱신 | 당시 구현 범위에 비해 큼 |
| SRT URL 한 줄 복사 | URL에 섞인 비밀의 노출 경로 | 기각 |
| 웹 로그인 + 일회용 코드 | 발급·교환·만료·시도 제한 | 기존 인증을 활용하는 경계로 채택 |

이것을 표준 OAuth Device Flow를 그대로 구현한 사례라고 부르지는 않는다. PokeClip의 기존 웹 계정과 플러그인을 연결하기 위해 정한 자체 페어링 계약이다. 코드의 생김새가 비슷하다고 다른 프로토콜의 보안 성질을 자동으로 가져오는 것은 아니다.

## 8자만으로 안전하다고 판단하지 않았다

코드는 Crockford Base32 8자를 `XXXX-XXXX`로 표시하고 10분 뒤 만료하도록 정했다. 성공한 코드는 다시 교환할 수 없다. 발급 계정에 묶여야 하며, 짧은 코드의 추측 위험을 줄이기 위해 시도 제한도 함께 둔다.

| 계약 | 정한 값 또는 경계 |
|---|---|
| 형식·수명 | 8자, 10분 |
| 재사용 | 한 번 교환한 코드는 거부 |
| 발급 제한 | 계정당 분당 3회 |
| 교환 제한 | IP당 분당 5회 |
| 계정 바인딩 | 발급한 계정의 자격증명만 반환 |

길이·만료·시도 제한 중 하나만 보고 안전하다고 할 수는 없다. 프록시 뒤에서 실제 요청자 IP를 구분하지 못하면 의도한 IP별 제한이 전체 요청의 공용 제한이 될 수 있다. 또 시도 기록을 제한 창보다 빨리 지우면 제한의 근거 자체가 사라진다. 최신 계약에는 신뢰할 프록시와 전달 헤더 설정, 기록 보존 조건을 함께 다루도록 보강했다. 실패 누적에 따른 추가 차단은 구현된 기능으로 쓰지 않는다.

## 성공한 코드의 행을 즉시 지우지 않은 이유

일회용이라는 말은 성공 직후 같은 코드를 허용하지 않는다는 뜻이지, DB 행을 그 순간 반드시 지운다는 뜻은 아니다. 사용 기록이 남아야 “이미 사용했다”는 응답을 줄 수 있다. 최신 계약에서는 만료 뒤 1시간 보존하고 10분 간격으로 정리하는 기준이 있다. 정리 후에는 이전 사유를 구분할 기록이 없어질 수 있지만 코드가 다시 유효해지는 것은 아니다.

이 차이는 사용자 경험과 운영 기록을 함께 설명한다. 사용된 코드를 다시 넣었을 때 재사용 거부와 존재하지 않는 코드가 같은 보안 결과를 낼 수는 있어도, 사용자에게 안내할 이유는 달라진다. 저장 기간은 단순 용량 설정이 아니라 어떤 실패 이유를 얼마 동안 설명할 수 있는지와 연결된다.

## 팀 구현에서 확인한 경계와 남은 경계

실제 연동 근거는 [OBS 팀 PR #179](https://github.com/3K-PokeClip/PokeClip-mono/pull/179)에 있다. 웹에서 발급한 코드의 교환 성공, 같은 코드 재사용 시 **409**, macOS 설정 파일의 **0600** 권한을 확인한 기록이다. 플러그인 구현과 실측은 팀원이 담당했으며, 나는 연결 흐름과 서버 입력·응답 계약을 조율했다.

passphrase는 전체 SRT URL 대신 별도 연결 필드로 넘기게 했다. 식별자인 streamid에는 사용자명·이메일을 넣지 않는다. [SRT 옵션 문서](https://github.com/Haivision/srt/blob/master/docs/API/API-socket-options.md)는 streamid와 passphrase가 서로 다른 옵션임을 설명하며, 실제 플러그인 전달 방식은 PR의 근거로 확인한다.

당시 개발 Auth 경로는 HTTP였고 로컬 송출 실험은 passphrase가 꺼진 조건이었다. 따라서 페어링 성공을 HTTPS와 계정별 암호가 연결된 전체 송출의 완료로 확대하지 않는다. 서버 수신 경로와 전송 보호는 별도의 구현·검증 조건이다.

## 한 번의 입력을 위해 서버 쪽 계약은 더 분명해야 했다

방송자의 반복 설정을 줄이는 대신 코드의 만료, 재사용, 계정 귀속, 제한과 보존을 서버가 책임져야 했다. 짧은 코드라는 UI만으로 단순한 인증이 되는 것은 아니었다. 플러그인에 OAuth 전체를 다시 넣지 않는 선택이 성립하려면, 그 사이를 연결하는 교환 계약을 작고 분명하게 만들어야 한다.
