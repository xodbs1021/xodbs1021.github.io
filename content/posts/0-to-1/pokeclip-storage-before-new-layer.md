클립을 만들 때 필요한 것은 선택한 시간대와 겹치는 원본 파일 몇 개입니다. 저장소 기술을 더 붙이면 빨라질 것 같지만, 먼저 현재 작업이 무엇인지 확인해야 했습니다. PokeClip은 이미 약 4초짜리 독립 객체와 시간 인덱스를 가지고 있었습니다. 큰 파일 한 개의 일부 바이트만 읽는 문제와는 출발점이 달랐습니다.

저는 별도 KV·FUSE·라이브 저장 계층을 추가하기보다 현재 객체 단위와 제한된 병렬 다운로드를 유지하기로 했습니다. 조사와 실험은 AI와 협업했고, 초기 조사의 잘못된 전제를 다시 검토하도록 요구했습니다. 이 글의 수치는 도입을 보류한 판단에 사용한 근거이지, 완성된 렌더 서비스의 처리량 성과는 아닙니다.

## 기술의 해법보다 입력 단위를 먼저 비교했습니다

큰 파일의 부분 읽기 방식은 바이트 위치를 찾는 인덱스가 필요합니다. 우리는 이미 시간별 파일을 갖고 있으므로, 예를 들어 12초 구간에 겹치는 몇 개 객체를 찾으면 됩니다. 새 저장 계층을 넣으면 인덱스와 실패 복구도 하나 더 운영해야 합니다.

| 비교 대상 | 우리 요구에 대입한 질문 |
|---|---|
| S3 키 분산 | 이미 방송·시간으로 나뉜 키에 추가 분산이 필요한가 |
| 별도 라이브 저장 서버 | 원본 가용성·복구 책임을 더 맡을 이득이 있는가 |
| 큰 파일 부분 읽기·FUSE | 작은 독립 객체를 가진 현재 구조에도 맞는가 |
| 제한된 병렬 GET | 현 인덱스와 객체를 유지하며 기다림을 줄일 수 있는가 |

처음 조사에는 빠진 것이 있었습니다. DVR은 사용자마다 다른 객체를 탐색할 수 있고, 렌더·AI 작업은 직접 GET합니다. “S3 쓰기는 비핵심”이라는 설명도 원본 가용성과 복구 영향을 놓쳤습니다. 이 전제를 고친 뒤 도입 여부뿐 아니라 조회 계약, 다운로드 동시성, pending age를 다시 봤습니다. 재검토 중 발견한 첫 조각 누락은 [구간 조회 계약 정정](/posts/0-to-1/pokeclip-segment-overlap-contract/)으로 이어졌습니다.

## PUT 수십 ms가 무엇을 설명하는지 제한했습니다

2026년 8월 30–31일의 개발 EC2 t3.small 원시 기록을 재집계했습니다. 두 크기의 객체를 각각 30회 순차 PUT했고 회차별 다른 키를 사용했습니다. 단일 curl 호출에서 연결을 재사용했으며, 첫 요청과 이후 29건을 나눴습니다.

| 객체 크기 | 첫 요청 | 이후 29회 p50 | 이후 29회 p95 |
|---|---:|---:|---:|
| 1,206,272B | 71.62ms | 40.52ms | 49.02ms |
| 849,920B | 61.43ms | 36.07ms | 39.82ms |

총 **60회 모두 HTTP 200**이었습니다. 비교한 값은 curl `time_total`이며 p95는 29표본의 nearest-rank 값입니다. 중간 응답 시점 차이의 원인이 확인되지 않아 TTFB를 비교 지표로 쓰지 않았습니다. 개별 p95를 더해서 종단 p95라고 부르지도 않았습니다. [PUT 결과와 해석](/portfolio/2026-10-15-v2/full.pdf#page=24)은 이 입력·순차 조건에서 저장 구간이 수십 ms였다는 정도를 말합니다. 파일 마감, 훅, 재포장, DB 확정은 별도로 봐야 합니다.

## 객체 하나보다 배치 전체가 끝나는 시간이 필요했습니다

2026년 10월 6일에는 실제 S3 GET으로 8개 객체를 모두 수신하고 SHA256까지 확인하는 시간을 비교했습니다. 서울 리전의 Python 3.13 ARM64 Lambda, 512MB, 연결 풀 16, 최대 시도 1, 256KiB 읽기 조건입니다. 1·2·4·8 동시성을 조건별 7회씩 무작위 순서로 실행했습니다.

| 파일 8개 배치의 중앙값 | 순차 | 2병렬 | 4병렬 | 8병렬 |
|---|---:|---:|---:|---:|
| 1MiB × 8 | 246.2ms | 154.4ms | 136.1ms | 130.5ms |
| 4MiB × 8 | 411ms | 372ms | 391ms | 359ms |

1MiB 배치는 약 **47%**, 4MiB 배치는 약 **13%** 짧아졌습니다. 4MiB에서 2병렬이 4병렬보다 짧았던 결과도 남겼습니다. AWS의 [S3 성능 지침](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-guidelines.html)은 동시 연결 등 여러 접근을 다루지만, 그것만으로 우리 워커의 최적 상한이 정해지지는 않습니다. 파일 크기와 자원 조건으로 검증해야 합니다.

8병렬 한 배치로 예열했고, 예열을 포함한 Lambda **456객체**의 크기·해시가 일치했습니다. 같은 코드의 로컬 Mac 1MiB 배치는 동시성 1·2·4·8에서 **884.9 / 437.9 / 312.6 / 257.0ms**였습니다. Mac은 예열 포함 232객체를 확인했고 SDK 재시도는 0이었습니다. 코드가 같아도 네트워크·CPU·Python·SDK 조건이 달라 Lambda와 합쳐 개선 배수를 만들지 않았습니다.

## 도입 보류도 검증 조건이 있어야 합니다

새 계층을 추가하지 않는 선택은 S3가 언제나 충분하다는 결론이 아닙니다. PUT은 짧은 순차 버스트이고, GET은 임시 Python 다운로드 실험입니다. 실제 렌더 워커의 파일 크기 분포·메모리·동시 작업 수가 달라지면 상한을 다시 정해야 합니다. 재사용 프로세스의 누적 RSS 최고값을 동시성별 메모리 차이로 해석하지 않은 이유도 같습니다.

[배치 실험 상세](/portfolio/2026-10-15-v2/full.pdf#page=25)를 통해 저는 “새 저장소가 필요한가”라는 큰 질문을 파일 가용 시점, 요청 범위, 배치 완료, 동시성 상한으로 쪼갰습니다. 지금 필요한 복잡도부터 선택하려면 유명한 저장 기법의 이름보다 우리 입력과 실패 단위를 먼저 고정해야 했습니다.
