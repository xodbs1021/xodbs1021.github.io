편집자는 원본의 오디오 6개가 필요하지만, 되감기 플레이어에는 대표 오디오 1개를 가진 재생 파일이 필요합니다. 원본을 직접 고치면 편집 가능성을 잃습니다. 반대로 변환 함수만 만들면 init이 저장되지 않거나 재생 조각 업로드가 실패한 상태를 놓치기 쉽습니다.

저는 재생용 바이트를 만드는 Producer와 DB·저장소의 상태를 확정하는 경로를 분리하기로 했습니다. 구현과 검증은 AI와 협업했고, 책임 경계와 실패 분류를 제가 정했습니다. 이 생산 계층은 2026년 9월 24일 [PR #192](https://github.com/3K-PokeClip/PokeClip-mono/pull/192)로 병합됐습니다.

## 변환 함수가 파일 저장까지 알 필요는 없었습니다

Producer는 입력 핸들과 방송 내 위치를 받아 init, 미디어 조각, init 해시를 반환합니다. init은 플레이어가 트랙과 코덱 설정을 이해하는 초기화 정보입니다. 파일 쓰기나 자식 프로세스 실행, DB·S3 접근은 이 부품 밖에 뒀습니다. [Producer 코드](https://github.com/3K-PokeClip/PokeClip-mono/blob/79da7f670474249fe94c78c89d36e02facc7277d/media/internal/playback/producer.go)는 재포장 방식이 바뀌는 경계만 인터페이스로 유지합니다.

이렇게 나누면 “변환이 결정적으로 실패한 입력”과 “바이트는 만들어졌지만 잠깐 업로드하지 못한 상태”를 다르게 처리할 수 있습니다. 잘린 입력, 필요한 트랙 누락, 빈 트랙, 크기 초과를 무작정 재시도해도 해결되지는 않습니다. 반면 일시적인 PUT 실패 때문에 원본 변환의 의미까지 바꿀 필요는 없습니다.

| 축 | 확정하는 것 | 복구 기준 |
|---|---|---|
| 편집용 원본 | 원본 객체 업로드 | 원본 상태 |
| 되감기 조각 | 재생용 객체 업로드 | 독립 CAS·수거 커서 |
| init | 해시와 업로드 완료 | init 확정 뒤 대기 조각 해제 |

원본 성공으로 재생 실패를 덮지 않는 것이 핵심입니다. 실제 시간 위치는 mtxi와 회차 보정값으로 정하며, 기존 회차의 init과 달라지면 실패를 확정하고 회차 종료 방향으로 전이시킵니다. 같은 방송에 호환되지 않는 init을 몰래 섞지 않기 위해서입니다.

## 실제 입력부터 저장소까지 이어 본 결과

2026년 9월 23일 Docker의 MediaMTX → sidecar → HTTPS MinIO 경로에서 RTMP 입력을 흘렸습니다. 재생 객체 24개와 init 1개가 모두 첫 시도에 업로드됐습니다. 두 번째 송출의 seq 12–23에서는 원본 12개와 재생용 12개의 완료 로그를 짝지었습니다.

| 관측 | 결과 |
|---|---:|
| 재생용 PUT 중앙값 / 최대 | 12ms / 14ms |
| 원본 완료 → 재생 완료 로그 간격 중앙값 / 최대 | 22.65ms / 29.72ms |
| 두 번째 송출 원본 / 재생용 | 12개 / 12개, 모두 첫 시도 |

[생산·저장 검증](/portfolio/2026-10-15-v2/full.pdf#page=16)의 두 시간은 같은 의미가 아닙니다. PUT 시간은 업로더가 기록한 소요이고, 완료 로그 간격에는 작업 전환·재포장·업로드가 포함될 수 있습니다. 순수 재포장 CPU 시간이나 입력부터 시청까지의 종단 지연으로 쓰지 않습니다. 이 환경은 AWS S3 성능 측정도 아닙니다.

hls.js 1.5.15에서 오류 0, 단일 버퍼, 탐색과 재생 진행을 확인한 기록이 있지만, 같은 109행 실행 로그에는 `negative_drift −1,980ms` 오류 1건도 남았습니다. 저장 성공이 시간축의 모든 문제 해결을 뜻하지 않기 때문에 불리한 결과를 함께 남겼습니다.

## 거절할 입력은 읽기 전에 거절하는가

전체 입력을 메모리에 읽는 구조에는 16MiB 상한을 뒀습니다. 2026년 10월 6일에는 실제 녹화 파일에 유효한 free box를 넣어 미디어 내용을 바꾸지 않고 정확한 경계를 만들었습니다.

| 입력 크기 | 결과 | 실제 읽기·산출 |
|---|---|---|
| 16,777,216B, 16MiB | 성공 | 16MiB 읽음, 산출물 생성 |
| 16,777,217B, 16MiB+1B | ErrInputTooLarge | Read 0회, 산출물 0 |

조건당 1회인 경계 검사입니다. 크기가 알려진 초과 입력을 읽기 전에 막는다는 근거이지, 모든 악성 MP4나 무한 스트림을 검증한 결과는 아닙니다. 단위·race·PostgreSQL 통합·골든·결함 주입 검증과도 역할이 다릅니다.

## 빠른 부품도 동시에 많이 돌리면 비싸집니다

별도의 동시성 시험은 패딩한 경계 파일 대신 실제 녹화 입력 3종을 사용했습니다. Apple M5, Go 1.26.5, GOMAXPROCS=4에서 동시성 1·2·4·8, 독립 프로세스 각 5회, 프로세스당 800회로 **48,000회**를 처리했고 출력 SHA256이 모두 일치했습니다.

6.78MB 입력에서 최대 RSS 중앙값은 동시성별 **85·107·172·303MiB**, 호출 p95 중앙값은 **5.83·10.57·11.15·45.21ms**였습니다. 4→8 작업의 처리량은 약 293→294회/초로 비슷했습니다. 디스크와 S3를 제외한 부품 시험에서도 작업 수를 무한히 늘릴 근거는 없었습니다. [동시성과 입력 상한 결과](/portfolio/2026-10-15-v2/full.pdf#page=14)를 따로 둔 이유입니다.

원본에 재생 객체와 회차별 init이 추가되므로 PUT과 저장량은 늘어납니다. 보정값의 재기동 복구와 일부 init 잔량 처리는 남은 한계입니다. Producer의 경계를 정한 덕분에 생성, 저장, 복구, 재생을 각자 확인할 수 있었지만, 재생목록 렌더와 발행까지 이 PR 하나로 완성되지는 않았습니다.
