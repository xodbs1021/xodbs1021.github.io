클립에서 배경음악을 빼려면 소리를 가능한 한 잘게 나눠 받아야 할 것 같았습니다. 처음에는 약 10개 소스를 직접 추적하는 방식을 검토했습니다. 그런데 이 방식에서는 플러그인이 소스의 생성·종료와 프로세스를 추적하고, 소리가 없는 동안에도 출력을 진행시켜야 했습니다. 음악을 제외하려던 기능이 별도의 오디오 엔진을 유지하는 일로 커졌습니다.

그래서 편집할 때 필요한 소리 조합부터 다시 정리했습니다. **본방 믹스와 게임·마이크·대화·음악·기타를 OBS 네이티브 6트랙으로 표현하면** 핵심 요구를 만족시킬 수 있었습니다. 저는 이 입력 계약과 구현 범위를 선택했고, 이후 플러그인 구현과 OBS 실측은 팀원이 맡았습니다.

## 최대 소스 수보다 편집에 남길 재료가 중요했습니다

필요한 것은 모든 프로세스의 소리를 독립적으로 다루는 범용 기능이 아니었습니다. 본방의 완성된 믹스는 남기고, 편집할 때 음악을 제외하거나 필요한 소리를 선택할 수 있어야 했습니다. [OBS 다중 오디오 트랙 가이드](https://obsproject.com/kb/multiple-audio-track-recording-guide)도 일반 재생용 믹스와 후편집용 분리 트랙을 함께 두는 구성을 설명합니다.

| 선택지 | 직접 유지할 것 | 판단 |
|---|---|---|
| 약 10개 소스를 직접 추적하는 믹서 우회 | 소스 수명·분류·무음 처리 | 핵심 편집 요구에 비해 구현 범위가 큼 |
| OBS의 6개 트랙 사용 | 기존 믹서 위의 배정과 송출 계약 | 필요한 조합을 표현할 수 있어 채택 |
| 본방 믹스만 저장 | 단순한 입력·재생 | 음악만 제외할 재료가 사라져 기각 |

고정 6트랙은 임의의 모든 소스를 독립적으로 편집하는 자유도를 포기하는 선택입니다. 대신 소리를 직접 캡처하는 엔진을 새로 유지하지 않고, OBS 믹서 위에서 편집에 필요한 정보를 보존할 수 있었습니다. 개발 시간 절감률을 측정한 것은 아니지만, 직접 책임질 기능이 무엇인지 구체적으로 줄였습니다.

## 트랙 이름을 늘리는 대신 순서를 고정했습니다

서버 입력은 `audio1`부터 `audio6`까지로 고정했습니다. 첫 오디오에는 본방 믹스를 두고 나머지는 편집 재료로 사용합니다. 되감기 시청용 파일은 첫 오디오로 단순화하되, 편집 원본에는 6개를 모두 남기는 방식입니다.

방송 중 소스 이름을 전달하려던 `trackManifest`와 라벨 API도 후속 결정에서 폐기했습니다. 소스 이름이 바뀔 때마다 서버 메타데이터와 실제 파일의 대응을 갱신하기보다 고정된 순서로 전달하는 계약을 먼저 보장하기로 했습니다. 다만 첫 번째 칸에 무엇이 들어가는지는 이름만으로 보장되지 않으므로, 본방 믹서와 첫 오디오의 대응은 별도로 검사해야 했습니다.

범위를 줄여도 플러그인은 필요했습니다. 본방과 SRT를 함께 보내고, 페어링 코드로 계정을 연결하고, 자동 배정이 사용자의 설정을 망가뜨리지 않게 해야 합니다. 동시 송출은 [팀 PR #179](https://github.com/3K-PokeClip/PokeClip-mono/pull/179), 자동 배정은 [팀 PR #195](https://github.com/3K-PokeClip/PokeClip-mono/pull/195)로 이어졌습니다. 없앤 것은 플러그인 전체가 아니라 별도 캡처 엔진의 책임이었습니다.

## OBS 설정의 6트랙이 파일에서도 6트랙인지 확인했습니다

2026년 8월 스파이크에서는 SRT 입력부터 fMP4 녹화, HLS 대체 오디오 목록, 선택 추출까지 연결했습니다.

| 확인 위치 | 관측한 결과 |
|---|---|
| fMP4 녹화 | 오디오 6개 보존 |
| LL-HLS 목록 | `EXT-X-MEDIA` 6개 |
| 선택 추출 | 여섯 번째 오디오 선택 뒤 출력 오디오 1개 |
| 파일·색인 대응 | 녹화 61파일과 DB 61행 일치 |

**6개를 보냈다는 설정과 6개가 남았다는 결과를 대조한 것**입니다. 초기 입력은 무음 씬이므로 이 결과는 트랙의 존재·순서·전달과 선택 추출까지 증명합니다. 실제 음악 제거의 청감 품질은 확인하지 않았습니다. 후속 팀 실험에서는 테스트 톤으로 소리 내용도 대조했으며, [멀티오디오 검증 글](/posts/0-to-1/pokeclip-multiaudio-end-to-end-verification/)에서 두 실험을 나눠 설명합니다.

이 방식에도 사용자 설정을 바꾸는 위험은 남습니다. 본방·VOD의 기존 체크를 건드릴 수 있으므로 자동 배정은 기본 꺼짐과 복원 가능한 설정이 필요했습니다. 트랙 수를 줄인 만큼 사용자를 대신해 결정한 기본값을 더 꼼꼼히 확인해야 했습니다.

결국 입력 설계의 질문은 “소스를 몇 개까지 받을 수 있는가”에서 “나중에 바꿀 소리 조합을 잃지 않는가”로 바뀌었습니다. 이 요구를 6트랙으로 표현할 수 있었기 때문에, 별도 오디오 엔진을 만드는 대신 전달과 복원 검증에 집중할 수 있었습니다.
