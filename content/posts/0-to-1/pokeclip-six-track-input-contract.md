클립에서 배경음악을 빼려면 소리를 가능한 한 잘게 나눠 받아야 할 것 같았다. 처음에는 약 10개 소스를 직접 추적하는 방식을 검토했다. 그런데 이 선택을 따라가면 플러그인이 소스의 생성·종료를 알아야 하고, 프로세스를 추적하고, 소리가 없는 동안에도 출력이 진행되게 만들어야 했다. 음악 하나를 제외하려던 요구가 별도의 오디오 엔진을 만드는 일로 커지고 있었다.

나는 편집에 필요한 소리 종류를 다시 정리해 본방 믹스와 게임·마이크·대화·음악·기타를 OBS 네이티브 6트랙으로 표현하기로 했다. 미디어 입력 계약과 범위 선택이 내 기여이고, 이후 플러그인의 실제 구현과 OBS 실측은 팀원이 맡았다. 구현 책임을 줄인 과정 자체가 이 사례의 핵심이다.

## 트랙 수가 아니라 사용자가 바꿀 조합을 세었다

사용자가 원하는 것은 모든 프로세스의 소리를 끝없이 따로 보관하는 기능이 아니었다. 본방의 완성된 소리는 그대로 남기되, 편집할 때 배경음악을 제외하거나 필요한 소리를 고를 수 있으면 됐다. [OBS의 다중 오디오 트랙 가이드](https://obsproject.com/kb/multiple-audio-track-recording-guide)도 전체 믹스와 편집용 분리 트랙을 함께 두는 구성을 설명한다.

| 선택지 | 책임 범위 | 당시 판단 |
|---|---|---|
| 약 10개 소스를 직접 추적하는 믹서 우회 | 소스 수명·분류·무음 처리까지 플러그인이 유지 | 핵심 편집 요구에 비해 구현 범위가 큼 |
| OBS의 6개 트랙 사용 | OBS의 믹서 위에서 배정과 송출 계약 관리 | 필요한 조합을 표현할 수 있어 채택 |
| 본방 믹스만 저장 | 입력과 재생은 단순 | 뒤에서 음악만 제외할 재료가 사라져 기각 |

트랙을 줄이는 것은 기능을 아무렇게나 생략하는 일과 달랐다. “음악을 뺀 조합을 만들 수 있는가”를 기준으로 남길 정보를 정했다. 최대 소스 수의 자유도는 줄지만, 송출과 서버 양쪽이 직접 유지할 예외도 줄어든다. 이 과정에서 개발 시간이 몇 시간 줄었다는 측정값은 만들지 않았다.

## 첫 오디오는 본방, 나머지는 편집 재료

서버에서 받는 트랙 이름은 `audio1`부터 `audio6`까지 고정했다. 첫 오디오는 본방 믹스를 보존하고, 나머지는 편집할 때 선택할 재료로 쓰는 계약이다. 되감기 시청용 파일은 첫 오디오를 사용해 단순화하고, 편집 원본에는 6개를 남긴다.

방송 중 바뀌는 소스 이름을 서버가 신뢰할 수 있는 의미로 다루려던 `trackManifest`와 라벨 API도 후속 결정에서 폐기했다. 소스 이름이 바뀔 때마다 서버 메타데이터와 실제 파일의 관계를 다시 맞추기보다, 순서가 고정된 입력을 먼저 보장하기로 했다. 이름이 없다고 의미가 저절로 맞는 것은 아니므로, 본방 믹서와 첫 오디오의 대응은 별도로 확인해야 했다.

이 계약은 플러그인이 필요 없다는 결론도 아니었다. 본방과 함께 SRT를 송출하고, 페어링 코드로 계정을 연결하고, 사용자의 설정을 보호하는 기능은 여전히 필요하다. 제거한 것은 소리를 직접 캡처하는 별도 엔진의 책임이었다. 동시 송출은 [팀 PR #179](https://github.com/3K-PokeClip/PokeClip-mono/pull/179), 자동 배정은 [팀 PR #195](https://github.com/3K-PokeClip/PokeClip-mono/pull/195)로 이어졌다.

## 계약이 파일까지 도착하는지 확인했다

“OBS가 6트랙을 지원한다”는 사실만으로 서버와 편집까지 동작한다고 볼 수는 없었다. 2026년 8월의 스파이크에서는 SRT 입력, fMP4 녹화, HLS의 대체 오디오 목록, 선택 추출을 연결해 확인했다.

| 확인 위치 | 관측한 결과 |
|---|---|
| fMP4 녹화 | 오디오 6개 보존 |
| LL-HLS 목록 | `EXT-X-MEDIA` 6개 |
| 선택 추출 | 여섯 번째 오디오 선택 후 출력 오디오 1개 |
| 파일·색인 대응 | 녹화 61파일과 DB 61행 일치 |

초기 입력은 무음 씬이었다. 따라서 이 결과가 증명하는 것은 트랙의 존재·순서·전달과 선택 추출이다. 실제 음악을 듣고 제거 품질까지 평가했다는 뜻은 아니다. 후속 팀 실험은 테스트 톤으로 소리 내용도 확인했으며, 그 구분은 [멀티오디오 검증 글](/posts/0-to-1/pokeclip-multiaudio-end-to-end-verification/)에 따로 적었다.

## 적은 트랙이 더 명확한 계약을 만들었다

고정 6트랙은 모든 방송자의 임의 구성을 표현하는 범용 오디오 시스템이 아니다. 기존 본방·VOD 설정을 건드릴 위험도 남아 자동 배정은 기본 꺼짐과 복원 가능한 설정으로 설계해야 했다. 적게 만든다고 사용자 설정의 책임까지 없어지지는 않는다.

그럼에도 선택을 바꿀 수 있었던 이유는 제품 요구를 다시 확인했기 때문이다. 가능한 많은 소스를 다루는 구현보다, 원하는 소리가 원본에 남고 이후 편집에서 선택 가능한 입력을 먼저 만들기로 했다. 새 기능을 붙일 때도 트랙 개수부터 늘리기보다 지금 계약으로 표현하지 못하는 편집 요구가 무엇인지 확인하려 한다.
