업로드 복구 실험이 실패했는데, 실제 녹화 파일에는 문제가 없었습니다. 공용 개발 DB에 통합 테스트가 만든 가짜 실패 행 **1,121개**가 남아 있었고, 제품의 스위퍼가 존재하지 않는 파일을 계속 처리하려 했습니다. 테스트의 잔여 데이터가 서비스의 실패처럼 보인 상황이었습니다.

저는 종료 때 행을 더 잘 지우는 방식보다 **테스트가 어디에 쓸 수 있는지**를 먼저 바꾸기로 했습니다. 테스트 전용 DB를 강제하고, 정리 대상이 정말 테스트 소유인지 확인하도록 결정했습니다. 구체적인 구현과 반례 검증은 AI와 협업했으며 변경은 [PR #61](https://github.com/3K-PokeClip/PokeClip-mono/pull/61)로 병합됐습니다.

## 연결을 닫는 것과 데이터를 지우는 것은 달랐습니다

기존 테스트는 종료할 때 DB 연결을 닫았지만, 생성한 상태 행은 남겼습니다. 테스트를 정상 종료할 때마다 지우도록 바꾸면 평상시에는 깨끗해 보일 수 있습니다. 그러나 강제 종료나 정리 실패가 발생하면 같은 오염이 다시 생깁니다. 기동 시 청소를 추가하는 방법도 문제가 있습니다. 공용 DB의 행 중 무엇이 가짜인지 구분해 삭제해야 하기 때문입니다.

| 후보 | 해결하는 부분 | 남는 문제 |
|---|---|---|
| 종료 시 자기 행 삭제 | 정상 종료의 잔여 데이터 | 강제 종료 시 오염 재발 |
| 공용 DB 기동 시 청소 | 과거 잔여 데이터 회수 | 실제 개발 데이터와 구분해야 함 |
| 전용 DB와 소유 표식 | 쓰기·정리 대상 자체를 분리 | 생성 권한과 이행 절차 필요 |

리포지터리에는 업로드 테스트의 전용 DB 패턴이 이미 있었습니다. store와 upload의 부트스트랩을 한 곳으로 모으고, `PG_TEST_DB`로 지정한 대상에만 쓰도록 통일했습니다. 하나의 테스트만 고치고 다른 진입점을 남기면 공용 DB로 쓰는 경로가 계속 열려 있기 때문입니다.

## 테이블 모양으로 소유자를 추측했다가 틀렸습니다

초기 판정은 테이블 개수를 보고 “테스트 DB처럼 보이는가”를 확인하는 방식이었습니다. 이 조건은 업무 DB가 우연히 같은 구조를 가지는 순간 무너집니다. 실제로 미끼 DB의 데이터가 삭제되는 반례가 확인됐습니다. 스키마 모양은 사용 목적을 증명하지 못했습니다.

수정한 기준은 `pokeclip_testdb_marker`라는 빈 마커 테이블입니다. **새 DB를 생성한 때에만** 표식을 만듭니다. 이미 존재하는 DB에 표식이 없으면 사용과 정리를 모두 거부합니다. 기존 DB에 먼저 마커를 넣고 “이제 내 것”이라고 판단하면 보호 장치가 아무 의미가 없어집니다. 이 구분이 변경의 핵심입니다.

| 입력·상태 | 부트스트랩의 결정 |
|---|---|
| 공용 DB와 테스트 DB 이름이 같음 | 시작 거부 |
| 기준 DSN의 DB 이름이 비어 있음 | 시작 거부 |
| 기존 DB에 표식 없음 | 사용·정리 거부 |
| 새 테스트 DB | 생성할 때 표식도 생성 |
| 표식이 있는 테스트 DB | 정해진 테스트 초기화 경로 사용 |

[PR #61의 변경과 테스트](https://github.com/3K-PokeClip/PokeClip-mono/pull/61/files)는 동일 이름, 빈 이름, 표식 없는 기존 DB의 거부 경계와 정상 생성 경로를 다룹니다. 이 사례의 수치 1,121은 오염이 발견된 당시의 행 수입니다. 삭제 시간을 줄였다는 성능 지표나 이후 모든 데이터 사고가 사라졌다는 통계로 쓰지 않습니다.

## 격리한 뒤에도 동시 실행은 별도 문제입니다

명시적 표식을 붙여도 같은 DB 이름을 두 테스트 실행이 함께 쓰면 서로의 데이터를 지울 수 있습니다. 그래서 실행별 고유 DB 이름 규약을 남겼습니다. 표식은 테스트가 사용할 권한이 있는 대상을 구분하지만, 두 실행을 서로 격리하는 이름까지 대신 만들어 주지는 않습니다.

DB를 생성하려면 테스트 계정에 `CREATEDB` 권한도 필요합니다. PostgreSQL의 [CREATE DATABASE 문서](https://www.postgresql.org/docs/current/sql-createdatabase.html)가 설명하는 생성 권한과 실제 테스트 환경 설정을 맞춰야 합니다. 기존 테스트 DB에는 일회성 이행이 필요하며, 표식이 없다는 이유로 발견한 DB를 자동으로 비우는 방식은 선택하지 않았습니다.

## 복구 코드를 의심하기 전에 실험이 오염됐는지 보기

이번 변경은 제품 업로더의 재시도 알고리즘을 빠르게 만든 일이 아닙니다. 복구 실험이 사용하는 데이터의 출처를 분리해, 제품의 실패와 테스트가 남긴 가짜 상태를 구분할 수 있게 한 일입니다. [전체본 33쪽](/portfolio/2026-10-15-v2/full.pdf#page=33)은 이 판단과 반례를 요약합니다.

테스트 종료가 반드시 실행된다는 가정은 프로세스 장애를 검증할 때 특히 약합니다. 저는 실패를 다루는 테스트일수록 정리 코드의 성실함보다 쓰기 대상과 소유권 확인이 먼저라는 기준을 얻었습니다. 실험이 끝난 뒤 치우는 일과, 애초에 다른 데이터에 손대지 못하게 하는 일은 서로 다른 보장입니다.
