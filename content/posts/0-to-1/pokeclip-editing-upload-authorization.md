방송자가 편집자에게 클립 제작을 맡겨도 자기 유튜브 채널에 무엇이 올라갈지에 대한 최종 결정은 갖고 싶을 수 있다. 그런데 “편집 가능”이라는 권한 하나가 업로드까지 허용한다면 제작 권한과 채널 통제 권한이 섞인다. 반대로 권한이 없다는 이유로 업로드 요청 자체를 막으면 편집자는 완성한 결과를 서비스 밖에서 다시 전달해야 한다.

나는 PokeClip의 전체 권한 흐름을 설계하면서 클립 제작, 직접 업로드, 자동 업로드를 나누고 승인 대기함을 두기로 했다. 코어 서비스의 주 구현은 팀원 담당이다. 이 글은 내가 선택·조율한 권한 모델이며, 모든 검사와 업로드가 배포돼 실제 통제가 완료됐다는 성과로 쓰지 않는다.

## 외부 채널 토큰과 내부 사용자 권한은 다른 질문이다

YouTube API에 영상을 올릴 때는 어느 채널을 대신할 자격이 있는지 확인해야 한다. [YouTube의 OAuth 문서](https://developers.google.com/youtube/v3/guides/authentication)는 사용자가 동의한 범위에 따라 애플리케이션이 사용자를 대신해 접근하는 구조를 설명한다. 하지만 그 채널 토큰을 가진 서버 안에서 어느 편집자의 요청을 실행할지는 우리 서비스의 권한 문제다.

편집자에게 방송자의 OAuth 토큰을 넘기는 방식은 택하지 않았다. 편집자는 자기 계정으로 로그인하고, 서버가 해당 행위의 허용 여부를 검사한 뒤 방송자가 연결한 채널 토큰으로 업로드를 실행하도록 설계했다. 편집자 자신의 유튜브 채널을 연결할 필요도 없다. 행위의 주체와 외부 채널의 소유자를 다르게 모델링한 것이다.

## 세 권한을 하나의 스위치로 합치지 않았다

| 행위 | 권한 관계 | 결과를 보내는 곳 |
|---|---|---|
| 기본 클립 제작 | 편집 권한 | 편집 결과 |
| 직접 업로드 | 별도의 직접 업로드 권한 | 방송자의 채널 업로드 경로 |
| 원클릭 자동 업로드 | 직접 업로드를 전제로 하는 상위 권한 | 승인된 자동 실행 범위 |
| 직접 업로드 권한 없는 요청 | 요청은 보존, 즉시 실행하지 않음 | 방송자의 승인 대기함 |

자동 업로드를 단순히 버튼 하나 덜 누르는 기능으로 보면 권한 관계가 모호해진다. 자동으로 실행할 수 있다면 직접 실행할 권한도 있어야 한다고 정했다. 자동 실행에 영향을 주는 템플릿 수정은 방송자에게 두어 그 범위도 통제하도록 했다.

이 모델은 권한을 세분화한 횟수 자체가 성과라는 뜻은 아니다. 서로 독립적으로 통제하고 싶은 행위를 먼저 찾고, 실제로 종속되는 행위만 연결했다. 편집을 허용하면서 게시 결정을 보류할 수 있어야 한다는 제품 요구에서 출발한 선택이다.

## 권한이 없어도 작업 결과를 버리지 않는다

직접 업로드 권한이 없는 편집자가 요청하면 승인 대기함에 남긴다. 방송자는 승인하거나 반려하고, 편집자는 자기 요청의 상태를 본다. 요청을 처음부터 차단하는 대안과 비교하면 서버가 관리할 상태가 늘지만, 결과물을 밖으로 옮겨 전달하는 일을 줄일 수 있다.

여기서 승인 대기와 실제 외부 전송은 분리해서 설명해야 한다. 승인은 그 결과를 게시해도 된다는 내부 판단이고, 전송은 외부 API와 네트워크가 관여하는 작업이다. 한 단계의 성공을 다른 단계의 완료로 표시하면 사용자는 승인됐는데 어디에도 없는 영상이나 실패했는데 완료로 표시된 상태를 보게 된다. 이 글은 그 상태 전이를 구현했다고 새로 주장하는 대신, 설계에서 나눠야 할 책임을 설명한다.

## 업로드도 공개와 전송을 나눠 생각했다

기본 비공개 업로드와 재개 가능한 전송을 설계했다. 파일을 서버에 올리는 동안 통신이 끊겼다고 완성된 편집 결과부터 다시 만들 필요는 없기 때문이다. [YouTube의 재개 가능한 업로드 문서](https://developers.google.com/youtube/v3/guides/using_resumable_upload_protocol)는 업로드 세션과 전송 상태를 이용해 중단된 전송을 이어 가는 절차를 설명한다.

다만 이 문서가 있다는 이유로 프로젝트의 전송 복구 검증이 끝난 것은 아니다. 외부 API 프로젝트의 검증과 할당량, 실제 토큰 수명과 실패 처리는 별도 조건이다. 예전 설계 문서에 적은 할당량을 현재의 확정 숫자로 가져오지 않는다. 이 글에는 실제 게시 처리량이나 권한 오류 감소율도 제시하지 않는다. 측정하지 않은 숫자를 설계의 효과로 붙이지 않기 위해서다.

## 통제와 협업을 같은 흐름 안에 남긴다

2026년 10월 판본에서 이 사례의 범위는 전체 권한 모델과 토큰 소유, 승인 흐름의 설계다. 관련 서비스가 구현·검증해야 할 경계가 무엇인지 정한 것이고, 실제 사용자 채널을 대상으로 상용 운영을 했다는 기록은 아니다.

편집자의 일을 서비스 밖으로 밀어내지 않으면서 방송자의 최종 통제를 유지하려면 요청을 보존하는 상태가 필요했다. 그래서 “누가 파일을 만들 수 있는가”, “누가 게시를 결정하는가”, “누구의 토큰으로 실행하는가”를 따로 물었다. 하나의 권한 스위치로 합치기 전에 이 세 질문을 나눈 것이 이 설계의 출발점이다.
