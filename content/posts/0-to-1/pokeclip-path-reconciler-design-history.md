계정별 방송 경로를 서버 메모리에 한 번 추가하면 끝일까. 미디어 서버가 재시작하면 경로가 사라질 수 있고, 계정 키가 폐기되면 이미 반영한 설정도 바뀌어야 한다. 인증 서비스가 잠시 응답하지 않는 동안 무엇을 지켜야 하는지도 정해야 했다.

이 글은 2026년 10월 초 검토했던 `path-reconciler`의 **과거 설계 기록**이다. 나는 Auth의 원하는 상태를 미디어 옆 조정자가 주기적으로 가져오는 방식을 선택하고 실패 조건을 정했다. 그러나 **10월 6일 연결별 인증 방식으로 방향을 바꿨으므로, 아래 조정자가 현재 구현이라고 소개하지 않는다.** 설계·실측은 AI 협업이었고 대안 채택과 전환은 내가 결정했다.

## 한 번 밀어 넣는 대신 주기적으로 맞추려 했다

당시 경로별 passphrase를 설정해야 한다는 전제에서는 Auth가 MediaMTX로 한 번 push하는 것만으로 충분하지 않았다. Auth가 미디어 서버 재시작을 알아야 하고, 서버 사이에 관리 API 접근도 열어야 한다. 그래서 미디어 옆 조정자가 Auth의 원하는 상태를 pull하고 실제 경로와 맞추는 안을 택했다. 경로를 다루는 기반 API는 [MediaMTX Control API](https://mediamtx.org/docs/features/control-api)다.

| 대안 | 처리하기 쉬운 것 | 추가로 남는 책임 |
|---|---|---|
| Auth에서 경로 변경 push | 계정 변경 직후 알림 | 미디어 재시작 감지·재전송·관리 API 접근 |
| 미디어 옆 조정자의 pull | 재시작 뒤 원하는 상태 재수집 | 주기 지연·부분 응답·삭제 판단 |
| 연결별 인증 | 연결 시점에 계정을 판정 | 인증 대기·응답기·수신부 계약; 후속 선택 |

조정자는 Auth의 모든 페이지를 받아 완전한 목록을 만든 뒤 비밀 참조를 해석하고 Control API에 반영하는 구조였다. 평문 비밀 대신 Secrets Manager 참조를 받는 안이었고, 실제 비밀 저장 이행은 선행 조건이었다. 원문 저장 이전은 현재 준비 중인 별도 계획이며, 옛 조정자안과 함께 완료된 것으로 묶지 않는다.

## 없는 계정과 읽지 못한 계정은 다르다

첫 페이지는 받았지만 둘째 페이지에서 실패했다면 아직 못 읽은 계정이 있다. 여기서 “응답에 없는 경로는 삭제”를 적용하면 정상 방송을 지울 수 있다. 그래서 전체 목록의 완전성을 확인하기 전에는 누락을 삭제 근거로 쓰지 않기로 했다.

키 폐기는 반대 방향의 위험도 있다. 확인한 폐기 결정을 다음 주기의 오류 때문에 되돌려서는 안 된다. 이미 진행 중인 세션과 새 접속은 구분하고, 마지막 정상 확인 이전에 시작한 방송은 종료까지 보호하는 조건을 검토했다. Auth 장애 허용 시간이 지나 확인되지 않은 새 접속을 닫더라도, Control API 실패로 실제 반영이 지연된다면 그 차이를 health에 드러내야 한다고 정했다.

이것은 완성된 장애 처리의 성과가 아니라 설계에서 세운 불변 조건이다. 프로세스 자체가 죽으면 마지막 설정이 남는 fail-static, 조회와 변경 사이의 경합은 여전히 제약이었다. 문서에 차단 규칙이 있다고 실제 차단이 즉시 보장되는 것은 아니다.

## 앞 단계가 시간을 다 쓰지 않게 한다

Auth 조회, 비밀 해석, 경로 적용에 시간 예산을 나누었다. 앞 단계의 대기가 전체 시간을 사용하면, 이미 알고 있는 폐기를 적용하는 일도 밀릴 수 있기 때문이다. 계속 실패하는 키 하나가 뒤의 후보를 굶기지 않도록 FIFO 후보 큐도 검토했다. 긴급 차단은 Auth 폐기와 운영자 차단 목록으로 다루고 서버 재시작을 정상적인 키 폐기 수단으로 삼지 않았다.

이 판단을 뒷받침한 당시 인증 지연 주입 기록이 있다. 10월 5일 원시 패킷과 로그를 다시 읽어 새 연결과 다른 요청의 대기를 비교했다.

| 실험 조건 | 관측 |
|---|---|
| 동시 연결 10개, 인증 지연 0.1초 | 마지막 수락 1.059초 |
| 동시 연결 10개, 인증 지연 0.3초 | 마지막 수락 3.057초 |
| 인증 지연 1.5초 | 새 HLS 세션과 경로 목록 API도 약 1.49초 대기 |

연결마다 인증 요청은 1회였고 순서대로 처리됐다. 새 HLS 세션과 목록 API는 각각 10회 확인했다. 인증 대기가 다른 요청으로 번지는 조건을 본 것이며, 기존 방송 전체가 중단됐다는 결과나 수정 후 성능 개선율은 아니다.

## 전제를 바꾸면 설계도 과거형으로 남겨야 한다

후속 방향은 연결마다 MediaMTX의 HTTP 인증을 응답기가 받아 Auth에 계정을 확인하고, 그 계정의 SRT passphrase를 연결에 사용하는 방식이다. 관련 상류 제안 [MediaMTX #6306](https://github.com/bluenviron/mediamtx/pull/6306)은 2026년 10월 15일 확인 시 열려 있으며, 병합·릴리스 성과로 세지 않는다. dev-media 연동과 실제 서버 검증도 별도 진행 조건이다.

전환했다고 이전 검토가 전부 무의미해진 것은 아니다. 부분 응답과 삭제를 구분하고, 이미 확인한 폐기를 뒤의 오류로 뒤집지 않으며, 인증 대기의 영향을 관측해야 한다는 판단은 남는다. 다만 그 판단을 보여주기 위해 폐기한 구현을 현재 시스템처럼 설명할 필요는 없다.

이 사례를 대표 성과 대신 참고 기록으로 둔 이유도 그것이다. 현재 연결별 방식의 구현·검증을 설명할 때 비교 대상으로 활용할 수 있지만, 과거 조정자안의 상세함이 현재 기능의 완료를 대신하지는 않는다.
