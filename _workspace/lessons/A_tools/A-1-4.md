## 레벨 A-1 / 4강: `.env` vs `.zshrc` — 두 파일의 로딩 타이밍과 스코프

> 둘 다 환경 변수를 쓰지만 *언제 / 어디서 / 누가 읽는지*가 완전히 다르다. 헷갈리면 API 키가 깃에 올라간다.

---

### 들어가며 — 같은 "환경 변수"라는 이름의 함정

3강에서 환경 변수와 PATH를 다뤘다. `export OPENAI_API_KEY=sk-...` 한 줄로 셸에 키를 박을 수 있다는 걸 봤다. 그런데 여기서 입문자 90%가 다음 단계로 이런 선택을 한다.

> "매번 export 치기 귀찮으니 `.zshrc`에 적어두자. 그러면 터미널 열 때마다 자동으로 잡힌다."

겉으론 합리적이다. 실제로 동작도 한다. 그래서 더 무섭다. 이 한 줄이 한 달 뒤에 다음과 같은 사건으로 돌아온다.

```
$ git push
remote: ----------------------------------------------------------
remote:  We detected a OpenAI API key in your repository.
remote:  Please remove it and rotate the key.
remote: ----------------------------------------------------------
```

또는 더 조용하게, 6개월 뒤에 OpenAI 청구서가 평소의 40배 찍힌다. 누군가 깃허브 공개 저장소에서 키를 긁어 GPT-4를 돌렸다는 뜻이다.

이 강의는 그 사고를 막는 강의다. `.env`와 `.zshrc`가 *무엇이 어떻게 다른지*만 정확히 알면 사고는 일어나지 않는다.

비유 하나로 머리에 박아두자.

- `.zshrc` = **셸 켤 때 읽는 설정 메모**. 셸이 자기 자신을 위해 본다.
- `.env` = **앱이 시작할 때 들고 가는 봉투**. 앱 프로세스가 자기를 위해 본다.

다른 사람이 읽고, 다른 시점에 읽고, 다른 곳에 영향을 준다.

---

### 1. `.zshrc` 가족 — 셸이 자기를 위해 읽는 파일

`.zshrc`만 있는 게 아니다. 비슷한 이름의 파일이 여럿 있고, 입문자에게는 다 똑같아 보인다. 우선 줄세우자.

| 파일 | 사용자 | 언제 읽히는가 |
|---|---|---|
| `.zshrc` | zsh | 셸이 켜질 때마다 (interactive) |
| `.zprofile` | zsh | login shell로 켜질 때만 한 번 |
| `.bashrc` | bash | 셸이 켜질 때마다 (interactive non-login) |
| `.bash_profile` | bash | login shell로 켜질 때만 |
| `.profile` | 모든 sh 계열 | login shell 기본 fallback |

macOS 기본 셸은 zsh, Amazon Linux EC2 기본 셸은 bash. 둘이 파일 이름이 다르다는 사실 자체가 입문자 사고의 절반을 만든다. EC2 들어가서 `.zshrc`에 박은 export가 안 먹어서 30분 헤매는 일이 흔하다.

#### login shell vs non-login shell (결론만)

| 셸 진입 경로 | 종류 | 읽히는 파일 (zsh 기준) |
|---|---|---|
| 터미널 앱(iTerm/Terminal) 새 창 | interactive | `.zshrc` |
| `ssh user@host`로 원격 접속 | login + interactive | `.zprofile` → `.zshrc` |
| 스크립트 실행 (`bash script.sh`) | non-interactive | 아무것도 안 읽힘 |
| Docker 컨테이너 `CMD` | non-interactive | 아무것도 안 읽힘 |

기억해야 할 결론은 단 하나.

> **스크립트와 Docker는 `.zshrc`를 안 읽는다.**

이것 하나만 알아도 "로컬 터미널에선 잘 되는데 cron / Docker / CI에선 환경 변수가 비어있다"는 80%의 사건을 즉시 진단할 수 있다.

#### `.zshrc`가 실제로 하는 일

```zsh
# ~/.zshrc 예시
export PATH="/opt/homebrew/bin:$PATH"
export EDITOR="vim"
alias gs="git status"
alias k="kubectl"

# 프롬프트 커스터마이즈
PS1='%F{cyan}%n@%m%f %~ %# '

# 자동완성
autoload -U compinit && compinit
```

PATH 세팅, 별칭, 프롬프트, 자동완성 — **셸 자신을 쓰기 편하게 만드는 설정**이 본질이다. 키-값 한 두 개 박는 것보다 셸의 행동 자체를 정의하는 곳이다.

### 2. `.env` — 애플리케이션이 자기를 위해 읽는 파일

`.env`는 형식이 매우 단순하다.

```
OPENAI_API_KEY=sk-proj-abc123
CHZZK_CHAT_TOKEN=ch-xyz789
AWS_ACCESS_KEY_ID=AKIA...
AWS_SECRET_ACCESS_KEY=...
DATABASE_URL=postgresql://user:pass@localhost:5432/pokeclip
```

키=값을 한 줄씩 적은 텍스트 파일. 그게 끝이다. 표준 포맷도 아니다. 누가 정한 적도 없다. **셸은 이 파일을 자동으로 읽지 않는다.**

> `.env`는 셸이 안 읽는다. 앱이 읽는다.

읽는 주체가 누구냐에 따라 라이브러리가 갈린다.

#### Python — `python-dotenv`

```python
# main.py
from dotenv import load_dotenv
import os

load_dotenv()  # 같은 디렉터리의 .env를 os.environ에 주입

api_key = os.getenv("OPENAI_API_KEY")
print(f"키 앞 8자: {api_key[:8]}")
```

```bash
$ pip install python-dotenv
$ python main.py
키 앞 8자: sk-proj-
```

`load_dotenv()`가 하는 일은 단순하다. `.env` 파일 한 줄씩 읽어서 `os.environ` 사전에 넣는다. **Python 프로세스 안에서만 산다.** 셸로 안 새어 나가고, 자식 프로세스에는 (export처럼) 상속된다.

#### Node.js — `dotenv`

```javascript
// index.js
require('dotenv').config();

console.log(`키 앞 8자: ${process.env.OPENAI_API_KEY.slice(0, 8)}`);
```

```bash
$ npm install dotenv
$ node index.js
키 앞 8자: sk-proj-
```

원리는 똑같다. `.env`를 읽어서 `process.env`에 넣는다.

#### Docker Compose — `env_file`

```yaml
# docker-compose.yml
services:
  analyzer:
    image: pokeclip/analyzer:latest
    env_file:
      - .env                # 파일 통째로 컨테이너 환경 변수에 주입
```

Compose가 컨테이너 띄울 때 `.env`를 읽어 컨테이너 프로세스에 환경 변수로 넘겨준다. 컨테이너 안의 Python은 `os.getenv("OPENAI_API_KEY")`로 그대로 받는다. **이 경우 `python-dotenv`는 필요 없다** — Compose가 이미 주입했기 때문.

### 3. 결정적 차이 4가지 — 이 표 하나가 강의의 무게중심

| 항목 | `.zshrc` | `.env` |
|---|---|---|
| **로딩 주체** | 셸 (zsh)가 직접 읽음 | 셸은 안 읽음. 앱/라이브러리/Compose가 읽음 |
| **스코프** | 그 셸 세션 + 거기서 띄운 모든 자식 프로세스 | 그 앱 프로세스 한 개 (또는 Compose가 띄운 컨테이너 한 개) |
| **라이프타임** | 터미널 창 닫을 때까지 | 앱이 종료될 때까지 (보통 더 짧음) |
| **깃 추적 여부** | 보통 dotfiles 저장소에 *공개*로 올림 | 절대 안 올림 (`.gitignore` 필수) |

이 표를 손으로 한번 써보고 다음으로 가자. 외워야 한다. 이 4행을 외우면 *모든 결정*이 자동으로 나온다.

#### 결정 트리

"API 키를 어디 박을까?" 물음에 대한 답은 위 표에서 자동 도출된다.

- **로딩 주체**: 키는 앱이 쓴다 → `.env`
- **스코프**: 키는 한 앱만 알면 된다, 셸 전체에 노출될 필요 없음 → `.env`
- **라이프타임**: 앱이 죽으면 키도 사라지는 게 안전 → `.env`
- **깃 추적**: 키는 절대 깃에 안 들어가야 함 → `.env` (`.gitignore`로 막음)

**4행 모두 `.env`가 정답.** `.zshrc`가 정답이 되는 케이스는 *없다*.

### 4. 안티패턴 — `.zshrc`에 API 키 박고 git push까지 가는 사고 시퀀스

가장 흔한 사고를 시간순으로 풀어본다.

#### Day 1 — 잠깐의 편의

```zsh
# ~/.zshrc 마지막 줄에 추가
export OPENAI_API_KEY="sk-proj-abc123xyz789"
```

터미널 새 창 열면 자동으로 잡힌다. 편하다. 동작 OK.

#### Day 30 — 노트북 셋업 백업

새 맥북을 사거나, 설정을 잃기 싫어서 dotfiles를 깃허브에 올린다.

```bash
$ cd ~/dotfiles
$ cp ~/.zshrc .
$ git add .zshrc
$ git commit -m "Add zsh config"
$ git push
```

저장소가 `private`이면 일단 살았다. `public`이면 끝.

#### Day 31 — 봇이 긁어간다

깃허브 공개 저장소를 실시간으로 스캔하는 봇이 수십 개 돈다. `OPENAI_API_KEY=sk-` 패턴은 30초 안에 잡힌다. 깃허브 자체 시크릿 스캔도 잡는다 — 그래서 `git push` 거부 메시지가 뜨기도 한다. 단, *못 잡는 경우*가 더 무섭다.

#### Day 45 — 청구서

OpenAI 대시보드에 평소의 40배 호출량이 찍힌다. 누가 GPT-4 32k로 한 달 내내 돌렸다.

#### 후처리

키 폐기는 OpenAI 대시보드 한 번이면 된다. 그런데 깃 히스토리에 박힌 키는 *현재 파일을 지워도 남아 있다*. `git log -p`로 다 보인다.

> 히스토리에서 키를 완전히 지우려면 `git filter-repo` 같은 history rewrite가 필요한데, 이건 A-2 (Git 깊이) 강의에서 다룬다. **지금은 "애초에 박지 않는다"가 유일한 방어**.

#### 회피 — 한 줄짜리 규칙

```
.zshrc에 API 키를 넣지 않는다.
```

이 규칙 하나만 지키면 위 사고는 일어나지 않는다. 그리고 키를 `.env`로 보낼 때 따라붙는 규칙이 다음 항목이다.

### 5. `.env`는 무조건 `.gitignore` — `.env.example` 패턴

`.env`를 쓴다고 자동으로 안전하지는 않다. 깃에 올라가면 똑같이 죽는다. 그래서 **모든 프로젝트는 다음 두 파일을 동시에 둔다**.

#### `.gitignore`

```gitignore
# 환경 변수 파일 — 절대 커밋 금지
.env
.env.local
.env.*.local

# 단, 예시 파일은 허용
!.env.example
```

`.env.local` 같은 변종까지 막아둔다. Next.js, Vite 등이 환경별 파일을 쓰기 때문.

#### `.env.example` — 키 이름만 공유

```
# .env.example — 깃에 커밋함
# 실제 값은 1Password / AWS Secrets Manager / 팀 노션 비공개 페이지에서 받아 .env에 채워 넣을 것

OPENAI_API_KEY=
CHZZK_CHAT_TOKEN=
AWS_ACCESS_KEY_ID=
AWS_SECRET_ACCESS_KEY=
AWS_REGION=ap-northeast-2

DATABASE_URL=postgresql://user:pass@localhost:5432/pokeclip
SRT_LISTENER_PORT=9000
```

값은 비워두고 *키 이름과 형식*만 공유한다. 신규 팀원은 이걸 보고 `.env`를 만든다.

```bash
$ cp .env.example .env
$ vim .env   # 실제 값 채우기
```

이 패턴이 표준이다. README에는 보통 다음 한 줄을 쓴다.

> `cp .env.example .env` 후 실제 값을 채워 넣으세요. `.env`는 깃에 커밋하지 마세요.

### 6. `direnv` — 디렉터리 진입 시 자동 로드 (한 줄 소개)

`.env`를 매번 `load_dotenv()` 호출 없이 셸 단에서 자동 로드하고 싶을 때 쓰는 도구. `cd` 들어가면 그 디렉터리의 `.envrc`/`.env`를 자동으로 export, 나오면 자동 unset. 설치/셋업은 A 트랙 슬림 원칙상 다루지 않음 — *이름만 기억*하면 됨.

### 7. Docker 환경 변수 주입 — 3가지 방법

Docker 컨테이너 안의 프로세스는 `.zshrc`를 안 읽는다. `.env`도 자동으로 안 읽는다. **명시적으로 넣어줘야 한다.** 방법은 셋.

#### 방법 1 — `-e KEY=value` (한 개씩)

```bash
$ docker run \
    -e OPENAI_API_KEY=sk-proj-abc123 \
    -e AWS_REGION=ap-northeast-2 \
    pokeclip/analyzer:latest
```

가장 단순. 한두 개일 때만. 키가 셸 history (`~/.zsh_history`)에 평문으로 남는다는 단점이 있다.

#### 방법 2 — `--env-file .env` (파일 통째)

```bash
$ docker run --env-file .env pokeclip/analyzer:latest
```

`.env` 파일을 통째 컨테이너에 넣는다. CLI 한 줄이라 깔끔하고 history 오염도 없다. 로컬 개발에서 가장 자주 쓰는 방식.

#### 방법 3 — Docker Compose `env_file` / `environment` (실무 표준)

```yaml
# docker-compose.yml
services:
  analyzer:
    image: pokeclip/analyzer:latest
    env_file:
      - .env                           # 파일에서 일괄 주입
    environment:
      LOG_LEVEL: INFO                  # 인라인으로 추가/덮어쓰기
      WORKER_COUNT: 4

  chat-lambda-local:
    image: pokeclip/chat:latest
    env_file:
      - .env
    environment:
      CHZZK_API_BASE: https://api.chzzk.naver.com
```

`env_file`로 공통 키 일괄 주입, `environment:`로 서비스별로 덮어쓰기. **운영 표준 패턴**.

#### 우선순위

같은 키가 여러 곳에 정의되면 다음 순서로 우선.

1. `environment:` (Compose 안 인라인)
2. `--env-file` / `env_file`
3. 컨테이너 이미지 자체의 `ENV` (Dockerfile)
4. 호스트 셸의 환경 변수 (Compose가 `${VAR}` 치환할 때만)

### 실무 적용 시나리오 3개

지금까지의 규칙을 *실제 사고 시점*에서 어떻게 쓰는지 본다.

#### 시나리오 1 — OpenAI API 키 발급. 어디에 박을까

OpenAI 대시보드에서 `sk-proj-...` 키를 새로 발급받았다. 3초 안에 결정해야 한다.

- `.zshrc`? **NO.** 모든 셸 세션에 노출. dotfiles 백업으로 새어나갈 위험. 4행 표의 4개 항목이 전부 어긋남.
- 셸에서 `export`만? **임시.** 터미널 닫으면 사라짐. 매번 다시 박아야 함.
- `.env`? **YES.** 

진행 절차.

```bash
$ cd ~/projects/pokeclip
$ cat .env.example   # 키 이름 확인
$ cp .env.example .env
$ vim .env           # OPENAI_API_KEY=sk-proj-... 채워 넣기
$ cat .gitignore | grep '^\.env'   # .env가 무시되는지 재확인
.env
$ git status         # .env가 untracked로도 안 나오는지 확인
```

Python 코드에서.

```python
from dotenv import load_dotenv
import os
from openai import OpenAI

load_dotenv()
client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))
```

**판단 근거**: `.env`는 (1) 앱이 읽고, (2) 한 프로젝트에만 산다, (3) 앱 종료 시 사라진다, (4) 깃에 안 올라간다. 4행 표 그대로.

#### 시나리오 2 — 로컬에선 잘 되는데 EC2에선 안 됨

PokéClip 분석 서버를 EC2에 배포했다. 로컬에서 잘 돌던 코드가 EC2에서 다음과 같이 죽는다.

```
$ python analyzer.py
Traceback (most recent call last):
  File "analyzer.py", line 12, in <module>
    client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))
  File ".../openai/_client.py", line 105, in __init__
    raise OpenAIError("api_key is required")
openai.OpenAIError: api_key is required
```

원인을 3초에 진단해야 한다. 머릿속에서 4행 표를 본다.

> `.env`의 스코프 = 그 앱 프로세스 한 개.
> 깃 추적 = 안 됨.
> 따라서 **`.env`는 깃 pull로 EC2에 따라오지 않는다.**

`.env`를 EC2에 직접 올려야 한다. 

```bash
# 로컬에서 EC2로 .env 복사
$ scp -i ~/.ssh/pokeclip.pem .env ec2-user@1.2.3.4:/home/ec2-user/pokeclip/.env

# EC2 안에서 확인
$ ssh pokeclip
[ec2-user@ip-... pokeclip]$ ls -la .env
-rw------- 1 ec2-user ec2-user 412 Jun 23 14:22 .env
[ec2-user@ip-... pokeclip]$ python analyzer.py   # OK
```

`.env` 자체는 깃이 가져다 주지 않는다는 게 핵심. 운영 환경에선 더 안전한 방법(AWS Secrets Manager, Parameter Store 등)을 쓰지만 그건 G/I 트랙. *지금 단계의 진단*은 "`.env` 안 올라옴" 한 줄.

#### 시나리오 3 — Docker 컨테이너 환경 변수가 비어있음

Compose로 띄운 분석 컨테이너 안에서 `OPENAI_API_KEY`가 비어있다.

```bash
$ docker compose up analyzer
analyzer | api_key is None
analyzer exited with code 1
```

4행 표 재확인. **컨테이너 = 별도 프로세스 = 별도 스코프.** 호스트 셸의 환경 변수도, 호스트의 `.env`도 자동으로는 안 들어간다. 명시적으로 주입해야 한다.

체크리스트 3개.

1. **`env_file:` 빠짐**

   ```yaml
   services:
     analyzer:
       image: pokeclip/analyzer:latest
       # env_file 줄이 없음 ← 원인
   ```

   고치기.

   ```yaml
   services:
     analyzer:
       image: pokeclip/analyzer:latest
       env_file:
         - .env
   ```

2. **경로 오타 / 잘못된 위치**

   Compose는 `docker-compose.yml`이 있는 디렉터리를 기준으로 `.env`를 찾는다. 다른 폴더에 두면 못 찾는다.

   ```bash
   $ ls
   docker-compose.yml
   config/.env          ← 여기 있으면 못 찾음
   ```

   고치기 — Compose 옆으로 옮기거나 경로 명시.

   ```yaml
   env_file:
     - config/.env
   ```

3. **변수 이름 오타**

   `.env`에 `OPENAI_KEY=sk-...`로 박았는데 코드는 `os.getenv("OPENAI_API_KEY")`를 부른다. 컨테이너 안에서 직접 확인.

   ```bash
   $ docker compose run analyzer env | grep OPENAI
   OPENAI_KEY=sk-proj-abc123
   ```

   `_API_`가 빠졌다. 한쪽을 맞춘다.

세 체크리스트가 *3분 안에* 끝난다. 4행 표를 외워뒀기 때문에 "컨테이너는 자기 스코프"라는 사실에서 출발할 수 있다.

### PokéClip 적용 — 운영 표준 패턴

PokéClip이 실제로 채택하는 키 관리.

```
pokeclip/
├── .env.example          ← 깃 커밋. 키 이름과 형식만
├── .env                  ← 깃 무시. 실제 값. 로컬+EC2에 각각 둠
├── .gitignore            ← .env 차단
├── docker-compose.yml    ← env_file: [.env]
├── analyzer/
│   └── main.py           ← python-dotenv는 안 씀 (Compose가 이미 주입)
└── chat_lambda/
    └── handler.py        ← Lambda는 환경 변수를 콘솔에서 설정 (별도)
```

`.env`에 들어가는 키들.

```
OPENAI_API_KEY=sk-proj-...
CHZZK_CHAT_TOKEN=...
CHZZK_CHANNEL_ID=...
AWS_ACCESS_KEY_ID=AKIA...
AWS_SECRET_ACCESS_KEY=...
AWS_REGION=ap-northeast-2
S3_BUCKET=pokeclip-vods
DYNAMODB_TABLE=pokeclip-segments
SRT_LISTENER_PORT=9000
WHISPER_MODEL=large-v3
```

- **로컬 개발**: `.env`를 프로젝트 루트에 두고 Compose가 읽음.
- **EC2 분석 서버**: `scp`로 `.env`를 올린 뒤 Compose가 똑같이 읽음.
- **Lambda (채팅 분석)**: Compose가 못 쓰므로 AWS 콘솔에서 함수의 환경 변수에 직접 등록. 같은 키 이름 유지.
- **`.zshrc`**: 절대 안 박음. 셸 단에서는 `pyenv`, `aws-cli` PATH 같은 *셸 자체 동작*만.

이 패턴 그대로 가면 A-1-4의 모든 규칙이 자연스럽게 지켜진다.

### 이번 강의 핵심 3줄

1. `.zshrc`는 **셸이 자기를 위해** 읽는 파일. `.env`는 **앱이 자기를 위해** 읽는 파일. 로딩 주체부터 다르다.
2. 4행 표 — **로딩 주체 / 스코프 / 라이프타임 / 깃 추적**. 모든 행에서 API 키는 `.env`가 정답이다.
3. `.env`는 `.gitignore` 필수, `.env.example`로 키 이름만 공유, Docker엔 `env_file`로 주입. 이 세 가지가 운영 표준.

다음 강(A-1-5)에선 이 `.env`를 *원격 EC2*에 올리는 그 SSH 자체를 다룬다. 키 페어, `~/.ssh/config`, 첫 접속의 known_hosts까지.
