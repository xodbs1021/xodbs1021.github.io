# 시리즈 계획 A-1 — 터미널 + 환경 변수 + 에러 읽기

## 시리즈 한 줄 hook

AI가 짠 명령의 결과를 *읽을 줄* 알아야 디버깅이 가능하다. 터미널은 AI 출력의 첫 검증 도구이고, PokéClip EC2/Docker 환경에서 일이 막혔을 때 사람이 직접 가야 하는 유일한 자리.

## PokéClip 적용 영역

- **SRT Listener Server (EC2)**: SSH 첫 접속, 프롬프트 읽기, 분석 서버 에러 디버깅
- **Analysis Engines**: FFmpeg/YOLO/Whisper 실행 시 발생하는 stderr·exit code·traceback 해석
- **환경 변수 관리**: `.env`에 OpenAI API 키 / 치지직 채팅 API 토큰 / AWS 자격 증명 박기, Docker 컨테이너에 환경 변수 주입
- **운영 디버깅**: `command not found`와 PATH 오염, 잘못된 셸 초기화 파일

## 선행 시리즈

없음 — A 트랙 첫 시리즈. 마스터 의존 그래프상 모든 트랙의 뿌리.

## 시리즈 범위 (마스터 인용)

- **다룰 핵심 항목**:
  - 터미널/셸/CLI 용어 구분
  - 프롬프트 읽기 (사용자/호스트/경로/권한)
  - 환경 변수와 PATH 직관
  - "command not found"의 진짜 원인
  - 에러 메시지 읽기 패턴 (exit code / stderr / traceback)
  - `.env` 와 `.zshrc` 의 차이
  - SSH 첫 접속과 EC2 환경
- **다루지 않는 것**:
  - 셸 스크립팅 (Python으로 대체 — B 트랙)
  - Linux 명령어 외우기 (`ls/grep/awk` 등은 AI 위임)
  - Oh My Zsh 깊은 셋업 / 테마 / 플러그인 매니저
  - bash 함수 / alias 고급 패턴
  - Git (A-2에서 별도)

## 강의 구성

### A-1-1: 터미널 · 셸 · CLI · 프롬프트 — 검은 창의 4요소부터 읽기 — AI가 출력한 한 줄이 어디서 어떤 권한으로 돌고 있는지 모르면 그 다음 모든 디버깅이 추측이 된다

- 핵심 다룰 항목:
  - GUI vs CLI 짧은 정리 (왜 백엔드는 CLI인지)
  - 터미널·콘솔·셸·CLI 4개 용어 엄밀 구분 (창 vs 프로그램 vs 방식)
  - 프롬프트 4요소: 사용자 / 호스트 / 경로 / 권한 기호(`%`, `$`, `#`)
  - 로컬 macOS 프롬프트와 EC2 Amazon Linux 프롬프트 비교 (같은 구조, 다른 모양)
  - `whoami` / `hostname` / `pwd` / `id` 4개 — 프롬프트를 명령으로 검증
  - `%`(일반 사용자)와 `#`(root)의 차이 — 권한 한 글자 인식
  - 작업 디렉터리 한 줄 자동화 시연 (`mkdir -p`)
- 예상 분량: ~450줄
- 트레이드오프 포인트: GUI vs CLI 강의 전체를 도입에 두지 말 것 — AI 시대 핵심은 "출력 읽기"이므로 비교는 8~10줄로 압축하고 프롬프트 해부에 무게중심 이동
- 실무 적용 시나리오:
  - 시나리오 1: AI가 짜준 명령을 SSH 창에 붙였는데 권한 오류 → 프롬프트 `#` 아니고 `$`인 걸 보고 즉시 원인 진단
  - 시나리오 2: 두 터미널 창에서 같은 명령이 다른 결과 → 한쪽이 다른 서버라는 걸 호스트명으로 1초 만에 식별
  - 시나리오 3: PokéClip EC2 들어가자마자 `whoami`로 ec2-user인지 ubuntu인지 확인하고 sudo 필요 여부 판단
- 선행 강의: 없음 (시리즈 첫 강의)
- PokéClip 적용 인용: EC2 SRT Listener 서버에 SSH 접속한 직후 프롬프트 4요소를 1초 안에 읽고 "여기는 어떤 서버의 어떤 사용자로 들어와 있는가"를 판단하는 첫 행위

### A-1-2: 환경 변수와 PATH — "command not found"의 진짜 원인 — 명령은 실패하는 게 아니라 *못 찾는다*. 모든 셸 실수 70%는 PATH 한 변수에서 나온다

- 핵심 다룰 항목:
  - 환경 변수의 정체 (프로세스마다 들고 다니는 키-값 사전)
  - `env` / `printenv` / `echo $PATH`로 직접 보기
  - PATH = 콜론으로 이어진 디렉터리 검색 순서
  - 셸이 명령어를 실행할 때 PATH를 *순서대로* 뒤지는 알고리즘
  - `which` / `type` / `command -v`로 어떤 바이너리가 실제로 잡히는지 확인
  - "command not found"의 4대 원인: 설치 안 됨 / 설치는 됐는데 PATH에 없음 / PATH 순서가 잘못돼서 다른 게 잡힘 / 셸 캐시(`hash`) 오염
  - `export VAR=value` 와 `VAR=value command` (한 줄짜리 환경 변수)의 차이
  - 자식 프로세스로의 상속 (`export`가 없으면 안 넘어감)
- 예상 분량: ~480줄
- 트레이드오프 포인트: PATH 순서 변경(`export PATH=/new:$PATH` vs `export PATH=$PATH:/new`)의 결과 차이가 큰데 입문자가 가장 자주 망치는 지점 — 시연 2~3개 필수
- 실무 적용 시나리오:
  - 시나리오 1: `python3` 쳤더니 시스템 Python이 잡힘 → `which -a python3`로 우선순위 확인 → pyenv 경로 PATH 앞에 넣어 해결
  - 시나리오 2: `aws` 명령이 없다 → pip install 했는데 PATH에 ~/.local/bin이 없어서 안 잡힘
  - 시나리오 3: EC2에서 `node` 잡히는데 Docker 컨테이너 안에서는 안 잡힘 → 컨테이너의 PATH가 더 짧다는 사실 인식
- 선행 강의: A-1-1 (프롬프트와 셸 개념)
- PokéClip 적용 인용: pyenv로 띄운 Python 가상환경 안에서 FFmpeg 실행할 때 `ffmpeg: command not found`가 가장 자주 등장 — PATH 우선순위 디버깅이 일상

### A-1-3: 에러 메시지 읽기 — exit code · stderr · traceback의 3층 구조 — AI는 에러를 잘 짚지만 *어느 줄을 봐야 하는지*는 사람이 먼저 안다. 출력의 어디가 진짜 원인인지 골라내는 훈련

- 핵심 다룰 항목:
  - stdout vs stderr 분리 — 셸은 두 스트림을 같은 화면에 쏟지만 다른 채널
  - `>`, `2>`, `2>&1`, `&>`로 두 스트림을 갈라보기 (간단한 리디렉션만, 본격은 안 다룸)
  - exit code (`$?`)의 의미 — 0은 성공, 1~255는 실패의 종류. 셸이 다음 명령으로 갈지 말지의 기준
  - `&&` / `||`의 의미 = exit code 분기
  - Python traceback 읽는 순서 — *밑에서 위로* (최상단이 첫 호출, 최하단이 진짜 실패 지점)
  - 셸 에러 메시지 5종 분류:
    - `command not found` (PATH/타이포)
    - `permission denied` (권한)
    - `no such file or directory` (경로/오타)
    - `syntax error` (셸 자체의 문법)
    - 프로그램 자체의 에러 메시지 (Python·FFmpeg·Docker가 각자 던지는 것)
  - AI에 에러 붙여넣을 때 *무엇을 같이 줘야 하는가* — 명령어 + 마지막 N줄 + exit code + 환경(OS·셸·버전)
- 예상 분량: ~500줄
- 트레이드오프 포인트: AI 시대 핵심 강의. "에러 다 복붙해서 AI에 던지면 됨"의 함정을 깬다 — *어느 부분을 잘라서 줄지*가 디버깅 속도를 결정. 에러 컨텍스트 잘라내기 패턴 3~4개 명시
- 실무 적용 시나리오:
  - 시나리오 1: FFmpeg 100줄 로그에서 `[error]` 한 줄만 골라 AI에 전달 → 5번 왕복할 디버깅을 1번에 끝냄
  - 시나리오 2: Python traceback 30줄 중 *진짜 실패는 7번째 줄*임을 알아채고 그 부분만 발췌
  - 시나리오 3: 셸 스크립트가 조용히 실패(`$?` 0이 아님)했는데 화면엔 멀쩡해 보임 → exit code 체크 습관으로 발견
- 선행 강의: A-1-2 (셸 동작 모델)
- PokéClip 적용 인용: YOLO 분석 컨테이너가 OOM으로 죽을 때 stderr만 잡아내야 함 — stdout(추론 결과 JSON)과 stderr(에러)를 섞으면 분석 결과 파일이 오염

### A-1-4: `.env` vs `.zshrc` — 두 파일의 로딩 타이밍과 스코프 — 둘 다 환경 변수를 쓰지만 *언제 / 어디서 / 누가 읽는지*가 완전히 다르다. 헷갈리면 API 키가 깃에 올라간다

- 핵심 다룰 항목:
  - `.zshrc` / `.bashrc` / `.zprofile` / `.bash_profile` — 셸이 켜질 때 한 번 읽는 *셸 초기화 파일*
  - login shell vs non-login shell — 어떤 파일이 언제 읽히는가 (간단 표로 결론만)
  - `.env` — 셸이 아니라 *애플리케이션이* 읽는 파일 (Python의 `python-dotenv`, Node의 `dotenv`, Docker Compose의 `env_file`)
  - 둘의 결정적 차이 4가지: 로딩 주체 / 스코프 / 라이프타임 / 깃 추적 여부
  - 절대 `.zshrc`에 API 키 박지 말 것 — 모든 셸 세션에 노출 + 백업으로 새어나감 위험
  - `.env`는 무조건 `.gitignore` — `.env.example`로 키 이름만 공유하는 패턴
  - `direnv`(소개만, 셋업 X) — 디렉터리 진입 시 `.env` 자동 로드해주는 도구
  - Docker에서 환경 변수 주입 3가지: `-e KEY=val` / `--env-file .env` / Compose `environment:` (실무 가장 흔한 패턴)
- 예상 분량: ~440줄
- 트레이드오프 포인트: 입문자가 가장 자주 저지르는 사고가 *API 키를 `.zshrc`에 박고 git push* — 사고 회피 패턴을 강의 절반 분량으로 다룸. 깃 히스토리에서 키 제거하기는 A-2(Git)로 미룸
- 실무 적용 시나리오:
  - 시나리오 1: OpenAI API 키 받자마자 어디에 박을까 → `.env` + `python-dotenv`로 결정. `.zshrc`로 안 가는 이유 설명 가능
  - 시나리오 2: 로컬에선 잘 되는데 EC2에서 안 됨 → `.env` 파일을 서버에 안 올렸음을 즉시 진단
  - 시나리오 3: Docker 컨테이너 안에서 환경 변수가 비어 있음 → Compose `env_file` 빠짐 / 이름 오타 / 경로 문제
- 선행 강의: A-1-2 (환경 변수 개념)
- PokéClip 적용 인용: 치지직 채팅 Lambda의 토큰 / OpenAI / AWS 자격 증명을 `.env`에 박고 Docker Compose `env_file`로 컨테이너에 주입하는 운영 표준

### A-1-5: SSH 첫 접속과 EC2 환경 — 키 한 개로 원격 서버 열기 — 로컬에서 익힌 모든 게 *원격*에서도 똑같이 돈다는 걸 몸으로 확인하는 강의. 첫 SSH가 가장 무섭고 가장 빨리 익숙해진다

- 핵심 다룰 항목:
  - SSH = 원격 셸에 텍스트로 연결되는 프로토콜
  - 비밀번호 vs 키 페어 — EC2는 키 페어가 표준(비번 로그인 비활성)
  - 키 페어의 정체: 공개키(서버에 박힘) / 개인키(내 노트북에만 있음, `.pem`)
  - `~/.ssh/` 폴더와 `id_*` 파일, `authorized_keys`, `known_hosts`의 역할
  - 키 파일 권한 600 — `ssh -i key.pem`이 거부하는 가장 흔한 이유
  - `ssh -i ~/.ssh/pokeclip.pem ec2-user@PUBLIC_IP` 한 줄 해부
  - 첫 접속 시 `Are you sure you want to continue connecting (yes/no)?` — known_hosts에 fingerprint 등록되는 순간
  - 접속 후 환경 차이: 셸이 bash / 사용자가 ec2-user / 홈이 `/home/ec2-user` / `.env`는 직접 올려야 함
  - `~/.ssh/config` 단축 — `ssh pokeclip` 한 단어로 접속 (가장 실용적인 한 컷)
  - 끊김·재접속·`exit` / `Ctrl-D`로 빠져나오기
  - 보안 한 줄: 개인키는 절대 깃·슬랙·이메일에 올리지 말 것
- 예상 분량: ~470줄
- 트레이드오프 포인트: tmux/screen 같은 세션 유지 도구는 *언급만* — A 트랙 슬림화 원칙상 별도 강의로 빼지 않음. SSH 자체 셋업과 보안에 집중
- 실무 적용 시나리오:
  - 시나리오 1: 새 EC2 인스턴스 띄우자마자 키 다운로드 → `chmod 600` → `~/.ssh/config` 등록 → 단축어로 접속. 10분 표준 절차
  - 시나리오 2: 팀원이 키 잃어버림 → 내 공개키를 서버 `~/.ssh/authorized_keys`에 추가해서 임시 접속 권한 부여
  - 시나리오 3: 접속하니 권한 거부 → 키 파일이 644 → `chmod 600`으로 해결
- 선행 강의: A-1-1 (프롬프트 읽기 — EC2 프롬프트가 로컬과 어떻게 다른지 이미 익숙)
- PokéClip 적용 인용: AWS EC2의 SRT Listener Server / 분석 컨테이너 호스트에 매일 SSH로 들어가 FFmpeg·Whisper·YOLO 프로세스 상태 점검 — A-1 시리즈가 끝나는 그날부터 일상 운영의 출발점

## 시리즈 결과

이 시리즈를 마치면 학습자는 다음을 할 수 있다.

1. 임의의 터미널 창을 열어 프롬프트만 보고 "어떤 서버의 / 어떤 사용자로 / 어떤 디렉터리에서 / 어떤 권한으로" 작업 중인지 5초 안에 판단
2. AI가 짜준 명령이 `command not found`로 실패할 때 PATH·설치 여부·셸 캐시 중 어느 원인인지 추적
3. 셸/Python/FFmpeg 에러 메시지에서 *진짜 원인 한 줄*만 잘라 AI에 전달, 1회 왕복으로 해결
4. API 키를 `.env`에 박고 Docker로 주입하는 운영 표준 패턴 구현, `.zshrc`에 박는 안티패턴 회피
5. 새 EC2 인스턴스에 키 페어로 SSH 접속, `~/.ssh/config` 단축 등록, 끊김 없이 작업
