## 레벨 A-1 / 3강: 에러 메시지 읽기 — exit code · stderr · traceback의 3층 구조

> AI는 에러를 잘 짚는다. 그러나 *어느 줄을 보여줘야 하는지*는 사람이 먼저 안다. 출력의 어디가 진짜 원인인지 골라내는 훈련.

---

### 왜 "에러 읽기"가 AI 시대에 더 중요해졌는가

2강에서 `command not found`의 4대 원인을 분류했다. PATH 한 변수만 정확히 봐도 디버깅 절반이 끝났다. 그런데 그건 셸이 던지는 *5종 에러* 중 하나일 뿐이다. 나머지 4종을 만나면 어떻게 해야 하는가.

가장 흔한 입문자의 대처는 이렇다.

1. 에러 메시지가 나옴 (100줄짜리 FFmpeg 로그, 30줄짜리 Python traceback)
2. 화면 전체를 드래그해서 복사
3. ChatGPT/Claude에 "이거 왜 안 돼?" 한 줄과 같이 붙임
4. AI가 *추측*으로 답을 줌
5. 다시 안 됨 → 또 복붙 → 또 추측. 4~5번 왕복.

문제는 (3)이다. 100줄 중 *진짜 원인은 한 줄*인데 그 한 줄이 어디 있는지 사람이 안 골라줬다. AI는 100줄 전체를 *고르게* 본다 — 진짜 원인 한 줄과 무관한 99줄을 같은 무게로 읽는다. 그래서 추측이 된다.

이번 강의는 AI 시대 백엔드 입문자가 가장 빨리 효과를 보는 영역이다. **셸 출력의 3층 구조 — exit code, stderr, traceback — 를 분리해서 보는 법**과 **AI에게 던질 컨텍스트를 잘라내는 체크리스트**까지. PokéClip 운영 디버깅 속도가 *왕복 5번이 1번*으로 줄어드는 차이를 만든다.

---

### 로그는 두 채널의 동시 방송 — stdout vs stderr

검은 창에 명령을 친다. 화면에 출력이 쏟아진다. 이 출력은 보기엔 한 덩어리지만 사실 **두 개의 채널이 같은 화면에 동시 송출되는 라디오 방송**이다.

| 채널 | 정식 이름 | 셸 번호 | 용도 |
|---|---|---|---|
| 1번 | **stdout** (표준 출력) | `1` | 정상 결과. 다음 명령에 *데이터로* 흘러가는 줄. |
| 2번 | **stderr** (표준 에러) | `2` | 에러·경고·진행 메시지. 데이터가 아닌 *상태 보고*. |

[설명] stdout = standard output, stderr = standard error. 셸이 모든 프로그램에 자동으로 열어주는 두 출력 통로다. 입력 통로 stdin(번호 `0`)까지 합쳐 **표준 입출력 3종**.

같은 화면에 섞여 쏟아지므로 눈으로 보면 구분이 안 된다. 그런데 **셸은 두 채널을 따로 다룰 수 있다**. 이 사실 하나가 디버깅의 핵심이다.

```bash
# FFmpeg를 돌려본다 — 정상 결과(영상 데이터 X, 진행 로그)와 에러가 같이 쏟아진다
ty@MacBook-Pro pokeclip % ffmpeg -i input.mp4 output.mp4
ffmpeg version 6.1.1 Copyright (c) 2000-2023 the FFmpeg developers       ← stderr
  built with Apple clang version 15.0.0                                   ← stderr
  configuration: --prefix=/opt/homebrew/...                                ← stderr
...
Input #0, mov,mp4,m4a, ...                                                ← stderr
Stream #0:0: Video: h264 ...                                              ← stderr
[error] moov atom not found                                               ← stderr (★ 진짜 원인)
Conversion failed!                                                        ← stderr
```

놀라운 사실: FFmpeg가 화면에 쏟는 *거의 모든 줄이 stderr*다. FFmpeg는 stdout은 변환된 영상 데이터를 흘려보낼 때만 쓰고, 사람이 읽는 로그는 전부 stderr로 던진다. 이 설계는 "stdout은 다음 명령으로 데이터를 흘리는 파이프, stderr은 사람이 읽는 보고"라는 유닉스 철학을 충실히 따른 것.

같은 원리로 다음도 성립한다.

| 프로그램 | stdout으로 보내는 것 | stderr로 보내는 것 |
|---|---|---|
| `ls` | 파일 목록 | `permission denied` 같은 오류 |
| `python3 script.py` | `print()`로 찍은 줄 | traceback, `sys.stderr.write()` |
| FFmpeg | (보통 안 씀) 영상 데이터 | 진행 로그·에러 전부 |
| `docker run` | 컨테이너의 stdout | 컨테이너의 stderr + Docker 자체 메시지 |

### `>`, `2>`, `2>&1`, `&>` — 두 채널을 갈라보기

두 채널을 *셸이* 분리해주는 도구가 **리디렉션(redirection)** 연산자다. 표 한 장으로 끝.

| 기호 | 풀이 | 동작 |
|---|---|---|
| `>` | stdout만 파일로 | stderr는 화면에 그대로 보임 |
| `2>` | stderr만 파일로 | stdout은 화면에 그대로 보임 |
| `2>&1` | stderr를 stdout으로 합침 | "2번 채널을 1번 채널로 보내" |
| `&>` | stdout + stderr 둘 다 파일로 | `> file 2>&1`의 축약 (bash/zsh) |
| `2>/dev/null` | stderr를 *버림* | `/dev/null`은 모든 입력을 삼키는 휴지통 |

[설명] `2>&1`은 "2번을(stderr) 1번이 가리키는 곳으로(`&1`) 보내라". `&` 기호는 "1번 *파일* 말고 1번 *채널*"이라는 표시. `2>1`로 쓰면 *`1`이라는 이름의 파일*에 쓰게 되니 주의.

직접 시연해 본다.

```bash
# (A) 그냥 실행 — stdout과 stderr가 화면에 섞여서 보임
ty@MacBook-Pro pokeclip % ffmpeg -i input.mp4 output.mp4
ffmpeg version 6.1.1 ...
[error] moov atom not found
Conversion failed!

# (B) stdout만 파일로 — 에러는 여전히 화면에 보임
ty@MacBook-Pro pokeclip % ffmpeg -i input.mp4 output.mp4 > result.log
[error] moov atom not found                ← stderr는 화면 그대로
Conversion failed!

ty@MacBook-Pro pokeclip % cat result.log
                                            ← FFmpeg는 stdout 거의 안 써서 파일이 거의 빔

# (C) stderr만 파일로 — 에러만 따로 모음 (★ 분석용으로 가장 유용)
ty@MacBook-Pro pokeclip % ffmpeg -i input.mp4 output.mp4 2> error.log
ty@MacBook-Pro pokeclip % cat error.log
ffmpeg version 6.1.1 ...
[error] moov atom not found
Conversion failed!

# (D) 둘 다 한 파일로 합쳐서 — 시간 순서 그대로 보존
ty@MacBook-Pro pokeclip % ffmpeg -i input.mp4 output.mp4 > combined.log 2>&1
ty@MacBook-Pro pokeclip % cat combined.log
[전체 출력 시간 순서대로]

# (E) PokéClip 분석 표준 패턴 — stdout은 JSON 파일로, stderr는 별도 로그로
ty@MacBook-Pro pokeclip % python3 yolo_infer.py video.mp4 > result.json 2> infer.log
```

(E)는 PokéClip에서 매일 쓰는 패턴이다. YOLO 추론 스크립트의 `print(json.dumps(...))`는 `result.json`으로, 진행 로그·경고·에러는 `infer.log`로 분리. 둘이 섞이면 *결과 JSON 파일이 깨진다*. (이 시나리오는 끝부분에서 다시 다룬다.)

### exit code — 셸이 다음 명령으로 넘어갈지의 기준

화면에 보이는 텍스트 외에 *보이지 않는* 정보가 하나 더 있다. 모든 명령은 끝날 때 **exit code**라는 0~255 사이의 숫자를 반환한다.

| exit code | 의미 |
|---|---|
| `0` | 성공 |
| `1` | 일반적인 실패 |
| `2` | 셸 사용법 오류 (`grep --invalid-flag` 같은) |
| `126` | 권한 없음 (실행 불가) |
| `127` | command not found |
| `128 + N` | 시그널 N으로 종료 (`130` = Ctrl-C로 죽음 = `128+2`) |
| `137` | OOM killer로 죽음 (`128+9` = SIGKILL) |
| 그 외 `1~255` | 프로그램이 직접 정한 의미 |

직전 명령의 exit code는 `$?` 변수에 담긴다.

```bash
# 성공한 명령
ty@MacBook-Pro pokeclip % ls /
[디렉터리 목록 출력]
ty@MacBook-Pro pokeclip % echo $?
0                                          ← 성공

# 실패한 명령
ty@MacBook-Pro pokeclip % ls /nonexistent
ls: /nonexistent: No such file or directory
ty@MacBook-Pro pokeclip % echo $?
1                                          ← 실패

# command not found
ty@MacBook-Pro pokeclip % nonexistent_command
zsh: command not found: nonexistent_command
ty@MacBook-Pro pokeclip % echo $?
127                                        ← 정확히 127

# OOM으로 죽은 경우 (PokéClip YOLO 분석에서 빈번)
ty@MacBook-Pro pokeclip % python3 huge_model.py
Killed
ty@MacBook-Pro pokeclip % echo $?
137                                        ← OOM killer 시그니처
```

**137은 PokéClip 분석 파이프라인에서 *반드시 외우는* 숫자**다. 화면엔 `Killed` 한 단어만 남고 stderr에도 친절한 설명이 없다. 그런데 exit code 137을 보는 순간 "메모리 부족으로 OS가 강제 종료시켰다"가 확정된다. EC2 GPU 인스턴스 RAM이 모자랐다는 진단이 1초 안에 나온다.

### `&&` / `||` = exit code 분기

exit code를 *사람이* 매번 `$?`로 확인하기엔 번거롭다. 셸은 두 명령을 잇는 짧은 문법 두 개로 자동 분기를 제공한다.

| 문법 | 동작 |
|---|---|
| `cmd1 && cmd2` | cmd1이 *성공*(exit 0)했을 때만 cmd2 실행 |
| <code>cmd1 &#124;&#124; cmd2</code> | cmd1이 *실패*(exit ≠ 0)했을 때만 cmd2 실행 |
| `cmd1 ; cmd2` | 결과 무관하게 둘 다 실행 |

```bash
# (1) 빌드 성공 시에만 테스트 실행
ty@MacBook-Pro pokeclip % python3 build.py && python3 test.py

# (2) 디렉터리가 없으면 만들고 들어감
ty@MacBook-Pro pokeclip % cd /tmp/pokeclip 2>/dev/null || mkdir -p /tmp/pokeclip && cd /tmp/pokeclip

# (3) Docker 컨테이너 실행 실패 시 즉시 알림
ty@MacBook-Pro pokeclip % docker run myanalyzer || echo "분석 실패 — 슬랙 알림"

# (4) FFmpeg 트랜스코딩 후 결과 검증 한 줄에
ty@MacBook-Pro pokeclip % ffmpeg -i in.mp4 out.mp4 2> err.log && echo "성공" || echo "실패: err.log 확인"
```

[설명] `&&`와 `||`는 셸 스크립트의 *조건 분기*를 한 줄로 압축하는 패턴. PokéClip 분석 파이프라인의 9단계 중 어느 한 단계가 실패하면 다음 단계가 *조용히 잘못된 데이터로 실행*되는 사고를 막는 첫 도구.

### Python traceback — *밑에서 위로* 읽는다

셸 에러 다음으로 자주 만나는 게 Python traceback. 30~50줄짜리 무더기를 보면 어디부터 읽어야 할지 막막하다. 규칙 한 줄로 끝.

> ***밑에서 위로* 읽고, 맨 아래 한 줄이 진짜 원인.**

전형적인 traceback의 구조를 시각화하면 이렇다.

```
Traceback (most recent call last):                            ← 1) 시작 안내
  File "main.py", line 42, in <module>                        ← 2) 최초 호출 (오래된 프레임)
    analyze_video(path)
  File "main.py", line 17, in analyze_video                   ← 3) 다음 호출
    frames = extract_frames(path)
  File "ffmpeg_wrapper.py", line 88, in extract_frames        ← 4) 또 다음 호출
    return _decode(stream)
  File "ffmpeg_wrapper.py", line 105, in _decode              ← 5) 가장 최근 호출 (★ 진짜 실패 지점)
    raise RuntimeError(f"frame decode failed: {err}")
RuntimeError: frame decode failed: moov atom not found        ← 6) 에러 종류 + 메시지 (★★ 한 줄 답)
```

읽는 순서를 다시 그림으로.

```
[맨 위]  Traceback ...
         File "main.py", line 42         ┐
           analyze_video(path)           │ ← 호출 스택 (위쪽일수록 오래된 호출)
         File "main.py", line 17         │
           ...                           │ 사람은 *밑에서 위로* 거슬러 올라간다
         File "ffmpeg_wrapper.py", 105   ┘
           raise RuntimeError(...)
         RuntimeError: moov atom...      ← ★ 진짜 원인 = 맨 아래 한 줄
[맨 밑]
```

핵심 두 가지.

1. **맨 아래 한 줄 = 에러 종류 + 메시지**. 이게 *답*이다. 위는 모두 *어쩌다 거기까지 갔는지의 발자취*.
2. **밑에서 두 번째 `File ...` 줄 = 실제로 터진 코드 위치**. 어느 파일 몇 번 줄에서 터졌는지를 알려준다.

AI에 traceback을 던질 때 가장 효과 좋은 패턴은 *마지막 5~7줄만 잘라서* 주는 것. 위쪽 호출 스택이 길어도 진짜 원인은 항상 아래쪽에 있다. 이 강의 후반 시나리오 2에서 30줄 traceback을 7줄로 압축하는 예시를 다룬다.

### 셸 에러 메시지 5종 분류

`command not found`만 5종이 아니다. 셸에서 보게 되는 에러 메시지를 5가지로 묶어 두면 *원인 분류가 즉시*가 된다.

| 종류 | 메시지 예 | 진짜 원인 | 어디 채널 | exit code |
|---|---|---|---|---|
| (1) **command not found** | `zsh: command not found: ffmpeg` | PATH / 미설치 / 타이포 / 캐시 (A-1-2의 4종) | stderr | 127 |
| (2) **permission denied** | `bash: ./run.sh: Permission denied` | 실행 권한(`x`) 없음 / 파일 읽기 권한 없음 | stderr | 126 또는 1 |
| (3) **no such file or directory** | `cat: foo.txt: No such file or directory` | 경로 오타 / 현재 디렉터리 잘못 / 상대경로 착각 | stderr | 1 또는 2 |
| (4) **syntax error** | `bash: syntax error near unexpected token` | 셸 문법 오류 (따옴표 미스매치, 중괄호 등) | stderr | 2 |
| (5) **프로그램 자체 에러** | `[error] moov atom not found` / `RuntimeError: ...` | 프로그램 내부 로직이 던진 도메인 에러 | stderr (대개) | 프로그램이 정함 |

분류 결정 트리는 단순하다.

```
에러 메시지를 본다
  ├─ "command not found" → (1) → A-1-2 PATH 4종 분류로
  ├─ "permission denied" → (2) → ls -l로 권한 확인 → chmod
  ├─ "no such file..."   → (3) → pwd로 현재 위치 확인 → 경로 점검
  ├─ "syntax error"      → (4) → 따옴표/괄호 점검 (보통 본인이 친 줄)
  └─ 그 외 (영문 + 도메인 단어) → (5) → 프로그램 도메인 지식 필요 → AI에 발췌 전달
```

(1)~(4)는 *셸*이 던지는 메시지이므로 답이 정형화돼 있다. (5)만이 *프로그램*이 던지는 도메인 에러이고, 이때 AI 도움이 가장 크다. 즉 AI에게 컨텍스트를 정성껏 잘라서 줘야 하는 자리는 거의 항상 (5)다.

### AI에 에러 붙여넣을 때 같이 줘야 할 4가지 — 컨텍스트 체크리스트

이번 강의의 결론 영역. AI에 에러를 던질 때 *함께 줘야 효과가 폭증하는 정보 4가지*를 체크리스트로 박는다.

| 항목 | 왜 필요한가 | 어떻게 얻는가 |
|---|---|---|
| **1. 명령어 전문** | 어떤 입력에 대한 에러인지 모르면 추측밖에 못 함 | 친 명령을 그대로 복사 |
| **2. 출력의 마지막 N줄** | 진짜 원인은 끝에 있음. 100줄을 다 주면 노이즈 | `tail -n 20 error.log` 또는 화면 끝 5~20줄 |
| **3. exit code** | `Killed` 같은 짧은 출력은 코드가 진짜 정보 | `echo $?` 결과 |
| **4. 환경** | OS / 셸 / 언어 버전 / 컨테이너 여부 | `uname -a`, `python3 --version`, "macOS M1" 한 줄 |

체크리스트를 한 줄짜리 명령으로 정리.

```bash
# 한 줄에 전부 잡기
ty@MacBook-Pro pokeclip % python3 yolo_infer.py video.mp4 2> err.log; \
  echo "exit_code=$?" >> err.log; \
  echo "env: $(uname -sm) python=$(python3 --version)" >> err.log; \
  tail -n 20 err.log
```

[설명] `\` 는 한 줄짜리 명령을 시각적으로 여러 줄에 걸쳐 쓰게 해주는 줄바꿈 이스케이프. 세미콜론(`;`)은 결과 무관 순차 실행.

AI 프롬프트로 쓸 때의 전형 형태는 이렇다.

```
[명령] python3 yolo_infer.py video.mp4
[exit code] 137
[환경] macOS Darwin M1, Python 3.12.4
[stderr 마지막 8줄]
  Loading model weights from yolov8x.pt
  Model loaded: 68.2M parameters
  Processing frame 142/3600...
  Killed
```

이 4가지가 있으면 AI는 "exit 137 + Killed → OOM. Apple Silicon이라 통합 메모리. yolov8x는 무겁다 → yolov8s로 다운 또는 배치 크기 줄여라"까지 *한 번에* 도달한다. 4가지 없이 "왜 안 돼?"만 던지면 5번 왕복.

### 트레이드오프 — 복붙 전체 vs 발췌 N줄

"전체를 다 줘야 안전한 거 아닌가?" 합리적 우려다. 그런데 실제 측정해 보면 결과가 정반대다.

| 방식 | 토큰 비용 | AI 정확도 | 왕복 횟수 | 사람의 사전 준비 |
|---|---|---|---|---|
| **전체 복붙 (100~500줄)** | 높음 | 중간 (노이즈 묻힘) | 3~5회 | 거의 0 |
| **마지막 20줄 + 4가지 컨텍스트** | 낮음 | 높음 | 1~2회 | 30초 |

핵심은 **AI의 어텐션은 *고르게* 분배된다**는 사실이다. 100줄을 주면 진짜 원인 1줄과 무관한 99줄이 *같은 무게*로 읽힌다. 99줄에 우연히 다른 패턴 단어("warning", "deprecated")가 있으면 AI는 그쪽으로 끌려간다.

발췌의 원칙 3가지.

1. **stderr의 마지막 N줄**을 우선 (보통 N=10~30). 진짜 원인은 거의 항상 끝에.
2. **traceback은 Traceback부터 마지막 에러 줄까지** 그대로 (잘라먹지 말 것). 5~15줄 정도.
3. **로그 중간에 `[error]` `Error:` `Exception` `FATAL` 같은 키워드** 줄이 있으면 그 줄 ± 3줄을 추가.

발췌하지 *말아야* 할 때도 있다. 진짜 *처음* 디버깅하는 도메인이어서 어떤 줄이 의미 있는지 감이 없을 때는 차라리 전체를 주고 AI에게 "마지막 30줄 기준으로 원인 추정해줘"로 부탁하는 게 빠르다. 즉 *도메인 지식과 발췌 능력은 비례*한다.

[exit code] 1
[환경] macOS M1, ffmpeg 6.1.1, 입력은 OBS SRT+MPEG-TS 녹화 파일

**시나리오 3 — 셸 스크립트가 *조용히* 실패. exit code 체크 습관으로 발견**

PokéClip 분석 파이프라인 첫 단계: SRT 수신 → 디멀티플렉싱 → 트랙별 파일 저장. 한 줄짜리 셸 스크립트로 묶었다.

```bash
#!/bin/bash
# extract_tracks.sh — 받은 ts 파일을 트랙별 wav로 분리
ffmpeg -i $1 -map 0:a:0 mic.wav -map 0:a:1 game.wav -map 0:a:5 donation.wav
python3 analyze_audio.py mic.wav game.wav donation.wav
aws s3 cp results.json s3://pokeclip-analysis/$(date +%F)/
```

다음날 결과를 확인하니 S3에 파일이 멀쩡히 올라와 있다. 그런데 *분석 결과가 비어 있다*. 화면에는 멀쩡해 보였다. 어디서 잘못된 건가.

진단의 첫 도구는 exit code다.

```bash
ty@MacBook-Pro pokeclip % ./extract_tracks.sh stream.ts
[FFmpeg 출력]
[Python 출력]
upload: ./results.json to s3://pokeclip-analysis/2026-06-22/
ty@MacBook-Pro pokeclip % echo $?
0                                          ← 마지막 명령(aws s3 cp)은 성공
```

스크립트 전체가 0으로 끝났다고 *모든 단계가 성공*했다는 뜻이 아니다. 셸 스크립트는 기본적으로 한 단계가 실패해도 다음 단계로 *그냥 넘어간다*. exit code도 *마지막 명령의 것만* 반환한다.

해결 패턴 두 가지.

```bash
# (해결 A) 스크립트 맨 위에 set -e — 한 줄이라도 실패하면 즉시 종료
#!/bin/bash
set -euo pipefail                          ← 표준 셸 안전 헤더

ffmpeg -i $1 -map 0:a:0 mic.wav -map 0:a:1 game.wav -map 0:a:5 donation.wav
python3 analyze_audio.py mic.wav game.wav donation.wav
aws s3 cp results.json s3://pokeclip-analysis/$(date +%F)/

# (해결 B) && 로 명시적 연쇄
ffmpeg -i $1 -map 0:a:0 mic.wav -map 0:a:1 game.wav -map 0:a:5 donation.wav \
  && python3 analyze_audio.py mic.wav game.wav donation.wav \
  && aws s3 cp results.json s3://pokeclip-analysis/$(date +%F)/
```

[설명] `set -e`는 "어느 명령이라도 exit ≠ 0이면 즉시 스크립트 종료". `set -u`는 "정의되지 않은 변수 쓰면 에러". `set -o pipefail`은 "파이프(`|`) 중간에서 실패해도 잡음". 셋을 묶은 `set -euo pipefail`이 셸 스크립트의 *안전 표준 헤더*다.

이 한 줄을 안 박은 스크립트가 운영에서 *조용히 잘못된 데이터를 매일 만들어내는* 사고가 가장 무섭다. exit code 습관 = 사고 조기 발견.

### PokéClip 적용 — YOLO 분석 컨테이너 OOM에서 stderr만 잡아내기

이번 강의의 PokéClip 적용은 한 자리에 집중한다: **YOLO 영상 분석 스크립트의 stdout/stderr 분리**.

PokéClip의 영상 분석 단계는 다음 한 줄로 끝난다.

```python
# yolo_infer.py — 끝부분
print(json.dumps({"kills": kills, "deaths": deaths, "fights": fights}))
```

이 한 줄로 stdout에 분석 결과 JSON을 *흘려보낸다*. 다음 단계 스크립트가 *데이터로* 받는다.

```bash
# 분석 파이프라인 한 단계
ty@MacBook-Pro pokeclip % python3 yolo_infer.py video.mp4 > result.json
```

이 패턴은 깔끔하다. 그런데 YOLO 모델이 진행 로그를 *stdout*에 찍거나 `print(f"frame {i}")` 같은 디버그 print가 *stderr*가 아닌 stdout으로 흘러들어가는 순간, `result.json` 파일이 *깨진다*.

```bash
# (사고 케이스) yolo 라이브러리가 stdout에 진행 로그를 찍어 버림
ty@MacBook-Pro pokeclip % python3 yolo_infer.py video.mp4 > result.json
ty@MacBook-Pro pokeclip % cat result.json
Loading model weights...                   ← JSON 아님!
Processing frame 1/3600
Processing frame 2/3600
...
{"kills": 12, "deaths": 4, "fights": 8}    ← 진짜 결과는 맨 끝 한 줄
```

다음 단계가 `json.loads(open("result.json").read())`로 읽으면 첫 줄부터 *JSON 파싱 에러*. 분석 파이프라인이 멈춘다.

해결은 두 갈래다.

```bash
# 해결 A — 진행 로그를 stderr로 보내도록 yolo_infer.py 수정
import sys
print(f"frame {i}", file=sys.stderr)       ← stderr로 명시
print(json.dumps(result))                  ← stdout은 결과만

# 해결 B — 셸에서 stdout과 stderr를 분리 저장
ty@MacBook-Pro pokeclip % python3 yolo_infer.py video.mp4 > result.json 2> infer.log
```

OOM으로 컨테이너가 죽을 때도 같은 원리.

```bash
# 컨테이너에서 분석 실행
[ec2-user@ip-10-0-1-42 ~]$ docker run pokeclip/yolo python3 yolo_infer.py video.mp4 \
  > result.json 2> infer.log
[ec2-user@ip-10-0-1-42 ~]$ echo $?
137                                        ← OOM
[ec2-user@ip-10-0-1-42 ~]$ cat result.json
                                            ← 빈 파일 (정상 — 결과 없으니)
[ec2-user@ip-10-0-1-42 ~]$ tail -n 10 infer.log
Loading yolov8x.pt (68.2M params)
Allocating GPU memory: 4.2GB
Processing frame 142/3600
                                            ← Killed 메시지조차 stderr 안 남는 경우도 있음
```

exit code 137 + stderr 마지막 10줄 + 환경(EC2 GPU 인스턴스 메모리 사양)을 묶어 AI에 던지면 "yolov8x → yolov8s 다운, 배치 크기 감소, 또는 더 큰 GPU 인스턴스" 답이 1번 왕복으로 나온다.

핵심은 *stdout과 stderr가 처음부터 분리돼 있다*는 점. 분리되지 않은 파이프라인은 사고가 났을 때 결과 파일이 오염되고, 사고 원인은 또 다른 어딘가에서 *추가 사고*로 발견된다.

### 이번 강의 핵심 3줄

1. **셸 출력은 stdout / stderr 두 채널**이고, `>` `2>` `2>&1`로 분리한다 — 분석 결과는 stdout, 진행 로그·에러는 stderr가 표준.
2. **exit code 0은 성공, 1~255는 실패의 종류**이고, `137`(OOM) `127`(not found) 같은 시그니처는 화면 메시지보다 정확한 단서다 — `&&` / `||`로 단계 연쇄 시 *조용한 실패*를 막는다.
3. **Python traceback은 *밑에서 위로*** 읽고, 맨 아래 한 줄이 답 — AI에 던질 때는 *명령 + 마지막 N줄 + exit code + 환경* 4가지를 같이, 전체 복붙은 1~2번 왕복을 3~5번으로 늘린다.
