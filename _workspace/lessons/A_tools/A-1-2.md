## 레벨 A-1 / 2강: 환경 변수와 PATH — "command not found"의 진짜 원인

> 명령은 실패하는 게 아니라 *못 찾는다*. 모든 셸 실수의 70%는 PATH 한 변수에서 나온다.

---

### 왜 `command not found`가 가장 자주 보이는 에러인가

1강에서 검은 창의 4요소를 읽는 법을 익혔다. 이제 그 창에 명령을 친다. 그런데 가장 흔한 첫 사고가 이거다.

```bash
ty@MacBook-Pro pokeclip % ffmpeg -i input.mp4 output.mp4
zsh: command not found: ffmpeg
```

분명히 `brew install ffmpeg`로 설치했는데. 어제까진 됐는데. 다른 사람 노트북에선 되는데. 같은 명령이 왜 여기서는 안 되는가.

이 에러를 읽는 순간 대부분의 입문자는 *명령어를 다시 친다*. 오타를 의심한다. `ffmpeg` → `FFmpeg` → `ffmpeg-i` 같은 헛수고가 시작된다. 사실 셸이 던진 메시지는 정확히 "**못 찾았다(not found)**"이지 "**틀렸다(invalid)**"가 아니다. 글자 그대로다.

`command not found`는 거의 항상 **PATH**라는 환경 변수 하나의 문제다. AI에게 명령을 시키고 결과를 검증하는 시대에 이 한 변수만 정확히 이해해도 디버깅의 절반이 끝난다. PokéClip 운영에서 매일 두 번씩 마주칠 에러를 이 강의에서 영구히 정리한다.

---

### 환경 변수란 — 프로세스가 들고 다니는 *명함첩*

환경 변수(environment variable)는 어렵게 부르지 말고 **프로세스마다 들고 다니는 키-값 사전**이라고 생각하면 된다. 명함첩 비유가 가장 정확하다.

- 셸(zsh)이 켜진다 → 자기 명함첩을 한 벌 들고 시작
- 셸이 `python3 script.py`를 실행한다 → 자기 명함첩을 *복사해서* 자식 프로세스(python3)에 넘김
- python3는 그 명함첩을 보고 "OpenAI API 키가 뭐였더라" 같은 정보를 꺼냄

명함첩은 단순한 문자열 키 → 문자열 값의 사전이다. 자료형도 한 가지, 문자열뿐이다.

```bash
# 환경 변수 하나 추가해 보기
ty@MacBook-Pro pokeclip % MYNAME="ty"
ty@MacBook-Pro pokeclip % echo $MYNAME
ty
```

`$` 접두어는 "이 변수의 *값*을 꺼내라"는 지시. `MYNAME`이 키, `"ty"`가 값.

지금까지 친 모든 명령(`whoami`, `mkdir` 등)은 사실 *환경 변수 한 개*인 PATH의 도움을 받아 실행됐다. 이 사실을 본격적으로 들여다본다.

---

### 환경 변수 직접 보기 — `env` / `printenv` / `echo`

지금 내 셸이 들고 있는 명함첩 전체를 보고 싶다.

```bash
# 모든 환경 변수 출력
ty@MacBook-Pro pokeclip % env
SHELL=/bin/zsh
USER=ty
HOME=/Users/ty
PATH=/opt/homebrew/bin:/opt/homebrew/sbin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin
LANG=ko_KR.UTF-8
TERM=xterm-256color
...
```

`env`는 셸이 가진 환경 변수 전부를 키=값 형태로 쏟아낸다. EC2 기본 셸이면 30~60개, 로컬 macOS면 40~80개 정도가 보통.

특정 변수 하나만 보고 싶다면 두 가지 방법이 있다.

```bash
# 방법 1: printenv (env의 사촌, 변수 이름 지정 가능)
ty@MacBook-Pro pokeclip % printenv HOME
/Users/ty

# 방법 2: echo $변수명 (가장 자주 씀)
ty@MacBook-Pro pokeclip % echo $HOME
/Users/ty
```

둘 다 결과는 같다. 차이는 사용 위치에 있다. `printenv`는 셸 안에서 직접 쓸 때, `echo $VAR`는 스크립트나 다른 명령 안에 끼워 넣을 때 자연스럽다.

| 명령 | 용도 | 변수 없을 때 동작 |
|---|---|---|
| `env` | 모든 환경 변수 출력 | 해당 없음 |
| `printenv VAR` | 특정 변수 출력 | exit code 1, 출력 없음 |
| `echo $VAR` | 변수 값을 다른 명령에 끼워 넣기 | 빈 줄 출력 (`echo`는 성공) |

미묘하게 중요한 차이는 마지막 줄이다. `printenv NOPE`는 *조용한 실패*인데 `echo $NOPE`는 *조용한 빈 값*이다. A-1-3(에러 메시지)에서 이 차이가 다시 등장한다.

### PATH — 셸이 명령을 찾는 *주소록*

이제 강의의 본진. **PATH**는 "셸이 명령어를 찾을 디렉터리 목록"을 들고 있는 환경 변수다.

```bash
ty@MacBook-Pro pokeclip % echo $PATH
/opt/homebrew/bin:/opt/homebrew/sbin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin
```

콜론(`:`) 하나로 디렉터리 여러 개를 이어 붙인 한 줄 문자열. 위 예시는 7개 디렉터리가 들어 있다. 보기 좋게 줄바꾸면 이렇다.

```
1. /opt/homebrew/bin       ← Apple Silicon Homebrew 설치 명령들 (brew install로 깐 것)
2. /opt/homebrew/sbin      ← Homebrew 관리자용
3. /usr/local/bin          ← Intel Mac Homebrew 잔재 + 수동 설치
4. /usr/bin                ← macOS 기본 명령 (system Python, git 등)
5. /bin                    ← 가장 기본적인 명령 (ls, cp, mv 등)
6. /usr/sbin               ← 시스템 관리 명령
7. /sbin                   ← 부팅 시 필요한 관리 명령
```

PokéClip 학습용 MacBook 기준 7개. 일반적인 로컬 환경은 5~12개, 셸 셋업이 화려할수록 20개도 본다. EC2 Amazon Linux 기본은 4~6개로 짧다 — 이 길이 차이가 시나리오 3에서 큰일을 낸다.

---

### 셸이 명령을 실행하는 알고리즘 — *순서대로* 뒤진다

`python3 script.py`를 친다. 셸이 내부에서 하는 일을 풀어 적으면 이렇다.

```
입력: python3 script.py

1. "python3"가 셸 내장 명령인가? 아님 (cd, echo 등이 내장)
2. "python3"가 셸 함수인가? 아님
3. "python3"가 alias인가? 아님
4. PATH를 콜론으로 쪼개 디렉터리 7개를 얻음
5. 1번 디렉터리부터 *순서대로* "python3" 파일이 있는지 확인:

   /opt/homebrew/bin/python3      ← 있음! 멈춤. 이걸 실행.

6. 못 찾았으면: command not found
```

핵심은 두 가지다.

1. **순서대로** 뒤진다 (왼쪽 → 오른쪽)
2. **처음 찾은 것**을 실행하고 *멈춘다*

이 두 규칙이 모든 PATH 사고의 원인이자 해법이다. 같은 이름의 명령이 디렉터리 여러 곳에 있을 수 있다. 예를 들어 macOS는 시스템 Python을 `/usr/bin/python3`로 가지고 있고, Homebrew는 자기 Python을 `/opt/homebrew/bin/python3`로 깐다. PATH 순서에 따라 *어느 쪽이 잡히는가*가 달라진다.

```bash
# 시연 — PATH 순서를 바꿨을 때 잡히는 python3가 달라짐

# 원래 순서: Homebrew가 앞에 있음
ty@MacBook-Pro pokeclip % echo $PATH
/opt/homebrew/bin:/usr/bin:...
ty@MacBook-Pro pokeclip % which python3
/opt/homebrew/bin/python3        ← Homebrew Python 잡힘 (Python 3.12)

# 한 줄에 한정해서 PATH 순서를 바꿔 봄 (다른 셸에는 영향 X)
ty@MacBook-Pro pokeclip % PATH=/usr/bin:/opt/homebrew/bin which python3
/usr/bin/python3                 ← 시스템 Python 잡힘 (Python 3.9, 더 오래됨)
```

같은 명령, 같은 셸, 같은 시점인데 PATH 순서 하나로 잡히는 바이너리가 바뀐다. 이게 입문자가 "내 컴에서만 안 됨"의 진짜 원인.

### `which` / `type` / `command -v` — 누가 진짜 잡히는가

PATH 검색 알고리즘을 *내가 손으로 안 뒤져도* 셸이 대신 알려주는 명령 3개가 있다. 셋 다 비슷하지만 다르다.

```bash
# 1. which — PATH에서 첫 번째로 찾은 실행 파일 경로 출력
ty@MacBook-Pro pokeclip % which python3
/opt/homebrew/bin/python3

# 2. which -a — *모든* 매칭 경로를 PATH 순서로 출력 (★ 가장 유용)
ty@MacBook-Pro pokeclip % which -a python3
/opt/homebrew/bin/python3
/usr/bin/python3

# 3. type — 내장 명령/함수/alias/외부 명령을 구분해서 알려줌 (★★ 가장 강력)
ty@MacBook-Pro pokeclip % type python3
python3 is /opt/homebrew/bin/python3

ty@MacBook-Pro pokeclip % type cd
cd is a shell builtin              ← cd는 외부 명령이 아니라 셸 내장

ty@MacBook-Pro pokeclip % type ll
ll is an alias for ls -alh         ← ll은 alias

# 4. command -v — type의 간단 버전 (스크립트에서 if문에 자주 씀)
ty@MacBook-Pro pokeclip % command -v python3
/opt/homebrew/bin/python3
```

세 명령의 차이를 표로 정리.

| 명령 | 정체 | 출력 | 추천 사용처 |
|---|---|---|---|
| `which` | 외부 프로그램 | 첫 매칭 경로 한 줄 | 빠른 확인 |
| `which -a` | 외부 프로그램 | 모든 매칭 경로 | *중복 의심될 때 필수* |
| `type` | 셸 내장 | 내장/함수/alias/외부 구분 | 가장 정확한 디버깅 |
| `command -v` | 셸 내장 | 경로 한 줄 (없으면 exit 1) | 스크립트 if문 |

`which`는 외부 프로그램이라 셸 내장 명령(`cd`, `echo` 등)을 못 본다. `type`은 셸이 직접 답하므로 내장까지 다 본다. 디버깅에서 정답이 안 보일 땐 거의 항상 `type`이 `which`보다 낫다.

**`which -a`가 진짜 중요한 이유**는 다음 시연 한 컷으로 끝난다.

```bash
# pyenv 깔린 환경에서
ty@MacBook-Pro pokeclip % which -a python3
/Users/ty/.pyenv/shims/python3        ← 1순위 (pyenv shim)
/opt/homebrew/bin/python3              ← 2순위 (Homebrew)
/usr/bin/python3                       ← 3순위 (시스템)
```

세 개의 python3가 한 시스템 안에 공존하고 있다. `python3`를 치면 **첫 번째인 pyenv가 잡힌다**. 이걸 모르면 "`pip install`했는데 `import`가 안 됨" 같은 사고의 진짜 원인을 평생 못 잡는다.

### "command not found"의 4대 원인 — 분류표

이제 `command not found`를 만났을 때 *원인을 4종으로 분류*하는 표를 머리에 박아두자.

| 원인 | 어떻게 확인 | 해결 방향 |
|---|---|---|
| **(1) 설치 자체가 안 됨** | `brew list \| grep ffmpeg` 또는 패키지 매니저로 확인 | 설치 (`brew install`, `apt install`, `pip install`) |
| **(2) 설치는 됐는데 PATH에 없음** | 실제 파일은 있는데(`ls /opt/homebrew/bin/ffmpeg`) PATH에 그 디렉터리가 없음 | PATH에 디렉터리 추가 (`export PATH=...:$PATH`) |
| **(3) PATH 순서가 잘못돼서 *다른 게* 잡힘** | `which -a` 결과가 의도와 다름 | PATH 순서 변경 (원하는 디렉터리를 앞으로) |
| **(4) 셸 캐시(hash) 오염** | `which`는 잘 가리키는데 셸이 옛 위치 캐시 / 또는 `command not found` 잘못 띄움 | `hash -r`로 캐시 비움 |

각 원인을 구분하는 진단 절차는 5분 안에 끝난다.

```bash
# 1단계: 진짜 안 깔린 건지 확인
ty@MacBook-Pro pokeclip % brew list | grep ffmpeg
ffmpeg                                  ← 깔려 있음 → (1) 아님

# 2단계: 실제 파일 위치 확인
ty@MacBook-Pro pokeclip % ls /opt/homebrew/bin/ffmpeg
/opt/homebrew/bin/ffmpeg                ← 파일은 있음

# 3단계: PATH에 그 디렉터리가 있는지
ty@MacBook-Pro pokeclip % echo $PATH | tr ':' '\n' | grep homebrew
/opt/homebrew/bin
/opt/homebrew/sbin                      ← 있음 → (2) 아님

# 4단계: which -a로 다른 게 잡히는지
ty@MacBook-Pro pokeclip % which -a ffmpeg
/opt/homebrew/bin/ffmpeg                ← 하나뿐 → (3) 아님

# 5단계: 셸 캐시 비우고 재시도
ty@MacBook-Pro pokeclip % hash -r
ty@MacBook-Pro pokeclip % ffmpeg -version
ffmpeg version 6.1.1 ...                ← (4)였음. 해결.
```

(4) 셸 캐시는 자주 등장하지 않지만 *가장 알기 어려운 원인*이다. 셸은 한 번 찾은 명령의 경로를 캐싱해서 다음 호출을 빠르게 한다. 그런데 `brew install`로 새로 깔거나 `brew uninstall`로 지우면 캐시가 *옛 정보*를 들고 있어 사고가 난다. `hash -r` (또는 zsh의 `rehash`) 한 줄이면 해결.

[설명] `tr ':' '\n'`은 콜론을 줄바꿈으로 바꿔서 PATH 디렉터리를 줄 단위로 보기 좋게 만드는 트릭. 자주 쓴다.

### PATH 순서 변경의 결과 차이 — 앞에 vs 뒤에

PATH 사고의 가장 흔한 원인 (3)을 해결하는 방법은 PATH에 디렉터리를 *어디에* 끼워 넣느냐다. 이걸 망치면 멀쩡한 도구가 갑자기 망가진다.

두 줄을 비교해 보자.

```bash
# (A) 디렉터리를 PATH 앞에 추가 — 우선순위 1순위
export PATH=/Users/ty/.pyenv/shims:$PATH

# (B) 디렉터리를 PATH 뒤에 추가 — 가장 마지막에 검색됨
export PATH=$PATH:/Users/ty/.pyenv/shims
```

`$PATH`의 위치 차이 하나로 우선순위가 천지차이다.

```bash
# 시연 1: 앞에 추가
ty@MacBook-Pro pokeclip % export PATH=/Users/ty/.pyenv/shims:$PATH
ty@MacBook-Pro pokeclip % which python3
/Users/ty/.pyenv/shims/python3          ← pyenv가 1순위
ty@MacBook-Pro pokeclip % python3 --version
Python 3.12.4                            ← pyenv가 관리하는 버전

# 시연 2: (같은 셸 그대로) 뒤에 추가했다면?
ty@MacBook-Pro pokeclip % export PATH=$PATH:/Users/ty/.pyenv/shims
ty@MacBook-Pro pokeclip % which python3
/opt/homebrew/bin/python3                ← Homebrew가 여전히 1순위
ty@MacBook-Pro pokeclip % python3 --version
Python 3.12.7                            ← Homebrew가 관리하는 버전 (의도와 다름)
```

규칙 한 줄로 외운다.

> ***내가 우선*이면 앞에, *기본을 살리고 보조*면 뒤에.**

PokéClip에서 pyenv로 Python 버전 관리할 거면 항상 *앞에*. `pip install --user`로 깐 도구의 `~/.local/bin`도 일반적으로 *앞에*. 회사 표준 셋업 위에 내 도구를 *살짝 얹는* 상황이면 *뒤에*.

| 패턴 | 효과 | 추천 시점 |
|---|---|---|
| `export PATH=새디렉터리:$PATH` | 새 디렉터리가 *최우선* | 버전 관리자(pyenv, nvm), 내 도구 우선화 |
| `export PATH=$PATH:새디렉터리` | 새 디렉터리가 *최후순위* | 기본 환경 유지하면서 보조 도구 추가 |

### `export VAR=value` vs `VAR=value command` — 일회용 변수의 정체

환경 변수를 *오래 살리고* 자식 프로세스에 넘기려면 `export`가 필요하다. 반면 *지금 이 한 줄짜리 명령에만* 적용하고 싶을 때가 있다.

```bash
# 방식 1: export — 셸 세션 전체에 적용, 자식 프로세스에 상속
ty@MacBook-Pro pokeclip % export OPENAI_API_KEY="sk-abc123"
ty@MacBook-Pro pokeclip % python3 -c "import os; print(os.environ['OPENAI_API_KEY'])"
sk-abc123                                ← 자식 python3가 변수 받음

ty@MacBook-Pro pokeclip % python3 -c "import os; print(os.environ['OPENAI_API_KEY'])"
sk-abc123                                ← 셸이 같은 동안 계속 적용

# 방식 2: 한 줄 한정 — 그 명령에만 적용, 다음 줄엔 사라짐
ty@MacBook-Pro pokeclip % OPENAI_API_KEY="sk-temp" python3 -c "import os; print(os.environ['OPENAI_API_KEY'])"
sk-temp                                  ← 그 한 명령에만 적용

ty@MacBook-Pro pokeclip % python3 -c "import os; print(os.environ['OPENAI_API_KEY'])"
sk-abc123                                ← 다음 줄은 export된 옛 값으로 돌아감
```

한 줄짜리 방식의 핵심은 다음 두 가지다.

1. *지금 이 명령*만 그 변수를 봄
2. 다음 명령엔 영향 없음

이 패턴은 **테스트 / 디버깅 / CI** 자리에서 매일 쓴다. PokéClip 분석 스크립트를 다른 모델로 한 번만 돌려 보고 싶을 때 `OPENAI_MODEL=gpt-4o python3 analyze.py`처럼.

`export`의 정체는 "이 변수를 자식 프로세스에 상속시켜라"라는 표시. `export` 없이 그냥 `MYVAR=value`만 쳐도 *현재 셸 안에서는* 보이지만 자식 프로세스로는 못 넘어간다.

```bash
# export 없는 변수의 함정
ty@MacBook-Pro pokeclip % MYVAR="hello"
ty@MacBook-Pro pokeclip % echo $MYVAR
hello                                    ← 현재 셸에선 보임

ty@MacBook-Pro pokeclip % python3 -c "import os; print(os.environ.get('MYVAR'))"
None                                     ← 자식 python3엔 안 넘어감

ty@MacBook-Pro pokeclip % export MYVAR
ty@MacBook-Pro pokeclip % python3 -c "import os; print(os.environ.get('MYVAR'))"
hello                                    ← export 한 뒤엔 자식이 받음
```

이 차이 때문에 "셸에선 `echo $KEY`로 잘 나오는데 Python 스크립트가 못 찾는다"는 사고가 끊임없이 발생한다. 답은 `export` 한 단어.

### 자식 프로세스 상속 — `subshell`로 직관 잡기

환경 변수의 자식 프로세스 상속은 *복사* 모델이다. 부모가 자식에게 명함첩을 *복사해서* 준다. 자식이 명함첩을 수정해도 부모의 명함첩은 그대로다.

```bash
# 부모 셸에서 변수 설정
ty@MacBook-Pro pokeclip % export PROJECT="pokeclip"

# 자식 셸을 띄움 (subshell — 셸 안에 셸)
ty@MacBook-Pro pokeclip % zsh
ty@MacBook-Pro pokeclip % echo $PROJECT
pokeclip                                 ← 자식이 명함첩 상속받음

# 자식 셸에서 값을 바꿈
ty@MacBook-Pro pokeclip % export PROJECT="other"
ty@MacBook-Pro pokeclip % echo $PROJECT
other

# 자식 셸 빠져나가서 부모로 복귀
ty@MacBook-Pro pokeclip % exit
ty@MacBook-Pro pokeclip % echo $PROJECT
pokeclip                                 ← 부모는 영향 안 받음
```

| 동작 | 부모 변수 | 자식 변수 |
|---|---|---|
| 부모가 `export FOO=bar` | bar | (자식 띄울 때) bar |
| 자식이 `export FOO=zzz` | bar (변함 없음) | zzz |
| 자식이 종료 | bar | (소멸) |

이 그림이 머리에 박히면 다음 사실들이 자연스럽게 따라온다.

- **스크립트 안에서 `export`해도 그 스크립트가 끝나면 부모 셸엔 안 남는다** — 그래서 `.zshrc` 같은 *셸 초기화 파일*에 박아야 한다 (A-1-4)
- **Docker 컨테이너의 환경 변수는 호스트의 환경 변수와 완전 별개** — 컨테이너 띄울 때 명시적으로 넘겨야 한다
- **EC2에 SSH 들어가면 새 셸이 시작되므로 로컬 환경 변수는 그쪽에 없다** — 서버에 별도로 설정해야 한다

### 트레이드오프 — PATH를 일시적으로 vs 영구적으로

PATH를 바꾸는 자리도 여러 군데다. 어디에 쓰느냐로 효과 범위와 위험도가 다르다.

| 방법 | 영향 범위 | 지속 시간 | 권장 시점 |
|---|---|---|---|
| `PATH=...:$PATH 명령` (한 줄) | 그 명령 한 번만 | 즉시 사라짐 | 일회성 테스트 |
| `export PATH=...:$PATH` (셸 안) | 현재 셸 세션 | 셸 종료까지 | 디버깅 / 임시 실험 |
| `.zshrc`/`.bashrc`에 `export PATH=...` | 새로 여는 *모든* 셸 | 영구 | 매일 쓰는 도구 (pyenv 등) |
| `/etc/paths` 또는 `/etc/profile.d/` | 시스템 *전체 사용자* | 영구 | 시스템 도구 (실무에선 거의 안 만짐) |

가장 흔한 함정은 두 번째와 세 번째의 혼동이다. 셸에서 `export PATH=...` 한 줄로 됐다고 안심하면, 새 터미널 탭을 열었을 때 *그 변경이 사라져 있음*을 보게 된다. 그 한 줄은 *현재 셸 세션 한정*이기 때문. 영구화하려면 `.zshrc`에 같은 줄을 적어 둬야 한다.

`.zshrc`와 `.env`의 차이는 A-1-4에서 본격적으로 다룬다. 지금은 "PATH는 셸 초기화 파일(.zshrc)에 넣는 게 표준"만 잡고 가면 충분.

### 실무 적용 시나리오

**시나리오 1 — `python3`이 시스템 Python으로 잡혀 pyenv 무용지물**

PokéClip 학습 첫 주. pyenv로 Python 3.12를 깔았다. 그런데 `python3 --version`을 치면 자꾸 3.9가 나온다. 시스템 Python이다.

```bash
ty@MacBook-Pro pokeclip % python3 --version
Python 3.9.6                             ← 시스템 Python (의도와 다름)

ty@MacBook-Pro pokeclip % which -a python3
/usr/bin/python3                          ← 1순위 — 시스템
/Users/ty/.pyenv/shims/python3            ← 2순위 — pyenv (얘가 와야 함)

# PATH 확인
ty@MacBook-Pro pokeclip % echo $PATH | tr ':' '\n'
/usr/bin
/bin
/usr/local/bin
/Users/ty/.pyenv/shims                    ← 한참 뒤에 있음

# 해결: pyenv shims를 PATH 앞으로
ty@MacBook-Pro pokeclip % export PATH="/Users/ty/.pyenv/shims:$PATH"
ty@MacBook-Pro pokeclip % which python3
/Users/ty/.pyenv/shims/python3            ← pyenv가 1순위
ty@MacBook-Pro pokeclip % python3 --version
Python 3.12.4                              ← 의도한 버전
```

영구화는 `.zshrc`에 같은 한 줄을 적어 두는 것. 새 터미널을 열어도 pyenv가 살아 있게 된다.

**시나리오 2 — `aws` 명령이 없다 (pip user install의 함정)**

```bash
ty@MacBook-Pro pokeclip % pip install --user awscli
[성공]

ty@MacBook-Pro pokeclip % aws --version
zsh: command not found: aws
```

설치는 성공했는데 명령은 못 찾는다. (1)이 아니라 (2)다.

```bash
# 어디 설치됐는지 직접 확인
ty@MacBook-Pro pokeclip % pip show awscli | grep Location
Location: /Users/ty/.local/lib/python3.12/site-packages

# 실행 파일은 같은 부모 폴더의 bin에
ty@MacBook-Pro pokeclip % ls ~/.local/bin/aws
/Users/ty/.local/bin/aws                 ← 있음

# 그런데 PATH에는?
ty@MacBook-Pro pokeclip % echo $PATH | grep ".local"
                                          ← 빈 출력 → 없음

# 해결: ~/.local/bin을 PATH에 추가
ty@MacBook-Pro pokeclip % export PATH="$HOME/.local/bin:$PATH"
ty@MacBook-Pro pokeclip % aws --version
aws-cli/2.15.0 Python/3.12.4 ...
```

`pip install --user`는 시스템에 안 깔고 *유저 홈 아래에* 깐다. 깔리는 디렉터리가 `~/.local/bin`인데 macOS와 일부 Linux 배포판은 이 디렉터리를 PATH에 *기본 포함 안 한다*. 그래서 깔자마자 PATH에 추가해 줘야 한다.

**시나리오 3 — EC2에선 잡히는 `node`가 Docker 컨테이너 안에선 안 잡힘**

```bash
# EC2 호스트에서
[ec2-user@ip-10-0-1-42 ~]$ which node
/home/ec2-user/.nvm/versions/node/v20.10.0/bin/node    ← nvm으로 깐 node

# Docker 컨테이너 안으로 들어가 보면
[ec2-user@ip-10-0-1-42 ~]$ docker run -it alpine sh
/ # node
sh: node: not found                        ← 컨테이너 안엔 아예 node 없음

/ # echo $PATH
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
                                            ← 5개 디렉터리 (호스트의 ~/.nvm/... 없음)
```

호스트와 컨테이너는 완전히 다른 파일시스템·다른 환경 변수·다른 PATH를 가진다. 호스트의 PATH에 `~/.nvm/versions/node/...`가 들어 있어도 컨테이너는 *자기 PATH*만 본다. 또한 자식 프로세스 상속 모델은 컨테이너 경계를 *넘지 못한다* — 호스트의 환경 변수는 명시적으로 `-e` 또는 `--env-file`로 넘기지 않으면 컨테이너에서 안 보인다.

해결은 두 갈래.

```bash
# 해결 A: node가 이미 깔린 이미지로 시작
[ec2-user@ip-10-0-1-42 ~]$ docker run -it node:20-alpine sh
/ # node --version
v20.11.0                                   ← 컨테이너 이미지에 node 포함

# 해결 B: 환경 변수 명시 전달 (PATH 자체는 컨테이너용이니 변수 사용 예시)
[ec2-user@ip-10-0-1-42 ~]$ docker run -e OPENAI_API_KEY="sk-..." -it myimage python3 analyze.py
```

호스트 PATH가 길다고 안심하지 말 것. 컨테이너의 PATH는 짧고, 그건 *의도된 것*이다.

### PokéClip 적용

PokéClip 분석 파이프라인은 *환경별 PATH 사고가 매일* 발생한다.

- pyenv 가상환경 안에서 FFmpeg를 호출하는데 `ffmpeg: command not found`가 가장 자주 등장 — pyenv의 shim PATH가 FFmpeg가 깔린 Homebrew bin을 가린 게 아니라, 가상환경 진입 직후 `hash -r`이 안 돼서 셸 캐시 (4)인 경우가 많다
- EC2 SRT Listener 서버에서 분석 GPU 인스턴스로 SSH 점프하면 *새 셸*이 시작되므로 로컬에 export한 `OPENAI_API_KEY`는 안 넘어감 — 서버의 `.env` + `python-dotenv` 패턴이 표준 (A-1-4)
- Docker 컨테이너로 Whisper/YOLO를 띄울 때 컨테이너의 PATH는 호스트와 별개이므로 컨테이너 이미지가 `python3` / `ffmpeg`를 갖고 있는지 *Dockerfile 작성 시점*에 확정해야 함

A-1-2의 PATH 모델 하나만 정확히 잡으면 이 세 자리에서 발생하는 사고의 70%가 자가 진단된다. 나머지 30%는 `.env` (A-1-4), SSH 세션 (A-1-5), 에러 메시지 읽기 (A-1-3)로 흡수.

### 다음 강의 미리보기 — A-1-3

다음 강의는 에러 메시지 읽기다. 이번 강의에서 `command not found`를 PATH 4대 원인으로 분류했는데, 그게 셸 에러 5종 분류의 *첫 번째 항목*이다. exit code · stdout · stderr · traceback의 3층 구조를 분해해 AI에 *어느 한 줄만 잘라서* 던지는 패턴까지 익힌다.

### 2강 핵심 3줄

1. **PATH는 콜론으로 이어진 디렉터리 검색 순서**이고, 셸은 *왼쪽부터 순서대로* 뒤져 *처음 찾은 것*을 실행하고 멈춘다.
2. `command not found`의 진짜 원인은 **4종 — 미설치 / PATH 누락 / 순서 오류 / 셸 캐시(`hash`) 오염** — `which -a`와 `type` 두 명령이 셋을 가른다.
3. `export`는 *자식 프로세스로의 명함첩 복사*를 의미하고, 없으면 현재 셸에서만 보인다 — 한 줄 한정은 `VAR=value command`, 영구화는 `.zshrc`.
