## 레벨 A-1 / 1강: 터미널 · 셸 · CLI · 프롬프트 — 검은 창의 4요소부터 읽기

> AI가 출력한 한 줄이 어디서 어떤 권한으로 돌고 있는지 모르면 그 다음 모든 디버깅이 추측이 된다.

---

### 왜 검은 창을 *읽는* 법부터 배우는가

AI가 명령어를 짜준 뒤 콘솔에 결과가 7줄 쏟아진다. 그중 한 줄은 `permission denied`이고 다른 한 줄은 `command not found`이다. 두 에러는 원인도 해결법도 다르다. 그런데 더 큰 문제는 *그 명령이 어느 서버의 어느 사용자로 돌고 있는지* 학습자가 모르고 있다는 것이다.

PokéClip에서 매일 일어날 장면. 로컬 MacBook에서 잘 되던 스크립트를 EC2 SRT Listener Server에 SSH로 들어가 그대로 실행한다. 결과가 다르다. 같은 명령인데. 차이는 단 하나 — 검은 창 위에 떠 있는 프롬프트가 가리키는 *환경*이 다르기 때문이다.

이 강의의 목표는 명령어 외우기가 아니라 **검은 창 한 줄을 5초 안에 해부하는 능력**이다. 사용자 / 호스트 / 경로 / 권한 — 4요소만 잡으면 그 다음의 모든 디버깅이 추측이 아니라 *판단*이 된다.

---

### GUI vs CLI — 8줄로 끝낸다

GUI(Graphical User Interface)는 마우스로 아이콘을 누르는 방식, CLI(Command-Line Interface)는 키보드로 명령을 글자로 치는 방식이다. 같은 결과를 두 방식이 모두 낸다.

백엔드 서버는 거의 항상 CLI로 다룬다. 이유는 세 가지로 충분하다.

1. 원격 서버에는 화면이 없다. 마우스를 못 꽂는다.
2. 같은 작업을 100번 자동화하려면 글자로 적어 둘 수 있어야 한다.
3. AI가 짜준 결과물도 명령 형태로 나온다 — AI 시대일수록 CLI 읽기가 중요하다.

GUI는 입문 친화적이고 CLI는 디버깅·자동화·원격 운영에 강하다. 이 강의는 여기서 GUI를 떠나 본격적으로 CLI 안으로 들어간다.

---

### 4개 용어를 엄밀하게 구분한다 — 터미널 · 콘솔 · 셸 · CLI

검은 창 한 개를 두고 사람들이 부르는 이름이 4개나 된다. 평소엔 섞어 써도 되지만, 에러를 디버깅할 땐 누가 진짜 범인인지 가려야 한다.

| 용어 | 정체 | 비유 |
|---|---|---|
| 터미널 (Terminal) | 텍스트를 입력받고 출력하는 *창* 자체 | 채팅창 UI |
| 콘솔 (Console) | 원래는 물리 키보드+모니터, 지금은 터미널과 거의 동의어 | 옛날 본체에 직접 연결된 모니터 |
| 셸 (Shell) | 입력된 명령을 해석해 OS에 전달하는 *프로그램* | 채팅 봇 |
| CLI (Command-Line Interface) | 글자로 명령을 주고받는 *방식·인터페이스 종류* | "글자로 대화한다"는 행위 자체 |

가장 중요한 분리는 **터미널 vs 셸**이다.

```
[ 터미널 창 ]  ← 너가 글자를 입력하고 보는 곳 (iTerm2 / Terminal.app / WezTerm 등)
       │
       │  키 입력 전달
       ▼
[ 셸 프로그램 ]  ← 그 글자를 명령으로 해석해 OS에 전달 (zsh / bash / fish 등)
       │
       │  시스템 호출
       ▼
[ 운영체제 (커널) ]  ← 실제로 파일 열고 프로세스 띄움
```

터미널은 *창*이고 셸은 *그 창 안에서 도는 프로그램*이다. macOS Terminal.app 위에서 zsh가 돌 수도 있고 bash가 돌 수도 있다. iTerm2 창 안에서 zsh가 도는 것과 Terminal.app 창 안에서 zsh가 도는 건 *셸*은 똑같다 — 창만 다르다.

왜 이 분리를 굳이 강조하는가. 에러가 났을 때 범인이 누구냐가 달라지기 때문이다.

- 글자가 깨져 보인다 → 터미널 문제 (폰트·인코딩 설정)
- `command not found`가 나온다 → 셸 문제 (PATH·환경 변수)
- 권한 거부 → OS 문제 (파일 권한)

A-1-3에서 에러 메시지 5종을 다루는데, 그때 "이 에러는 어느 층에서 나온 거냐"를 1초에 골라야 한다. 지금 깔아두는 분리가 그때 살아난다.

### 프롬프트 — 검은 창이 던지는 *명함* 한 줄

셸이 입력을 기다릴 때 화면 맨 앞에 표시하는 짧은 글자가 **프롬프트(prompt)**다. 영어로 "재촉한다"는 뜻 — 셸이 "명령 줘"라고 재촉하는 자리.

프롬프트는 단순한 장식이 아니다. 셸 입장에서 *너에게 지금 환경을 통보하는* 명함이다. 명함을 못 읽으면 잘못된 서버에서 잘못된 사용자로 잘못된 디렉터리에서 명령을 친다. 그 다음은 사고다.

표준 프롬프트는 **4요소**로 구성된다.

```
ty@MacBook-Pro pokeclip % 
└┬┘ └────┬───┘ └──┬───┘ └┬┘
 │       │       │      │
사용자   호스트   현재 경로  권한 기호
```

| 요소 | 의미 | 왜 중요한가 |
|---|---|---|
| 사용자 (user) | 지금 셸을 띄운 계정 이름 | sudo가 필요한지·파일 권한 누가 가졌는지 판단 |
| 호스트 (host) | 지금 접속해 있는 컴퓨터 이름 | 로컬인지 원격(EC2)인지 / 어느 서버인지 식별 |
| 경로 (cwd) | 현재 작업 디렉터리 | 상대 경로 명령이 어느 폴더 기준으로 도는가 |
| 권한 기호 | `%`(zsh 일반) / `$`(bash 일반) / `#`(root) | 단 한 글자로 권한 수준 통보 |

이 4요소는 셸·OS마다 모양이 조금씩 다르지만 *역할은 동일*하다. 모양 외워봐야 소용없다. **어느 자리에 무엇이 있는지 위치 감각**이 본질.

---

### 로컬 macOS와 EC2 Amazon Linux — 같은 4요소, 다른 모양

PokéClip 운영을 시작하면 매일 두 환경을 오간다.

**로컬 MacBook (zsh 기본)**

```
ty@MacBook-Pro pokeclip % python3 srt_listener.py
```

- 사용자: `ty`
- 호스트: `MacBook-Pro`
- 경로: `pokeclip` (홈 디렉터리 아래 한 단계)
- 권한 기호: `%` (zsh 일반 사용자)

**EC2 Amazon Linux (bash 기본)**

```
[ec2-user@ip-10-0-1-42 ~]$ python3 srt_listener.py
```

- 사용자: `ec2-user`
- 호스트: `ip-10-0-1-42` (EC2가 사설 IP를 호스트명으로 자동 부여)
- 경로: `~` (홈 디렉터리)
- 권한 기호: `$` (bash 일반 사용자)

`[...]` 대괄호와 색이 다를 뿐 **4요소는 그대로**다. 처음 SSH로 들어갔을 때 "이게 뭐지" 하고 굳을 필요가 없다. 위치만 보면 된다.

특히 호스트명 `ip-10-0-1-42`는 EC2 인스턴스가 가진 사설 IP가 그대로 박힌 형태로 매우 흔하다. 두 터미널 창을 띄워두고 "어느 게 어느 서버지" 헷갈릴 때 이 호스트명 한 줄이 1초 만에 답을 준다.

### 권한 기호 `%` vs `$` vs `#` — 한 글자가 가진 무게

프롬프트 마지막 한 글자가 가장 중요하다. 이건 *연출이 아니라 통보*다.

| 기호 | 의미 | 셸 |
|---|---|---|
| `%` | 일반 사용자 | zsh |
| `$` | 일반 사용자 | bash / sh |
| `#` | **root (관리자)** | 셸 무관 — *권한이 root면 항상 #* |

`#`이 보이면 그 셸은 **무엇이든 부술 수 있는 상태**다. `rm -rf /` 한 줄이 진짜로 시스템을 통째로 지운다. 일반 사용자(`%`/`$`)였다면 같은 명령이 권한 거부로 막혔을 텐데, `#`은 막을 사람이 없다.

```
# 같은 명령, 권한 한 글자 차이로 결과가 천지차이
ty@MacBook-Pro / % rm /etc/hosts
rm: /etc/hosts: Permission denied              [차단됨 — 살았다]

root@MacBook-Pro / # rm /etc/hosts
                                               [차단 없음 — 시스템 부분 사망]
```

PokéClip 운영에서 `#`을 보는 자리는 다음 두 곳이다.

1. EC2에서 `sudo su -`로 root 셸을 띄운 직후
2. Docker 컨테이너 안에 들어갔을 때 (컨테이너 안 기본 사용자가 root인 이미지가 많다)

이 두 자리에서는 **명령을 치기 전에 프롬프트를 한 번 더 보는 습관**이 사고 방지의 첫 줄. AI가 짜준 명령을 그대로 붙여 넣기 전에 마지막 한 글자만 확인하면 된다.

```
# AI가 짜준 명령
sudo systemctl restart nginx

# 붙여넣기 전 프롬프트 확인
[ec2-user@ip-10-0-1-42 ~]$    ← $ 이므로 sudo가 필요 (정상)
[root@ip-10-0-1-42 ~]#        ← 이미 # 이므로 sudo 빼도 됨 (이미 root)
```

`#`에서 `sudo`를 또 붙이는 건 무해하지만, `$`에서 `sudo` 빼고 시스템 명령을 치면 권한 거부로 시간을 잃는다. 한 글자에 디버깅 30초가 걸렸다 풀렸다 한다.

### 프롬프트를 *명령으로* 검증하기 — `whoami` / `hostname` / `pwd` / `id`

프롬프트를 못 믿는 상황은 의외로 많다. 호스트명이 너무 길어 잘려 보이거나, 커스텀 테마가 프롬프트를 꾸미느라 사용자명을 숨겼거나, 화면을 가득 메운 출력 때문에 프롬프트가 멀리 사라졌거나.

이럴 때 4요소를 *명령으로 직접 물어보는* 4개의 짧은 명령이 있다.

```bash
# 사용자 확인 — 지금 누구로 셸이 떠 있는가
whoami
# 출력 예시:
# ec2-user

# 호스트명 확인 — 지금 어느 머신에 있는가
hostname
# 출력 예시:
# ip-10-0-1-42.ap-northeast-2.compute.internal

# 현재 작업 디렉터리 확인 (print working directory)
pwd
# 출력 예시:
# /home/ec2-user/pokeclip

# 사용자 ID + 그룹 + 권한 그룹 종합 확인
id
# 출력 예시:
# uid=1000(ec2-user) gid=1000(ec2-user) groups=1000(ec2-user),10(wheel),190(systemd-journal)
```

이 4개는 어느 셸·어느 OS에서도 똑같이 동작한다(Windows의 Git Bash·WSL 포함). EC2 인스턴스에 SSH로 처음 들어가 가장 먼저 치는 4줄로 굳혀두면 좋다.

`id`가 특히 중요한데, `whoami`보다 정보가 풍부하다. `groups=...` 부분에 `wheel`이나 `sudo` 그룹이 들어 있으면 *지금은 일반 사용자(`$`)지만 `sudo`로 root 권한을 빌릴 수 있다*는 뜻. EC2 Amazon Linux의 `ec2-user`는 기본으로 `wheel`에 속해 있어 sudo 가능, 반면 새로 만든 일반 사용자는 그룹에 명시적으로 넣지 않으면 sudo가 거부된다.

```bash
# 한 줄로 4요소를 한 번에 확인하는 패턴 (자주 씀)
echo "[$(whoami)@$(hostname) $(pwd)]"
# 출력:
# [ec2-user@ip-10-0-1-42 /home/ec2-user/pokeclip]
```

스크립트가 자동화 중간에 자기가 어디 있는지 로그로 남길 때도 유용한 한 줄.

### 작업 디렉터리 한 줄 자동화 — `mkdir -p`

프롬프트의 4요소 중 "경로"는 단순히 *보는 것*만 아니라 *내가 통제하는* 요소다. 작업 시작 직후 디렉터리 구조를 한 줄에 만들어 두는 작은 자동화 하나를 익히면 5초가 매번 절약된다.

PokéClip 분석 결과를 일자별로 모아두는 폴더 구조를 만든다고 하자.

```bash
# 일반적인 mkdir — 부모 폴더가 없으면 에러
mkdir /home/ec2-user/pokeclip/output/2026-06-22/clips
# mkdir: cannot create directory '...': No such file or directory
```

`mkdir`는 기본적으로 *마지막 한 폴더*만 만든다. `output/`도 `2026-06-22/`도 없는 상태에선 실패한다.

```bash
# -p (parents) — 중간 폴더가 없으면 알아서 만들어 줌
mkdir -p /home/ec2-user/pokeclip/output/2026-06-22/clips
# [성공 — 4단계 폴더 한 번에 생성]

# 검증
ls /home/ec2-user/pokeclip/output/2026-06-22/
# clips
```

`-p`는 두 가지 효용을 동시에 준다.

1. 중간 폴더 자동 생성 — 단계마다 `mkdir` 4번 칠 필요 없음
2. **이미 있는 경우 에러 안 냄** — 자동화 스크립트에서 매번 만들어도 안전

```bash
# 자동화 스크립트가 매번 실행되어도 안전한 패턴
mkdir -p ~/pokeclip/output/$(date +%Y-%m-%d)/clips
cd ~/pokeclip/output/$(date +%Y-%m-%d)/clips
# 오늘 날짜 폴더로 진입 — 폴더가 있든 없든 동작
```

`$(date +%Y-%m-%d)`는 *명령 치환(command substitution)*으로, 괄호 안 명령의 출력 결과를 그 자리에 끼워 넣는다. 오늘이 2026-06-23이면 `~/pokeclip/output/2026-06-23/clips`로 풀린다. A-1-2(환경 변수)에서 다시 만난다.

### 트레이드오프 — 프롬프트 커스터마이즈를 얼마나 할 것인가

검색해 보면 Oh My Zsh·Starship·Powerlevel10k 같은 화려한 프롬프트 도구가 나온다. 입문자가 가장 먼저 빠지는 함정 중 하나가 *셋업에 반나절 쓰는* 것.

| 선택 | 장점 | 단점 | 권장 시점 |
|---|---|---|---|
| 기본 프롬프트 그대로 | 4요소가 그대로 보임 / 셋업 0분 / EC2와 모양 비슷 | 색이 칙칙함 / Git 브랜치명 표시 X | **입문~첫 3개월** |
| Oh My Zsh 가벼운 테마 (robbyrussell 등) | 사용자/호스트/경로 색상 구분 / Git 브랜치 표시 | 셋업 10분 / 가끔 호스트명 숨김 | Git 본격 사용 후 |
| Powerlevel10k / Starship | 매우 화려 / 정보 풍부 / 빠름 | 셋업 30분~1시간 / 폰트 설치 / 호스트명·사용자 *숨기는 게 기본* | 1년차 이후 |

입문 단계의 권장은 **기본 그대로**다. 이유는 명확하다. 검은 창 4요소 위치를 몸이 외우기 전에 화려한 테마로 가리면, EC2에 SSH로 들어가 기본 프롬프트를 만났을 때 다시 헷갈린다. 도구가 가르쳐 줄 수 있는 건 보기 좋음이지 위치 감각이 아니다.

특히 Powerlevel10k는 기본 옵션이 *호스트명을 숨김*이다. 로컬에선 어차피 한 대니 상관없지만, EC2 여러 인스턴스에 SSH 들어가서도 같은 테마를 깔면 어디가 어디인지 즉시 모른다. 사고 회피의 정반대 방향.

이 강의는 6개월 뒤 EC2 운영이 일상이 됐을 때 Starship 같은 도구를 *원격 서버 식별 강조 설정*으로 깔라고 권한다. 그전엔 기본 프롬프트 위에서 4요소 위치 감각부터.

### 실무 적용 시나리오

**시나리오 1 — AI 명령 SSH 권한 오류 즉시 진단**

AI에게 "Nginx 재시작 명령 짜줘"라고 했더니 한 줄이 돌아온다.

```
systemctl restart nginx
```

이걸 EC2에 SSH로 들어간 창에 그대로 붙여 넣었더니 에러가 뜬다.

```
[ec2-user@ip-10-0-1-42 ~]$ systemctl restart nginx
Failed to restart nginx.service: Interactive authentication required.
```

프롬프트가 `$`다. 일반 사용자라는 통보. systemctl 같은 시스템 서비스 제어는 root 권한이 필요하다. *명령을 다시 짤 게 아니라 프롬프트를 다시 본 것*이 해법.

```
[ec2-user@ip-10-0-1-42 ~]$ sudo systemctl restart nginx
[성공]
```

`sudo` 한 단어 추가로 끝난다. 프롬프트 4요소 중 권한 기호 한 글자만 봤어도 처음부터 알았을 일.

**시나리오 2 — 두 터미널 창 다른 결과를 호스트명으로 1초 식별**

두 개의 iTerm2 탭을 띄워 두고 같은 `ls`를 쳤는데 파일 목록이 다르다. "왜 같은 폴더인데 다르지?" 5분을 헤맸다.

```bash
# 탭 1
ty@MacBook-Pro pokeclip % ls
README.md  src/  tests/

# 탭 2
[ec2-user@ip-10-0-1-42 pokeclip]$ ls
README.md  src/  output/  .env
```

호스트명만 봤어도 *탭 2는 EC2 원격이라는 사실*을 1초에 알았을 일. 로컬과 원격이 같은 폴더 이름을 갖고 있을 뿐 다른 머신의 다른 파일들이다.

```bash
# 헷갈릴 때 한 줄로 자기 위치 확인
[ec2-user@ip-10-0-1-42 pokeclip]$ echo "[$(whoami)@$(hostname)]"
[ec2-user@ip-10-0-1-42.ap-northeast-2.compute.internal]
```

**시나리오 3 — EC2 들어가자마자 `whoami`로 사용자 확인**

새 EC2 인스턴스에 처음 SSH로 들어갔다. AMI(Amazon Machine Image)에 따라 기본 사용자가 다르다.

| AMI | 기본 사용자 |
|---|---|
| Amazon Linux 2 / 2023 | `ec2-user` |
| Ubuntu | `ubuntu` |
| RHEL | `ec2-user` 또는 `cloud-user` |
| Debian | `admin` |

```bash
# SSH 들어간 직후 첫 명령
$ whoami
ec2-user

$ id
uid=1000(ec2-user) gid=1000(ec2-user) groups=1000(ec2-user),10(wheel),...
```

`wheel` 그룹이 보이므로 sudo 가능. PokéClip 분석 서버 셋업 스크립트를 root 권한으로 돌릴 수 있다는 판단이 1초에 선다. 만약 일반 사용자였고 `wheel`이 없었다면 *지금 sudo 못 한다*는 사실을 알고 사람을 부르는 게 정답.

### PokéClip 적용

PokéClip의 EC2 SRT Listener Server에 매일 SSH로 들어가 분석 프로세스 상태를 점검한다. 접속 직후 첫 3초의 표준 절차는 다음과 같다.

```bash
[ec2-user@ip-10-0-1-42 ~]$ whoami && hostname && pwd
ec2-user
ip-10-0-1-42.ap-northeast-2.compute.internal
/home/ec2-user
```

이 3줄로 *어떤 서버의 / 어떤 사용자로 / 어떤 디렉터리에서* 작업을 시작하는지 확정한다. SRT Listener Server와 분석 GPU 인스턴스가 둘 다 떠 있을 때 두 SSH 세션을 동시에 띄우는데, 둘의 호스트명이 비슷해 보여도 4요소만 분리해 보면 절대 헷갈리지 않는다.

A-1 시리즈 5강(SSH+EC2)에서 이 첫 접속 절차를 본격적으로 다룬다. 지금은 *프롬프트 4요소가 같은 구조로 원격에서도 그대로 통한다*는 사실 하나만 잡고 다음 강의로 간다.

### 다음 강의 미리보기 — A-1-2

다음 강의(A-1-2)는 환경 변수와 PATH다. 이번 강의에서 `whoami`나 `mkdir`을 칠 수 있었던 건 셸이 *어디선가 그 바이너리를 찾아냈기* 때문이다. 어떻게 찾았는가, 못 찾으면 어떻게 되는가 — `command not found`의 진짜 원인이 그 자리에 있다. 입문자가 가장 많이 사고를 치는 한 변수, PATH로 진입한다.

### 1강 핵심 3줄

1. 검은 창 한 줄은 **4요소(사용자·호스트·경로·권한 기호)**로 해부한다 — 모양보다 위치 감각이 본질.
2. 권한 기호 한 글자(`%`/`$` 일반 vs `#` root)가 명령의 파괴력을 결정한다 — `#`을 봤으면 명령을 치기 전 한 번 더 본다.
3. 프롬프트가 못 미더우면 `whoami` · `hostname` · `pwd` · `id` 4개 명령으로 직접 검증한다 — 어느 셸·어느 OS에서도 동일하게 동작.
