# review — pokeclip-srt-latency-late-retransmission (2편)

## 시각 자료 판단

- 움직임: `LateRetransmit` 11초 반복 + 휴대폰판(개념도). 「재전송이 창 끝보다 먼저 오나 늦게 오나」가 시간 순서 자체라 움직임이 맞다고 판단(storyboard.md). 강조색은 창·메움, 위험색은 잃음·건너뜀만.
- 정적: 그림 1 ECharts(실측). 이중 축 금지라 오류 수 대신 오류 점을 같은 단위(직전 10초 최대 RTT)로 올렸다. 시각은 송출 시작 뒤 분, 시작 시각 KST는 캡션.
- 표 2(재정렬 오류, 복호 오류 조각): 정확한 값 조회. 같은 수치를 그래프로 되풀이하지 않음.
- 넣지 않음: Wi-Fi 지표 그래프, +2초 대 +4초 그래프, Mermaid 구성도, 생성 이미지.

## 독립 리뷰

(아래에 결과와 반영 기록)

새 컨텍스트 하위 에이전트 1회(원자료·결정 노트·PR #493·상류 소스 대조). 판정 「수정 필요」(MUST 2 · SHOULD 7 · NIT 4) → 아래처럼 반영.

- MUST 1: 측정 조건의 「2·3차 포화」 → 2차는 부하 서버 접속 실패로 포화 미실행, 3차만 포화.
- MUST 2: 「지연만 튀면 녹화가 깨지지 않았다」 일반화 → 「재정렬 오류가 없었다」로 한정(description · 첫 문단 · 소제목 · 판단 목록). 손실 없는 10초 급등의 drift 교체를 판단 목록에 덧붙임.
- SHOULD: 첫 문단·소제목을 「첫 시험 방송」으로, 공통점 문장을 「1초 안팎 막히거나 잃은 패킷을 1초 안에 메우지 못함」으로, 5,000ms 기각에 복호 오류 조각 차이(19·25 → 5·5)와 「효과 차이 작음」 판단을 함께, 2D 설명을 「뒤 패킷이 와서 손실을 알아채기까지 약 D」로(한쪽 지연 조건), 분당 손실 범위를 10:00–10:04로 한정, 무손실 경계에 뜻(재정렬 오류·교체·구멍 0) 붙임, 소제목 두 곳(송출 PC 정지·소켓 넘침 / 11월 4일 방송) 고침.
- NIT: 「OBS의 CPU 사용률」, 기준 라이브 지연 「약 0.9 · 약 2.9초」, 「실제보다 가혹」 · 「송신 버퍼가 찰 위험」에 추정 표기. 역할: 플러그인 코드 작성 주체는 원자료로 확인하지 못해 본문에 넣지 않음(사용자 확인 필요).
- 확인됨: 수치 전부(그림 1 오류 점 14개 좌표 포함), 링크 행 범위, 승인 규칙 1–7, 비공개 식별자 0건.
