# 측정 메모 (AI(Claude Code) 실행, 2026-11-13 16:11–16:40 KST)
- 기종: MacBook Air Mac17,3 Apple M5(고성능 4·효율 6), 32GB, 팬 없음, macOS 27.0.1, Docker 29.8.2. 같은 기계에서 다른 세션의 작업(다른 Docker 묶음 포함)이 함께 돌아 1분 load average가 측정 중 10–95였다. 브로커 4대(컨트롤러 1 + 브로커 3)와 클라이언트가 모두 한 노트북의 한 Docker VM 안이라 망·디스크 분리가 없다.
- 구성: compose.yml (프로젝트 tb6-kafka, 라벨 com.techblog.bench=tb6-kafka). 컨트롤러 전용 노드 1대(node 100, KRaft) + 브로커 3대(node 1–3). 컨트롤러를 따로 둔 이유: 브로커 둘을 멈춰도 메타데이터 정족수가 유지되게.
- K0(k0.txt, producer-defaults.txt): 기본값. 브로커 min.insync.replicas=1, replica.lag.time.max.ms=30000, unclean.leader.election.enable=false, broker.session.timeout.ms=9000, replica.selector.class=null. 기능 eligible.leader.replicas.version=1(ELR 켜짐), metadata.version 4.4-IV2, share.version 2. 프로듀서 acks=all, linger.ms=5, batch.size=16384, enable.idempotence=true.
- K1(k1-set1-highload.txt, k1-set2.txt): 토픽 bench 파티션 6 · 복제 3 · min.insync.replicas=2. 최대 처리량(--throughput -1, 200,000건 × 1,000바이트)은 같은 조건 반복 사이 2–3배 흔들렸다(호스트 부하). 지연 비교는 고정 처리량 2,000건/초(20,000건 × 1,000바이트) 결과로 한다 — p50: acks=1·linger 0 = 1ms(3회 1·1·1), acks=1·linger 5 = 5ms(5·5·5), acks=all·linger 0 = 1–4ms(2·1·4), acks=all·linger 5 = 5–7ms(5·7·?) — 원자료 k1-set2.txt.
- K2(k23.txt 위쪽): 토픽 nr(복제 1:2:3, min.insync.replicas=2)에서 kafka2·3을 docker stop → 약 7초 안에 ISR 1, ELR 3. acks=all 100건 전부 NotEnoughReplicasException, acks=1 100건 성공. (끝 오프셋 nr:0:0은 ListOffsets가 돌려준 high watermark다 — acks=1로 쓴 100건은 리더에만 있어 HW가 오르지 않았다.)
- K3(k23.txt 아래쪽): acks=1 — 1,000건(acks=all) 뒤 팔로워 둘을 docker pause, acks=1 100건 전부 확인 응답, 리더 kafka1 docker kill, 팔로워 unpause → 약 13초 뒤 리더 2(ISR 2,3), 새 리더 끝 오프셋 1000, kafka1 재시작 뒤 처음부터 읽은 레코드 1,000건 → 확인 응답을 받은 100건이 사라졌다. acks=all — 같은 순서에서 100건 전부 TimeoutException(확인 응답 없음), 멈춘 사이 팔로워가 펜싱돼 ISR 1·ELR 3, 리더 kill 뒤 ELR이던 3이 리더, 끝 오프셋 1000 · 읽은 레코드 1,000건 → 확인 응답을 받은 기록 중 사라진 것은 없다. 각 1회.
- get-offsets의 "끝 오프셋"은 클라이언트가 볼 수 있는 high watermark다(리더 로그 끝 LEO가 아님).
