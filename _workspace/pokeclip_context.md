# PokéClip 기술 컨텍스트

이 문서는 **lesson-planner / lesson-author / 블로그 작성 흐름**이 매번 cat으로 읽는 PokéClip 프로젝트의 기술 컨텍스트.

KPI/비즈니스/일정/팀 구성 등은 **포함 안 함** — 강의에 필요 없음. 기술 사양 + 학습자 진단 + 진행 중 결정만.

---

## 1. PokéClip 한 줄

AI 기반 라이브 스트리밍 하이라이트 자동 클립 추출 시스템. 치지직·SOOP 게임 스트리머의 편집자가 6~8시간 VOD를 처음부터 끝까지 안 봐도 하이라이트 추출+구간 태깅+편집 점프 카드를 받게 함.

---

## 2. 시스템 아키텍처 — 9단계 백엔드 파이프라인

```
[1] 스트리머 PC (OBS)
    ├─ Stream 탭: RTMP 1080p → 치지직
    └─ Recording 탭: SRT+MPEG-TS → 자체 서버 (멀티 오디오 4트랙)
[2] SRT Listener Server (AWS EC2)
[3] FFmpeg Demultiplexing (비디오 1 + 오디오 N개 분리)
[4] Track Routing (트랙 존재 여부에 따라 동적 분기)
[5] Analysis Engines (병렬)
    - YOLO Video Analysis (영상)
    - Whisper STT (마이크/Discord 음성)
    - Game Sound Recognition (효과음)
    - Discord Whisper
    - Donation Sound
    - Chat Analysis (Lambda, 치지직 공식 API)
[6] Score Integration (E Hybrid Voting)
[7] Segment Tagging (LLM Summary)
[8] Highlight Clip Detection
[9] Output (DynamoDB / S3 / Web Dashboard / EDL Export)
```

## 3. OBS 송출 구현 (확정)

| 항목 | 값 |
|---|---|
| 핵심 결정 | OBS native 기능만으로 구현 — 자체 송출 플러그인 X |
| Stream 탭 | RTMP → 치지직 1080p 6000kbps 믹스 오디오 1트랙 |
| Recording 탭 | Custom FFmpeg → URL 모드 → SRT+MPEG-TS → 자체 서버 720p 2500kbps 멀티 오디오 최대 4트랙 |
| 영상 인코딩 | 2회 NVENC (RTX 30/40/50 시리즈 3세션 지원, 2개 사용) |
| 오디오 트랙 | 트랙 1: 통합 믹스 / 트랙 2: 마이크 / 트랙 3: 게임 / 트랙 4: Discord / 트랙 5: BGM / 트랙 6: 후원 |
| 스트림 인증 | 자체 발급 stream key, SRT URL `streamid=KEY`에 포함 |
| 1080p 영상 활용 | 자체 서버는 1080p MPEG-TS 그대로 받아 보관 + 720p로 다운스케일하여 분석. 편집자에게 1080p 다운로드 제공 |

### Recording 탭 세부 설정 (실험 검증 완료)

| 항목 | 설정값 |
|---|---|
| 형식 | 임의 출력 (FFmpeg) |
| FFmpeg 출력 | URL 모드 |
| URL | `srt://server:port?streamid=KEY` |
| 컨테이너 | mpegts |
| Muxer | `mpegts_flags=+resend_headers` (PAT/PMT 주기적 재전송) |
| 비디오 비트레이트 | 2500 Kbps |
| 키프레임 간격 | 60 프레임 (1초) — AI 분석에 유리한 짧은 GOP |
| 출력 배율 재조정 | 활성화 / 1280x720 |
| 모든 코덱 표시 | 필수 체크 |
| 비디오 인코더 | h264_nvenc (Win) > h264_videotoolbox (Mac) > libx264 폴백 |
| 오디오 인코더 | AAC 128 Kbps |
| 오디오 트랙 선택 | 2, 3, 6 (마이크 / 게임 / 후원) |

### 멀티 오디오 트랙 분리 (OBS 설정)

| 오디오 소스 | OBS 소스 타입 | 캡처 대상 | 할당 트랙 |
|---|---|---|---|
| 마이크 | 오디오 입력 캡처 | 스트리머 마이크 장치 | 트랙 1 + 트랙 2 |
| 게임 사운드 | 응용 프로그램 오디오 캡처 (BETA) | LeagueClient.exe / LeagueOfLegends.exe | 트랙 1 + 트랙 3 |
| Discord | 응용 프로그램 오디오 캡처 (BETA) | Discord.exe | 트랙 1 + 트랙 4 |
| BGM (YouTube) | 응용 프로그램 오디오 캡처 (BETA) | chrome.exe / Spotify.exe | 트랙 1 + 트랙 5 |
| 후원 알림 | 응용 프로그램 오디오 캡처 (BETA) | Streamlabs / Twip 브라우저 | 트랙 1 + 트랙 6 |

트랙 1 = 모든 소리 통합 → 치지직 RTMP. 트랙 2~6 분리 → 자체 서버.

## 4. 분석 엔진 — 점수 산정 방식

태깅과 하이라이트는 독립 처리.
- **태깅**: 구간별로 어떤 내용이 있었는지 정리·요약 (영상+음성)
- **하이라이트**: 구간 안에서 점수가 높은 부분 식별 (영상+음성+채팅 점수 종합)

### 영상 점수 (V-2) — YOLO 기반 게임 도메인 이벤트 인식 (LoL 적용 예시)

| 감지 대상 | 점수 신호 |
|---|---|
| 킬피드 (Kill Feed) | 좌상단 킬 표시 OCR/이미지 인식 → 킬 발생 시점 마킹 |
| 데스 화면 | 회색조 전환 + "You Have Been Slain" 감지 |
| 오브젝트 처치 | 드래곤·바론·전령·내셔 처치 알림 인식 |
| 한타 발생 | 화면 내 챔피언 밀집도 + 이펙트 폭증 감지 |
| 타워 파괴 | 타워 파괴 이펙트 + 골드 알림 인식 |

### 음성 점수 — 멀티 트랙 분리 분석

| 트랙 | 분석 엔진 | 처리 내용 |
|---|---|---|
| 트랙 2 (마이크) | Whisper STT + LLM | A-1 데시벨 피크 1차 감지 → A-2 후보 구간만 Whisper STT + LLM 감정 분석 "잡았다", "미쳤다" 등 흥분 표현 감지 |
| 트랙 3 (게임 사운드) | 효과음 패턴 인식 | Penta Kill·Ace·Quadra Kill 사운드, 드래곤·바론 처치 사운드, 한타 BGM 전환 감지 → 영상 YOLO가 못 잡는 게임 이벤트 보완 |
| 트랙 4 (Discord) | Whisper STT + LLM | 팀원 환호/탄식 감지 ("GG", "잘했다", "와씨" 등) → 스트리머 본인 외 팀 분위기 반영 (트랙 존재 시에만) |
| 트랙 6 (후원 알림) | 효과음 패턴 인식 | 도네이션 TTS 알림음, 슈퍼챗 사운드 감지 → 채팅 점수의 슈퍼챗 신호와 교차 검증 (정확도 향상) |

음성 점수 = 트랙 2 (마이크) 가중치 높음 + 트랙 3·4 보조 신호 + 트랙 6은 채팅 점수 교차 검증. 각 트랙은 트랙 라우팅 단계에서 분기되어 병렬로 분석됨 (트랙 미존재 시 자동 스킵).

### 채팅 점수 (C-1, C-2, C-4, C-5) — 4가지 신호 종합

| 신호 | 내용 |
|---|---|
| C-1: 채팅 속도 급증 | 평균 대비 N배 폭증 시점 감지 (가장 핵심적인 신호) |
| C-2: 이모티콘/슬랭 폭발 | "ㅋㅋㅋㅋ", "ㄷㄷㄷ", "ㅁㅊ", 치지직 이모티콘 폭증 → 감정 결 파악 |
| C-4: 도네이션/슈퍼챗 | 슈챗 받는 순간 + 금액 비례 가중치 (1k~5k ×1.0 / 5k~20k ×1.2 / 20k~50k ×1.5 / 50k+ ×2.0) |
| C-5: 채팅 길이/반복 패턴 | 짧고 빠른 반응형 채팅 ("ㅋㅋ", "ㄷㄷ", "와") 비율 + 반복 키워드 |

### 채팅 딜레이 보정

| 단계 | 방식 |
|---|---|
| 초기 | 평균값 5초 고정 보정 (채팅 → 영상 타임스탬프로 -5초) |
| 동적 보정 | 방송 중 채팅 폭발 패턴 누적 분석 → N초 자동 보정 (첫 30분 데이터 축적 후 정확도 상승) |

## 5. 하이라이트 판단 로직

### 점수 정규화 (방법 B — 상대값 기반)

스트리머마다 평소 채팅 속도·볼륨·이벤트 빈도가 다르므로 절대값이 아닌 방송 평균 대비 상대값으로 정규화. 영상/음성/채팅 점수 모두 0~100 스케일.

**첫 30분 처리 정책 (옵션 B 채택)**: 첫 30분은 전체 누적 평균을 계속 업데이트하면서 그때그때 점수 내고, 나중에 30분 분량 쌓이면 보정 재계산.

### 점수 통합 방식 (E Hybrid)

셋 중 둘 이상의 신호가 임계치를 초과한 시점을 하이라이트로 판단.
- 한 신호만 폭발한 경우는 오탐으로 간주 (예: 채팅만 폭발한 단순 떡밥 채팅 등)
- 여러 신호가 함께 폭발한 순간이 진짜 하이라이트 (보스 클리어 + 환호 + 채팅 폭발 등)

자체 함수 형태는 **미정** — 단순 가중 평균 / 곱셈 결합 / 신호 간 곱+합 혼합 중 베타 단계 튜닝.

### 시간 단위 및 클립 길이

| 항목 | 설정 |
|---|---|
| 점수 계산 시간 윈도우 | 5초 단위 |
| 클립 길이 결정 방식 | 이벤트 경계 감지 — 점수 그래프의 상승/하락 자동 감지로 자연스러운 시작·종료점 추출 (peak detection, 슬라이딩 윈도우, 미분 임계 교차 등 알고리즘 후보 — 강의에서 다룸) |
| 최소 클립 길이 | 10초 (미정 — MVP 단계 튜닝) |
| 최대 클립 길이 | 90초 (미정 — MVP 단계 튜닝) |

### 분석 시점

방송 중 실시간 분석 + 점진적 대시보드 업데이트 (앞부분부터 제공) + 방송 종료 후 30분~2시간 내 최종 결과 + 1080p 영상 다운로드 제공. 분석은 방송 시간과 1:1로 이루어지지 않으므로 점진 처리.

## 6. 처리 순서 (방송 진행 중 + 종료 후)

| 순서 | 처리 | 결과물 |
|---|---|---|
| 1 | 구간 태깅 (영상+음성 분석) | "이 구간은 게임 / 저 구간은 시청자 소통" 카테고리 분리 |
| 2 | 구간별 내용 요약 (LLM) | "외식 얘기, 다른 스트리머 만난 얘기 등" 자연어 요약 |
| 3 | 점수 산정 (영상+음성+채팅) | 5초 단위 0~100 정규화 점수 |
| 4 | 하이라이트 판단 (E Hybrid) | 둘 이상 신호 임계치 초과 시점 마킹 |
| 5 | 이벤트 경계로 클립 시작·끝 결정 | 자연스러운 클립 길이 자동 추출 |
| 6 | 편집 점프 카드 생성 | 타임스탬프 + 점수 + 요약 |
| 7 | EDL/XML 내보내기 | 파이널컷·프리미어 임포트 가능 포맷 (포맷 우선순위 미정) |

## 8. 서버 인프라 (확정)

| 컴포넌트 | 인프라 | 이유 |
|---|---|---|
| SRT 수신 + 디멀티플렉싱 | EC2 (방송 시간대만 가동, Auto-scaling) | 실시간 스트림 처리 필요 |
| GPU 영상 분석 | EC2 GPU 인스턴스 (Auto-scaling) | Lambda는 GPU 미지원, 15분 제약 |
| 채팅 수집·분석 | AWS Lambda (서버리스) | 이벤트 기반 처리에 적합 |
| 결과 저장 | DynamoDB (서버리스) — **미정, 강의 트레이드오프 대상** | 태깅·점수 메타데이터 저장 |
| 웹 대시보드 API | API Gateway + Lambda | 서버리스로 비용 최소화 |
| EDL/XML 내보내기 | Lambda | 요청 시 생성 |
| 방송 시작/종료 감지 | OBS SRT 연결 감지 + 치지직 API | 즉시 가동 + 유효 방송 확인 교차 |

EC2 GPU Auto-scaling 트리거: OBS SRT 연결 감지 → 콜드스타트 EC2 부팅 (2~3분).

베타 편집자 10명 한정 운영. Docker 미정 (일단 EC2만 사용 예정).

## 9. 핵심 기술 스택

OBS native 송출 · SRT/MPEG-TS · AWS (EC2 GPU + Lambda + DynamoDB) · YOLO · Whisper API · LLM API

세부 미정 영역:
- **AI 모델**: PyTorch/TensorFlow/ONNX 미정. Whisper API vs self-hosted 미정. Qwen-VL 사용 여부 비용 트레이드오프 검토 필요. YOLO 학습 데이터 라벨링 도구 미정.
- **백엔드 언어**: PokéClip은 Python 자연스러움 (AI 생태계). Java/Spring은 치지직 입사 대비 별도 트랙.
- **DB**: DynamoDB는 LLM 추천만 듣고 박은 것. 후보 — DynamoDB / RDS PostgreSQL / MongoDB / TimescaleDB.
- **OCR**: 킬피드 OCR 미정 (Tesseract / PaddleOCR / 안 함).
- **효과음 패턴**: 사전 정의 템플릿 매칭 확정 (ML 분류기 아님).
- **점수 통합 함수**: 자체 설계 필요. 가중치/임계치 베타 튜닝.
- **클립 경계 알고리즘**: peak detection 알고리즘 강의에서 다룸.

## 11. 사용자 18+ Q&A 기술 답변 정리

### 송출/인코딩

- NVENC 2세션 = OBS native 활용. 3세션 한도는 신경 안 씀
- Recording 탭 SRT+MPEG-TS = 멀티 오디오 분석 목적 + PID 기반 트랙 식별
- 720p 분석 + 1080p 보관 둘 다 (자체 서버에서 1080p 받아 다운스케일하여 분석, 1080p는 그대로 보관)
- SRT_LATENCY = 균형 잡힌 값 (구체 수치 미정, 200ms 전후 가능)

### 트랙 라우팅

- 트랙 갯수 자동 감지 vs 설정값 — 미정 (강의에서 비교)
- 트랙 1은 자체 서버에 안 보내짐 (Recording 탭에서 트랙 2/3/6만 체크)

### AI/분석

- 영상 분석 = 여러 모델 합치거나 Qwen-VL 가능성. **킬피드는 고정 영역이라 YOLO만으로 가능** (비용 절감 우선)
- 킬피드 OCR 단계 분리 미정
- Whisper API vs self-hosted 미정 (AI 지식 부족)
- 효과음 패턴 = **사전 정의 템플릿 매칭** (확정)
- Whisper 인스턴스 트랙별 분리 병렬 처리
- AI 모델 선택 / 학습 / 파인튜닝 / 비용 트레이드오프 — 강의에서 다룸

### 채팅

- 4신호(C-1/2/4/5) 내부 가중 합산 → 채팅 점수 1개 → 영상/음성/채팅 셋 중 둘 이상 비교
- 채팅 딜레이 보정 — 치지직 채팅 wall clock 기준. 고정 vs 변동 미정
- 채팅 API = WebSocket 추정. 디테일 강의에서 다룸

### 점수 통합 + 클립 추출

- 자체 함수 짤 예정. 형태 미정 (가중 평균/곱셈/혼합)
- 점수 정규화 옵션 B (누적 평균 점진 보정)
- 클립 경계 — 점수 그래프 자동 감지 + ±30초 단계. 알고리즘 강의에서 다룸

### 인프라

- EC2 콜드스타트 트리거 방식
- 분석 시점 = 방송 중 점진 처리 + 종료 후 30분~2시간 내 최종
- DynamoDB는 LLM 추천만 듣고 박은 것. 강의 트레이드오프 대상
- Docker 미정 (당분간 EC2만)
- 인증 시스템 + React 프론트엔드 구현 의지 (단, 프론트 자체는 AI 위임)
